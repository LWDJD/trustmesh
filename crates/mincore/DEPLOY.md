# `tm_mincore` 部署清单

> 这份清单是**上线前逐条打勾**用的。
> 协议细节见 [`PROTOCOL.md`](PROTOCOL.md)，威胁模型见 [`../../审计/威胁模型.md`](../../审计/威胁模型.md)。

## 0. 三条不可妥协的

| # | 检查 | 不做会怎样 | 怎么验 |
|---|---|---|---|
| **1** | **`cap` 全网一致** | cap 不一致 ⟹ 长度不符 ⟹ 整条视图被拒 ⟹ **网络分裂成互不通信的孤岛** | 全网配置逐节点核对；或改用 `encode_prefixed`（cap 写进字节头） |
| **2** | **每个 node 都验签** | `on_view` 不信 `owner` 参数 ⟹ 任何人可冒充你最好的朋友，把女巫塞进你的分布 | 只接受「字节 + owner + 时间戳」三者验签通过的视图 |
| **3** | **发现从自己的清单出发** | 用别人给的名单发现节点 ⟹ 攻击者能决定你能看到谁（eclipse） | `tick()` 只从 `claims()` 抽人；检查你的发现逻辑没有引入外部名单 |

## 1. 参数

| 参数 | 默认 | 怎么定 | 主要影响 |
|---|---|---|---|
| `beta` | 0.3 | **要你拍板** | 决定「防陌生人刷分」vs「防熟人背叛」的权衡。β↑ 更抗串谋但更圈子化 |
| `half_life` | 72 | 与业务节奏一致 | 「伤害时效」：伤害多久衰减一半。72h 让攻击残留从 0.990 掉到 0.250（−74.7%） |
| `cap` | 512 | `>= 你的关注上限` | 视图字节数 = `cap*6+2`。cap=128(770B) / 256(1538B) / 512(3074B) |
| `decay_enabled` | true | 除非做消融实验 | 关掉 ⟹ 时间不再衰减（攻击残留不退） |

**`cap` 取值实测**（5 seed × 440 账户，诚实观察者视角）：

| cap | 字节 | S1 女巫 | 分布覆盖 | 截断次数 |
|---|---:|---:|---:|---:|
| 64 | 386 B | **精确 0** | 87.6% | **214,181** |
| 128 | 770 B | **精确 0** | 90.9% | 42,499 |
| **256** | **1,538 B** | **精确 0** | 90.9% | **0** |
| 512 | 3,074 B | **精确 0** | 90.9% | 0 |

**S1 与 cap 无关**（四档全精确 0）—— 定长表没有哈希碰撞就没有噪声底。
所以 cap 是**纯工程权衡**（流量 vs 分布宽度），不涉及安全。
默认建议 256：与 512 的 S1/覆盖完全相同，但体积只有一半且截断次数也是 0。

⚠️ 「256 零损失」是**那张图的属性**（`max_follows=256` 限制了清单长度）。
换成关注上限 1000 的图，cap=256 会开始截断。经验规则 `cap >= max_follows`。
详见 [`../../审计/cap决策.md`](../../审计/cap决策.md)。

## 2. 应用层必须实现（内核不管）

| # | 能力 | 为什么内核不管 |
|---|---|---|
| 1 | 账户号 ↔ 公钥映射 | 内核的 `Acc` 是不透明 `u32`，它不知道公钥 |
| 2 | 视图验签 | `on_view(owner, ...)` 的 `owner` 是调用方声称的 |
| 3 | 投递 / 超时 / 重试 | `tick()` 只给「该问谁」 |
| 4 | 节点发现 | 内核完全不碰传输层 |
| 5 | 防 DDoS / 防淹没 | 明确不承诺 |
| 6 | 内容排序 / 推荐 | 明确不做（`设计规格.md` §0.2 归应用层） |

## 3. 运行时

| # | 检查 | 为什么 |
|---|---|---|
| 1 | 每轮 `publish` 一次，不要更频繁 | 发布是 `O(视图数 × cap + 清单长度)` |
| 2 | `k`（每轮抽样数）按业务定 | 见 `审计/A10-抽样参数k与轮次节奏.md` |
| 3 | 连续失败的节点用 `probe()` 兜底 | `probe` 从整份清单抽，比 `tick` 更广 |
| 4 | **关机前存快照** | 否则重启后节点在**下一步就分叉** |
| 5 | 监控 `stats()` | `(接受数, 拒绝数)`，拒绝率突然升高 = 有人在塞垃圾/验签失败 |

## 4. 读数消费

| 要点 | 说明 |
|---|---|
| 用 `query(acc)` 还是 `distribution()` | 关心单点时用 `query`（`O(来源数·log cap)`）；要整份分布时用 `distribution`（`O(视图数·cap + 清单长)`） |
| 两者一致 | 同状态下 `query(acc,now)` 恰等于 `distribution(now).get(acc)`（有测试守着） |
| **不要跨节点比较** | 声望是**同一节点内的相对排序**，不同节点的清单/视图不同，读数不可比 |
| 不要当绝对分用 | `[0,1]` 是归一化后的相对值，不是「可信度得分」 |
