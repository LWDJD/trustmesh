# P0 为什么不能在 Count Sketch 上独立修复

> 测于 2026-11-23。**结论**：`total_mass` 的「发布方声明 + 接收方校验」方案
> 在 Count Sketch 表示下**不存在紧的可验证下界**，因此无法独立于 P2 修复。
> 正确路线是 P0 与 P2 合并：先把视图表示换成 A12 定长稀疏表。

## 1. 问题复述

`crates/engine/src/runtime.rs` 的 `Engine::on_view` 用**接收方自己的账户表**求和得到分母：

```rust
let mut total_mass = 0.0f32;
for i in 0..self.accounts.len() as u32 {
    if let Some(k) = self.accounts.key_of(i) {
        let q = view.query(&k);
        total_mass += q.clamp(0.0, 1.0);
    }
}
```

⟹ 同一份视图字节，账户表大的接收方算出大分母 ⟹ 读数被系统性压低。

**墙 1：跨节点语义不一致**（`crates/engine/examples/unbounded_mass_divergence.rs`）

⟹ 耗时随账户表长度**线性增长**。攻击者只需让我 intern 大量不同 key（每 key 32 字节），
我的每条 `on_view` 就变慢，直到处理不过来。

## 2. 测过的方案：发布方声明 + L1 范数校验

### 方案设计

1. `CompressedView` 加 `declared_mass` 字段，与视图一起传输（+4 字节）
2. 发布方职责：`D = Σ min(score, 1)`，在 `add` 时累加（Count Sketch 不可枚举，只能边写边记）
3. 接收方：直接用 `D` 作分母 ⟹ **O(1)**，跨节点一致
4. 校验：接收方算视图的 L1 范数 `L1 = Σ_h Σ_b |cell[h][b]|`，要求 `D ≥ K·(L1/d)`

### 校验的原理

```text
每个 add(key, s) 在 d 个 hasher 行各贡献一次 sign*s
无碰撞时:  L1 = d · Σ|s|   ⟹   Σ|s| = L1/d
有碰撞时:  |Σ| ≤ Σ|·|（三角不等式） ⟹ L1/d ≤ Σ|s| ⟹ 是下界 ✅
```

协议规定评分 ∈ [0,1]，所以 `min(s,1) = s` ⟹ 诚实视图下 `D = Σs = L1/d`（无碰撞时精确）。

### 致命的实测结果：R 随写入条数衰减

定义 `R = (L1/d) / D`。测三组桶配置、写入 n 个账户各 1.0：

| 写入条数 n | R（2048×5，默认） | R（256×3） | R（1024×7） |
|---|---|---|---|
| 1 | 1.0000 | 1.0000 | 1.0000 |
| 10 | 1.0000 | 1.0000 | 1.0000 |
| 50 | 0.9840 | 0.8933 | 0.9543 |
| 100 | 0.9640 | 0.8200 | 0.9400 |
| 200 | 0.9500 | 0.6933 | 0.9057 |
| 350 | 0.9280 | 0.5886 | 0.8539 |
| 500 | 0.8840 | 0.4947 | 0.8000 |
| 1000 | 0.8004 | 0.3793 | 0.6723 |
| 2000 | 0.6646 | 0.2613 | 0.5264 |
| 5000 | **0.4732** | **0.1747** | **0.3479** |

**混合评分（90% 写 0.5、10% 写 1.0）**：n=100 R=0.9673 / n=500 R=0.8938 / n=1000 R=0.8145
**小评分（全部 0.1）**：n=100 R=0.9640 / n=500 R=0.8840 / n=1000 R=0.8004
（与均匀 1.0 完全一致 —— 说明 R 只取决于**条数**与碰撞程度，与分值大小无关）

### 为什么这条路不通

校验规则 `D ≥ K·(L1/d)` 要**不误拒合法视图**，必须 `K ≤ min(R)`。
但 R 随 n **单调下降且无下界**：碰撞把 L1 吞掉的比例取决于 n，
而 n（发布方写了多少条）是**发布方的私密信息** ——
Count Sketch 不可枚举，接收方无从得知。

⟹ **不存在与 n 无关的紧 K。**

各 K 下攻击者能达到的放大倍数上限 `1/(K·R)`：

| K | R=0.95 | R=0.80 | R=0.47 | R=0.17 |
|---|---|---|---|---|
| 0.4 | 2.6× | 3.1× | 5.3× | 14.6× |
| 0.5 | 2.1× | 2.5× | 4.3× | （误拒合法视图） |
| 1.0 | 1.05× | （误拒） | （误拒） | （误拒） |

对比**完全不校验**：放大上限 = `D_honest`，即写入 1000 条时可放大 **1000 倍**。

⟹ 校验能把「无界放大」压到「有界放大」，但**压不到 1 倍**，而且 K 越紧误拒风险越大。
这不是工程取舍就能解决的问题，是**表示本身的信息损失**。

### L1 校验下的残余收益（实测）

按 K=0.5 的规则，攻击者会把声明值压到规则允许的**最小值** `D_min = 0.5·(L1/d)`。
单来源写入 n 个目标各 1.0 时，实测它的总读数预算：

| 写入条数 n | R | D_min（K=0.5） | 攻击者总读数 | 预算倍数 |
|---|---|---|---|---|
| 1000 | 0.8004 | 400.2 | 2.3763 | **2.38×** |
| 2000 | 0.6646 | 664.6 | 2.6106 | **2.61×** |
| 5000 | 0.4732 | 1183.0 | 3.1148 | **3.11×** |
| 10000 | 0.3508 | 1754.0 | 3.8180 | **3.82×** |
| 20000 | 0.2519 | 2518.8 | 4.8873 | **4.89×** |

对比「完全不校验」时的实测：`D=1` ⟹ **951/1000 个目标的读数饱和到 1.0**、
总读数 665.7（**951 倍放大**）。

⟹ L1 校验确实把「951 倍无界放大」压到了「2.4~4.9 倍」，**但它压不住增长**：
放大倍数随写入条数 n **单调上升**（n=1000 时 2.38×，n=20000 时 4.89×，n 更大时继续增长），
因为 R 随 n 单调下降，而 D_min 跟着 L1/d 一起缩小。

### 误拒边界

实测 min(R) = 0.3508（n=10000）⟹ `K ≤ 0.3508` 时诚实视图一律通过。
但 `K` 每调小一点，攻击者的放大倍数就同比例变大 —— **这是同一枚硬币的两面**，
不存在能同时满足「零误拒」与「有界放大」的 K。
## 3. 为什么 A12 稀疏表能解决

`crates/mincore/src/view.rs` 的归一化是**精确整数运算**，不是估计：

```rust
// decode 时从槽位重算，不读也不信任何声明值
let total_q = slots.iter().map(|&(_, q)| u32::from(q)).sum();

/// Σ 分数（精确整数，u32）
#[must_use]
pub fn total_q(&self) -> u32 { self.total_q }

/// 归一化观点 q / Σq；不在表里或空表返回 0。
#[must_use]
pub fn normalized(&self, acc: Acc) -> f32 {
    if self.total_q == 0 { return 0.0; }
    (f64::from(self.q_of(acc)) / f64::from(self.total_q)) as f32
}
```

三个目标一次达成：

| 目标 | 为什么稀疏表满足 |
|---|---|
| 跨节点一致 | `total_q` **由字节唯一决定**，任何节点解码同一份字节得到同一个 `u32` |
| 无法虚报 | `total_q` 是**重算出来的**，不是读声明值 ⟹ 没有可虚报的字段 |
| O(1) | 只需 `binary_search` + 一次除法，与接收方账户表长度无关；且 `cap ≤ 4096` 有上界 |

另外还有一个附带好处：`Σv ≡ 1` 在声明集合上成立（mincore 有专门测试
`normalized_声明集合上求和恒一`），影响力预算天然闭合。

## 4. 建议路线

**P0 与 P2 合并成一步**：先把视图表示从 Count Sketch 换成 A12 定长稀疏表，
`total_mass` 的跨节点不一致与 O(N) 放大器**随之自动消失**，不需要额外的声明字段
也不需要任何校验。

在 P2 完成前：

1. `total_mass` 的跨节点不一致应作为**已知限制**写进 `SECURITY.md`
   （与现有「单节点可用、跨节点不可比」的口径对齐）；
2. `crates/engine/examples/unbounded_mass_divergence.rs` 与 `unbounded_onview_cost.rs`
   保留为**探针**（它们钉住的就是这个问题，P2 完成后应改为断言「恒为 1.00」与「不随长度增长」）；
3. 不要为 Count Sketch 加声明字段 —— 那会在 P2 之后变成又一个要拆的东西。

## 5. 影响范围

| 使用档位 | 是否触发 |
|---|---|
| **L1 原型 / L2 单节点** | **不触发**：只有一个节点，分母唯一，没有跨节点比较 |
| L3 对抗性（多节点但各自只看自己的读数） | **部分触发**：读数受本节点账户表长度影响，但没有人拿两个节点的读数对比 |
| **L4 大规模（跨节点比较同一账户声望）** | **完全触发**：这是本缺陷的定义场景 |

⟹ 现阶段（L2 档）这个缺陷**可以被接受**，但一旦有「A 节点觉得某人 0.9、B 节点觉得他 0.1」
这种场景出现，就必须先做 P2。
