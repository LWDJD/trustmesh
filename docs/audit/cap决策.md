# cap 决策：两个探针合起来看

> 2026-11-18。有两个探针，各回答一半问题：
>
> | 探针 | 回答什么 |
> |---|---|
> | `cap_loss` | cap 调小会**丢多少质量** |
> | `cap_sensitivity` | 丢了之后**反女巫效果差多少** |

## 0. 结论

**cap 是本库唯一需要你拍板的参数，而它只影响「分布有多宽」，不影响「反女巫有多强」。**

| cap | 字节 | 反女巫 S1 | 分布覆盖 | 截断量 | 建议 |
|---:|---:|---:|---:|---:|---|
| 64 | 386 B | **精确 0** | 87.6% | **214,181 次** | ❌ 太小，信息损失明显 |
| **128** | **770 B** | **精确 0** | 90.9% | 42,499 次 | ✅ 省流量首选 |
| **256** | **1,538 B** | **精确 0** | 90.9% | **0 次** | ✅ **默认推荐** |
| 512 | 3,074 B | **精确 0** | 90.9% | 0 次 | ⚠️ 无收益（与 256 完全相同） |

---

## 1. 最反直觉的发现：**S1 与 cap 完全无关**

四档 cap（64/128/256/512）的 S1 女巫声望**全部是精确 0.000000**。

这是定长表的结构性质，不是参数调出来的：**定长表里没有哈希碰撞，就没有噪声底**。
所以「cap 调小会不会让女巫溜进来」的答案是 —— **不会**。

**这条很重要**：它意味着 cap 的选择是一个**纯工程权衡**（流量 vs 分布完整性），
不涉及安全。你不需要为了安全而牺牲流量，也不需要为了流量而牺牲安全。

---

## 2. cap 到底影响什么

### 2.1 分布条数 / 覆盖账户

| cap | 分布条数 | 覆盖账户 |
|---:|---:|---:|
| 64 | 385 | 87.6% |
| 128 | 399 | 90.9% |
| 256 | 399 | 90.9% |
| 512 | 399 | 90.9% |

`cap=64` 已经开始丢账户（385 vs 399，少 14 条 = 3.3 个百分点）。
`cap=128` 起就饱和了 —— 说明这张图的信息量在 128 条就基本装得下。

### 2.2 诚实账户的分化程度（S3：最大值 ÷ 均值）

| cap | S3 |
|---:|---:|
| 64 | 4.5214 |
| 128 | 4.0122 |
| 256 | **3.9866** |
| 512 | **3.9866** |

**cap 越大，S3 越低**（3.9866 < 4.0122 < 4.5214）。这是**好事**：
分布越完整，头部账户的优势越接近真实比例，而不是被截断放大。
cap=256 与 cap=512 完全相同 ⟹ **256 之后没有收益**。

---

## 3. 为什么默认建议 256 而不是 512

| 理由 | 说明 |
|---|---|
| **收益归零** | 256 与 512 的 S1/S3/覆盖**完全相同**（本图信息量在 256 就装下了） |
| **流量减半** | 1,538 B vs 3,074 B |
| **但零损失** | 256 的截断次数也是 0，不是「用损失换流量」 |

**唯一该用 512 的情况**：你的关注上限超过 256。经验规则 `cap >= max_follows`。

---

## 4. 但「256 零损失」是这张图的属性，不是 cap 的属性

这张图零损失，是因为 `max_follows=256` 本身就限制了每人最多关注 256 个，
所以清单长度天然 ≤ 215。换成「关注上限 1000」的图，`cap=256` 就会开始截断。

**所以 §0 的表只在「关注上限 ≤ 256」的网络里成立。**
部署前必须按你自己的关注上限重跑这两个探针。

## 5. 复现（两个探针都在 crates/mincore/examples/）

~~~powershell
$env:TMP="<仓库根>/.tmp"; $env:TEMP=$env:TMP
cd crates/mincore

cargo run --release --example cap_loss         # 截断损失（5 seed × 400 账户，约 3 秒）
cargo run --release --example cap_sensitivity  # 反女巫效果（5 seed × 440 账户，约 12 秒）
~~~

## 6. 我在写这两个探针时踩的坑（对后来者有用）

### 6.1 `Kind::Sybil { cluster }` 的 cluster 是身份的一部分

`w.indices_of(Kind::Sybil { cluster: 2 })` 只拿到**第 3 个集群**，不是全部女巫。
我第一次拿到 0 个女巫，然后 `sum / len` 直接除零 panic。
正确做法：遍历 `0..k` 合并。

### 6.2 S1 必须只统计**诚实观察者**

我第一次把「所有观察者的女巫声望平均值」当 S1，得到 **0.002273** ——
看着像「女巫几乎拿不到声望」，很符合预期。**但它测的是错的东西**：
那些观察者里有一半是女巫自己，女巫看女巫当然有分数（集群内互评是设计预期的）。

改成只统计诚实观察者后：**精确 0.000000**。

**教训**：一个「看着合理的小数字」比一个「明显荒谬的大数字」危险得多 ——
后者你会去查，前者你会直接接受。

### 6.3 `on_view` 要求「我已给 owner 打过分」

这是结构性拒绝（`src/node.rs:223`）：没关系的来源，观点对我没有权重，存了也没用。
所以模拟收视图时必须先检查 `rated.contains(owner)`，否则收到的视图数恒为 0。
