# cap 该设多大：截断损失 vs 清单长度的实测曲线

> 2026-11-18。作者的设计意图原话：「**文件越大精度越高**」——
> 这一份把这个说法量化：给定社会图的清单长度分布，`cap` 取多少才开始丢质量、丢多少。

## 0. 一句话结论

**本测试图的清单长度 p99 = 187，max = 215。所以 `cap = 256` 已经零损失，`cap = 128` 会截断 20.1% 的视图、平均丢 2.81%。**

注意这和 A12 报告里的「cap=128 截断 20.8%、平均丢 1.49%」不同 —— 那份用的是另一批参数（见 §4 差异说明）。

---

## 1. 复现

~~~powershell
$env:TMP="<仓库根>/.tmp"; $env:TEMP=$env:TMP
cd crates/mincore
cargo run --release --example cap_loss
~~~

实验设置：`tm_sim::World`，`n_initial=400`、`steps=120`、`follow_min=120`/`follow_max=200`/`max_follows=256`、
`attack_kind=None`、**5 个 seed**（1~5）合并统计，共 **2,000 个账户视图**。

---

## 2. 清单长度分布（这是「文件该多大」的决定因素）

| 分位 | 清单长度 |
|---|---:|
| min | 62 |
| p25 | 87 |
| **p50** | **100** |
| p75 | 123 |
| p90 | 147 |
| **p99** | **187** |
| **max** | **215** |

**读法**：这个图里没有人给出超过 215 条正分。所以只要 `cap >= 215`，就是**零损失**。

---

## 3. 截断损失曲线

| cap | 视图字节数 | 被截断的视图 | 平均损失 | 最大损失 |
|---|---:|---:|---:|---:|
| 64 | 386 B | **99.8%** | **36.81%** | 70.23% |
| **128** | **770 B** | **20.1%** | **2.81%** | 40.47% |
| **256** | **1,538 B** | **0%** | **0%** | **0%** |
| 512 | 3,074 B | 0% | 0% | 0% |
| 1024 | 6,146 B | 0% | 0% | 0% |

### 3.1 关键读法

- **cap=64 会毁掉数据**：99.8% 的视图被截、平均丢 **36.81%** 的质量。不能用。
- **cap=128 有可见损失**：每 5 个视图就有 1 个被截，平均丢 2.81%，最坏 40.47%。
  这个「最坏 40%」是**单个账户**的灾难：如果某人的清单 215 条而 cap=128，
  他发布的视图只剩 128 条 ⟹ 他认识的那 87 个人在别人眼里**完全不存在**。
- **cap=256 起零损失**（在本图上）。1,538 字节 = Count Sketch 的 **3.8%**。

### 3.2 但「零损失」是图的属性，不是 cap 的属性

这个图是 `follow_max=200`/`max_follows=256` 造的 —— **社交图本身限制了每人最多关注 256 个**。
所以清单长度天然 ≤ 256。**换成「关注上限 1000」的图，cap=256 就会开始截断。**

⟹ **cap 必须按你实际的关注上限来定，不能照抄 256。**
经验规则：`cap >= 你的 max_follows`（这样零损失），否则要接受 §3.1 的尾部损失。

## 4. 与 A12 报告数字的差异（必须说明）

| 项 | A12 报告 | 本探针 | 为什么不同 |
|---|---|---|---|
| 截断视图占比（cap=128） | 20.8% | 20.1% | 图参数不同（A12 用 `attack_kind` 混合场景 + cap 512 基线） |
| 平均损失（cap=128） | 1.49% | 2.81% | A12 的分数字段更**不均匀**（真实世界评分），本探针用**等分**（1/L） |

**等分是最坏情况**：所有条目同分 ⟹ 截断丢掉的质量占比最高（保留下来的条数比例即质量比例）。
真实评分如果高度集中在少数人身上，截断丢的质量会更少（因为高分条目优先保留）。

所以 **2.81% 是上界，1.49% 是更真实的下界**。两个都对，取决于分数分布。

---

## 5. 对 cap 默认值的建议

| 你的场景 | 建议 cap | 字节 | 理由 |
|---|---:|---:|---|
| 关注上限 ≤ 256 | **256** | 1,538 B | 零损失，且只有 Count Sketch 的 3.8% |
| 关注上限 ≤ 128 | **128** | 770 B | 零损失，最小体积 |
| 关注上限 512 | 512 | 3,074 B | 零损失 |
| 想省流量、能接受尾部损失 | 128 | 770 B | 每 5 个视图截 1 个，平均丢 2.81% |

**⚠️ 无论选哪个，`cap` 必须全网一致** —— 定长格式不自描述，发送方 cap=256（1,538 B）
而接收方期望 770 B ⟹ 长度不符 ⟹ 整条拒绝 ⟹ **网络分裂成两个互不通信的孤岛**。
这也是 `审计/有损压缩架构.md` §5 里那个「三个解法」的问题。

## 6. 探针代码

`crates/mincore/examples/cap_loss.rs`（78 行，可重跑）。
核心调用是 `SparseView::truncated_mass(cap, &pairs)` —— 这是 mincore 自带的静态估算口径，
返回「1 − 保留的定点质量 / 全部定点质量」，不需要真的建表就能算损失。
