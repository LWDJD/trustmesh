# 传输淹没：女巫接管网络传输层，这个库能做什么

> 装置：`crates/engine/examples/transport_flood.rs` / `transport_mitm.rs` / `bootstrap_list.rs`。
> 2026-11-17。回答作者：「我要的是**传输上的淹没**——女巫节点接管整个网络，
> 导致正常节点无法正常发现其他的正常节点」。

## 0. 先划清一条线（这是最重要的一句）

`设计规格.md` §0.2 已经把**节点发现、连接建立、加密与认证**划给「应用层 / 覆盖网络」。
所以**发现协议本身不在本库范围内**——本库不能决定「你能连上谁」。

但本库与传输层之间有一个**明确的接口**，而这个接口恰恰是抗劫持的关键：

```text
本库每轮   →  tick()/probe()      →  「我该去要这几个账户的观点」（FetchRequest 列表）
应用层     →  网络 I/O            →  成功 on_view / 失败 on_view_failed
```

**这份 FetchRequest 名单只由我自己的评分产生，任何对端都无法注入或删除。**

---

## 1. 传输被淹没 = 全部请求失败：本库会怎样（`transport_flood.rs`）

**设定**：我评过 40 个人；k=6；每轮 12h；**连续 30 轮，每一个取观点请求都失败**（100% 失败率）。

| 问题 | 实测 |
|---|---|
| 引擎会不会停止请求？ | **不会**。30 轮里发出 172 个请求全部失败后，第 31 轮仍返回 6 个请求 |
| 会不会卡死？ | **不会**。最长连败 5 次，退避权重有下限（2^-64），永不为 0 |
| 会不会遗忘？ | **不会**。`query` 前后**最大绝对差 = 0.00000000**（逐位相同） |
| 正分清单会不会被清？ | **不会**。仍是 40 条。传输失败**不删除**任何评分 |
| trust_distribution 还正常？ | **正常**。40 个非零条目，总和 = 1.000000 |
| 有没有兜底通道？ | **有**。`probe()` 不走退避，一次返回 22 个请求，强制覆盖本轮全部条目 |

### 1.1 三条结构性保证

1. **退避永不归零**：`backoff_weight` 用相对指数 `2^-(streak - min_streak)`，
   截断在 `BACKOFF_MAX_EXPONENT`，所以再多失败也抽得出东西（`store/src/lib.rs:1064`）。
2. **失败只改退避输入**：`on_view_failed` → `record_failure` 只 `fail_streak += 1`，
   **不动** `last_check`、**不动** `score`（`store/src/lib.rs:469`）。
3. **个人项永不衰减、永不依赖网络**：即使一份观点都收不到，我对每个人的评分一点不丢。

### 1.2 代价（必须说清）

传输全废时，**群体项归零**（一份观点都收不到 = 全员弃权），结果退化为 `β·个人项`。
也就是说：**判断还在，但会变「只看自己的观点」**。这是可逆的——传输恢复后自动恢复。

---

## 2. 传输被接管 = 攻击者可冒充任何对端：本库挡得住多少（`transport_mitm.rs`）

这比「请求失败」严重得多，也是你真正担心的那条（**eclipse attack**）。

**设定**：我信任 8 个人；攻击者接管传输，把**每一份朋友的观点**都换成伪造的
（伪造内容：500 个女巫各 100 分）；我也 intern 了那 500 个女巫。

| | 正常状态 | 传输被接管后 |
|---|---:|---:|
| 朋友声望均值 | 0.125000 | 0.037500 |
| 女巫声望 | 0.000000 | **0.010937** |
| 女巫 / 朋友 比值 | 0.0000 | **0.2917** |
| 正分清单 | 8 条 | **仍是 8 条** |
| 女巫在清单里？ | 不是 | **仍然不是** |
| 引导名单（shares） | 8 条 | **仍是 8 条，全是我评过的朋友** |

### 2.1 关键分界：攻击者能伪造「朋友说了什么」，但伪造不了「谁是我的朋友」

| 攻击者能改的 | 攻击者改不了的 |
|---|---|
| 观点**内容**（`CompressedView` 的字节） | 正分清单（`PositiveList`，只由我的 `rate` 决定） |
| 观点的 `published_at` / `last_check` | 份额分配（`share = score / total_rating`） |
| 观点里的账户列表 | 引导名单（`shares()`，见 §3） |
| 对端自述的身份 | 抽样决策（`RoundSampler`，本地状态） |

**所以传输接管的最坏后果是「群体项被污染」——这正是 S3（背书 4.35 倍）/ S5（套利 1.60 倍）
已经量化的东西，不是「我的名单被篡改」。**

### 2.2 但本库不做验签

`设计规格.md` §0.2 把「加密与认证」划给应用层，本库**不做**观点签名验证。
所以「传输被冒充」在本库层面只能被**减损**（靠清单与份额的本地性），**不能被消除**。

**应用层必须做的**：观点签名 + 对端身份认证。这是 eclipse 防御的**第一道**，也是唯一一道真正有效的。

---

## 3. 本库能给应用层的抗劫持工具：`shares()` 就是引导名单（`bootstrap_list.rs`）

eclipse 的标准防御是：**不要从对端学「网络里有哪些节点」，而是从本地可信名单起步**。

本库恰好天生提供这份名单：`Engine::shares()` 返回「我给谁打了正分、各占多少份额」。

**实测**：我给 8 个朋友各 1.0；500 个女巫在网络上狂欢，冒充我 8 个朋友各投一份 100 分自吹视图。

```text
shares 条数：8 → 8（不变）
shares 内容变化：0 条（女巫完全没能动我的引导名单）
传输全挂 20 轮后：shares 仍有 8 条 —— 引导名单不依赖网络
```

### 3.1 对端**无法**做的事（因为 `shares()` 只读本地评分）

* 无法**注入**新节点（要进 `shares()` 必须我先 `rate` 它）
* 无法**删除**现有节点（删除要我 `rate(负数/0)`，而负分路径已砍掉、0 = 没表态）
* 无法**花钱买位置**（份额 = 我的评分比值，不是对端说了算）
* 无法**通过谎报「我有很多节点」**影响它（本库完全不看对端自述）

### 3.2 应用层的用法

```text
1. 节点发现从 shares() 里的 N 个账户起步（而不是硬编码种子）
2. 每个候选节点多路尝试（因为 shares() 不知道谁在线）
3. 首次冷启动 shares 为空 —— 此时才需要硬编码种子，且**只在那一次**
```

### 3.3 它做不到的三件事

* **不知道**哪些对等节点在线 —— 那是传输层的事；
* **不能保证** shares 里的节点此刻可达 —— 需要应用层多路尝试 / 重试；
* **首次冷启动时为空** —— 种子节点仍需应用层提供（这是**唯一**需要信任外部输入的时刻）。

## 4. 直接回答「传输淹没这个威胁，这个库够不够」

| 威胁的具体形式 | 本库能做什么 | 够不够 |
|---|---|---|
| 请求全部失败（链路被打掉） | **引擎不崩、不忘、不停**；`probe()` 兜底；个人项逐位不变 | **✅ 够**（实测 100% 失败率 × 30 轮） |
| **发现协议被劫持**（对端谎报网络只有它们） | **`shares()` 提供不依赖对端的引导名单** | **✅ 够**（前提是应用层真的用它起步） |
| **伪造观点内容**（MITM 冒充朋友） | 清单与份额无法伪造；但观点内容能 | **⚠️ 只能减损**（女巫/朋友比值 0.29，不是 0） |
| **对端身份冒充** | **本库不做验签** | **❌ 必须应用层做**（`设计规格.md` §0.2） |
| 女巫挤占 my 的连接配额（DDoS） | **本库不碰连接** | **❌ 应用层 / 传输层**（`设计规格.md:22`） |
| 已知诚实节点被集体封锁 | 建议：应用层多路（隐藏服务/中继）；本库不碰 | **❌ 应用层** |

### 结论

> **传输「淹没」有两层，本库只负责其中一层，而且负责得很干净：**
>
> 1. **接口层（本库负责）**：即使传输 100% 失效，引擎不停、不忘、不丢名单；
>    `shares()` 提供一份**对端无法篡改**的引导名单。**这层实测通过。**
> 2. **发现协议层（应用层负责）**：真正的 eclipse 防御是「签名验证 + 从本地名单起步 + 多路发现」。
>    本库提供第 2 项的**原料**（`shares()`），但不实现协议。

> **所以答案是：作为「传输被淹没时仍然能算出可信名单、并且能告诉你该去找谁」的库，够了。**
> **作为「防止节点被发现协议劫持」的完整方案，不够——但缺的那一半在设计上就归应用层。**

---

## 5. 一条必须写进集成文档的约束

**`shares()` 是 eclipse 防御的关键出口，应用层若不用它起步，本库对传输劫持毫无帮助。**

用错的方式：

```text
❌ 从对端学「网络里有哪些节点」 → 对端全女巫 → 我只认识女巫
❌ 硬编码一份种子列表 → 种子被打掉 → 再也连不上
```

对的方式：

```text
✅ 每次开机先从 shares() 取 N 个起步（这 N 个是被我评过的人，不是对端告诉我的）
✅ 每个候选多路尝试 + 签名验证
✅ shares() 为空时才用硬编码种子（只在首次冷启动）
```

~~~powershell
$env:TMP="<仓库根>/.tmp"; $env:TEMP=$env:TMP
cd crates/engine
cargo run --release --example transport_flood   # 100% 请求失败 × 30 轮

~~~
