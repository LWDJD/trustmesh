# 工程可用性评估（2026-11-22）

> 作者问：「我不知道现在能不能投入工程使用，你有什么建议吗，因为整个东西都是 Vibe coding 的产物。
> 我自己只提供了想法。」

> **结论先说**：能用于 **L2（小规模、单机、可信网络）**，不能用于 L4（跨节点语义一致、无限网络）。
> 离 L3 差一项：参数误用护栏。离 L4 差一项：`total_mass` 的 P0 修复。

---

## 0. 三级判定

| 级别 | 定义 | 判定 | 差什么 |
|---|---|---|---|
| **L1 可原型/内部试用** | 编译过、测试绿、无内存安全风险、行为可复现 | ✅ **满足** | — |
| **L2 可小规模生产**（单机、n ≤ 366、可信网络、可重启） | L1 + 性能可接受 + 状态可持久化 | ✅ **满足（有前提）** | 前提：显式设 `max_views`、n 不要超过几百 |
| **L3 可对抗性生产**（真实攻击者、不可信网络） | L2 + 不可信输入不崩 + 已知攻击已定界 + **参数误用有护栏** | ⚠️ **差一项** | 参数误用只有文档警告，没有强制 |
| **L4 可大规模生产**（跨节点一致、无限网络） | L3 + **跨节点语义一致** + 无 O(N) 放大器 | ❌ **不满足** | P0 `total_mass` 未修 |

## 1. 可以信的部分（这些是实测的，不是「作者说对」）

| 承诺 | 证据 | 强度 |
|---|---|---|
| 963 测试全绿 / 0 failed / 6 ignored | `verify-all.ps1` 每次实跑 | 强 |
| 零 unsafe | 6 个 crate 全部 `#![forbid(unsafe_code)]`，编译器强制 | **最强** |
| 零外部依赖 | CI `no-external-deps` job + 本地 `verify-all` | **最强**（供应链风险 = 0） |
| 跨平台逐位一致 | wasm32 vs native 两套 IDENTICAL（36 + 2739 个 f32 位模式） | 强 |
| 不可信字节不崩 | `untrusted_bytes.rs` 7 条：随机字节 / 每种截断前缀 / 每个字节位置的 ±Inf/NaN | 强 |
| 快照可精确恢复 | round-trip 200,000 个点，最大位差 0 | 强 |
| 测试与被测不同源 | `untrusted_bytes.rs` 刻意不用库内 `Rng`；`crates/exp` 不依赖 engine 自己重写传播链 | 强 |
| 性能有完整曲线（含「什么时候会输」） | n=100..1600 全路径实测，还量化了 mincore 慢 17× 的区间 | 强 |

**这几条在 Vibe coding 产物里属于罕见的扎实**——特别是「测试刻意不用被测实现」和
「性能不是只测最优路径」这两条，多数 AI 生成的项目会同时踩这两个坑。

## 2. 不能信的部分（每一条都是硬约束，不是建议）

### 2.1 跨节点语义不一致（P0，`total_mass`）

**这是最严重的一条**：同一份视图字节，不同节点算出不同声望。

实测（`cargo run --release --example unbounded_mass_divergence`）：

```text
发布者 P 给 300 个账户各 0.6 分（真实清单长度，不是极端构造）
观察者账户表长度      某账户声望        相对基线
           301        0.00231788        1.00
           397        0.00231788        1.00
          1297        0.00230263        0.99
         10297        0.00216718        0.93
        100297        0.00128913        0.56
       1000297        0.00024114        0.10
```

**根因**：`on_view` 用「我 intern 过多少个账户」当分母去估这份观点的总质量，
而总质量本应是「发布者写了多少内容」，与接收方无关。

**后果**：
- 节点间声望**不可比较**（S6 跨节点一致性失效）
- 新节点（账户表小）看到的声望系统性偏高 ⟹ **攻击者只要造一个新节点就能放大读数**
- 快照重放会不一致

**安全区间**：实测所有节点账户表长度**相差 < 1000** 时偏差 < 1%。
所以**小规模、节点规模相近**的部署不受影响；一旦节点规模差几个数量级就必须先修 P0。

### 2.2 性能硬墙：`trust_distribution`

| n | `trust_distribution` | `query` | `on_view` |
|---|---|---|---|
| 100 | 3.00 ms | 63 µs | 233 µs |
| 400 | 75.00 ms | 232 µs | 289 µs |
| 800 | ~340 ms | 536 µs | 364 µs |
| 1600 | **1914 ms** | 1.25 ms | 633 µs |

**只有 `trust_distribution` 是硬墙**（它内部 = n 次 query ⟹ O(n·m)）。其余路径温和。
**100 ms 门槛在 n≈366。** 如果你只需要 `query`（查单个人的声望），n 到 1600 都能用。

### 2.3 参数误用没有强制护栏

| 陷阱 | 后果 | 现状 |
|---|---|---|
| `AccountIdx` 是 `intern` 顺序 | 两节点顺序不同 ⟹ 观点整体错位 | 只有 quickstart 的注释警告 |
| `tick(now, k)` 的 `k` | 违反 `(n/k)·T ≤ H/2` ⟹ 衰减变噪声（实测 90.7% 来源 `fs<0.1`） | 有 `recommended_k()` 但要你主动调 |
| 刷新周期 `T` | 同上 | 库不管 |
| `ViewParams` 全网一致 | 不一致就**静默丢弃**，你不知道对面配错了 | 静默 |
| 每个账户（含攻击者）都要建 Engine | 只给诚实账户建 ⟹ S2 恒为 0（**假通过**） | 库不知道 |
| `max_views` 默认 **0 = 无上限** | 内存无界 | 默认不安全，必须显式设 |
| `penalty_strength` 默认 1.0 | 调 `report_bad_account` 就满额惩罚 | 默认行为合理但要知道 |

**这一条是 L3 的缺口**：不是代码错，是「库给了你一辆没有安全带的快车」。

## 3. Vibe coding 特有风险自查

你担心的是对的：Vibe coding 的失败模式不是「代码写不出来」，而是「**测试看起来很全，但全是自证**」。
逐条查了：

| 风险 | 判定 | 依据 |
|---|---|---|
| 测试与实现同源 | ✅ 已避免 | `untrusted_bytes.rs` 刻意不用库内 `Rng`；`crates/exp` 自己重写传播链；`mincore` 是独立第二实现 |
| 边界条件靠想象 | ✅ 较好 | 每种截断前缀遍历、每个字节位置塞 ±Inf/NaN、随机字节长度对/不对都测 |
| 性能只测最优路径 | ✅ 好 | 完整 n=100..1600 曲线，而且明确量化了「mincore 在什么区间更慢」 |
| 依赖别人正确性 | ✅ 无风险 | 零外部依赖 |
| 文档比代码漂亮 | ⚠️ 中 | `设计规格.md` 与代码 **8 处不一致**；`§4.9` 整节代码已删规格还在；审计报告里部分数字是旧口径 |
| 测试只测自洽不测现实 | ⚠️ 中 | 所有验证都在**仿真**里，没在真实网络跑过一秒 |
| **测试数量唬人但判别力弱** | **❌ 未知 = 高风险** | 没做系统性 mutation testing。只零星做过 2 次（换掉 `decay_factor`、改个人项口径），两次都抓住了 |
| **API 没人用过** | **❌ 高风险** | 除了你和我，没有第三方接入过。`Engine` 有 30 个 pub 方法，没有真实反馈 |

**最值得补的一件事是 mutation testing**，理由：
它专门回答「**测试是否真的在测实现**」——而这正是 AI 生成项目最容易骗过自己的地方。
963 条测试听起来很多，但如果 60% 是「用 A 方法的输出喂 A 方法的另一个方法」，它们就抓不住 bug。

**可行性**：`cargo-mutants` 是独立 CLI（`cargo install cargo-mutants`），`它不改 Cargo.toml、不加依赖 ⟹ **不违反零外部依赖原则**。
**但本机装不了**：沙箱的 TLS 证书有问题（`cargo search` 报 `SEC_E_NO_CREDENTIALS`）。

所以我自己做了 5 个**手工 mutation**（改代码 → 跑测试 → 看是否变红 → 还原），结果：

| # | Mutation | 结果 | 判定 |
|---|---|---|---|
| 1 | `beta: 0.3` → `0.5` | 1 failed | ✅ 抓住（但**只靠 1 条** `criteria` 一致性断言） |
| 2 | `half_life: 72` → `24` | 14 failed | ✅ 强 |
| 3 | `SNAPSHOT_VERSION: 2` → `3` | **0 failed** | ❌ **没抓住** |
| 4 | `DECAY_FLOOR` → `0.5` | 1 failed | ✅ 抓住（只 1 条） |
| 5 | `decay` 的 `exponent` ×1.01（1% 系统性偏差） | 5 failed | ✅ 抓住（3 条 agg 单元测试） |

**4/5 抓住。这是好消息**：测试确实有判别力，不是"数量唬人"。

**但第 3 个暴露了一个真实缺口**：

`SNAPSHOT_VERSION` 从 2 改成 3，**所有 479 条测试仍绿**。
原因：所有测试都用同一个常量（编解码两边一起变）。
真实后果：**已存的 v2 快照文件全部解不开了，而测试全绿**。

这是"缺一类测试"，不是"测试写得差"。补法很简单：

```rust
#[test]
fn v2_snapshot_bytes_are_still_decodable() {
    // 硬编码一段 2026-11-22 生成的 v2 快照字节（几百字节）
    let v2_bytes: &[u8] = &[0x54, 0x4d, 0x53, 0x4e, 0x41, 0x50, 0x53, 0x48, /* ... */];
    let snap = EngineSnapshot::decode(v2_bytes).expect("v2 快照必须仍能解");
    assert_eq!(snap.version, 2);
}
```

**7 号建议**里应该加上这一条。

## 4. 建议：分三档用

### 档 1：现在就能用（不需要任何改动）

**场景**：内部工具、原型、单机、账户数 ≤ 几百、节点规模相近。

必须做的 5 件事（**不照做等于没保护**）：

```rust
let cfg = EngineConfig {
    view_params: ViewParams::new(2048, 5, 0),   // 1. 全网统一，写进配置
    max_views: 512,                               // 2. **必须显式设**，默认 0 = 无上限
    ..EngineConfig::default()
};
// 3. intern 顺序必须全网一致 —— 最可靠的保证方式：按公钥字节序排序后批量 intern
for key in sorted_keys { engine.intern(key); }
// 4. k 用 recommended_k()，不要拍脑袋
let k = engine.recommended_k(period);
// 5. 每个账户都要建 Engine（**含攻击者**），否则 S2 是假通过
```

**这个档次的能力上限**：能挡住 S1/S2/S4/S6（结构性的，实测为零），
挡不住熟人背叛（4.37 倍）、单来源自吹（+83%）、重放（×4.0）——这三条 README 里写着。

### 档 2：再补 3 件事就能上对抗性环境

| # | 补什么 | 工作量 | 为什么 |
|---|---|---|---|
| 1 | **参数护栏**：`tick` 里检测 `k` 是否满足 `(n/k)·T ≤ H/2`，违反就 `debug_assert` 或返回警告 | 半天 | 这是 L3 的唯一缺口 |
| 2 | **mutation testing**：证明 963 条测试真的有判别力 | 1~2 天（含分析结果） | 消除最大的未知风险 |
| 3 | **符号签名**：观点必须验签（`设计规格.md` §0.2 归应用层） | 应用层工作 | 不加就是「重放 ×4.0」敞开 |

### 档 3：要上大规模（跨节点一致性）→ 必须先修 P0

| 优先级 | 修什么 | 工作量 | 效果 |
|---|---|---|---|
| **P0** | `total_mass` 改成「发布方声明 + 接收方校验」 | 约 300~500 行 + 测试 | 同时解决跨节点不一致 **和** `on_view` 的 O(N) 放大器 |
| P1 | 账户表只装「清单里的人」 | 约 200 行 | 让 `AccountTable` 有界 |
| P2 | mincore 的定长稀疏表替换 Count Sketch | 大工程 | 解决空账户、内存 183MB→3KB |
| P3 | `AccountTable::max_accounts` 硬上限 | 约 30 行 | 纯防御，即使 P0/P1 不做也有用 |

**P0 是唯一一个「不修就不能上大规模」的**。修它同时解决两个问题（墙 1 与墙 3 同源）。

## 5. 关于「Vibe coding」这件事本身

你说「整个东西都是 Vibe coding 的产物，我自己只提供了想法」——这个担心有道理，但要有区分：

**Vibe coding 真正不可靠的不是代码，是「你没验证过的东西」**。

这个项目的特殊之处在于：**它的验证方式不依赖「作者知道自己在干什么」**。

举几个例子：

| 验证方式 | 为什么它对 vibe coding 特别有效 |
|---|---|
| `#![forbid(unsafe_code)]` | 编译器强制，AI 骗不了 |
| 零外部依赖 | CI 检查 `Cargo.toml`，AI 骗不了 |
| wasm vs native 逐位相同 | 两个真实编译目标的输出比对，AI 骗不了 |
| `crates/exp` 不依赖 engine | 独立重写传播链，能和引擎对拍——**这是真正的交叉验证** |
| `crates/mincore` 是独立第二实现 | 两套架构比 S1~S6，结论是「S1/S2/S4/S6 全面优于」——**这个结论不是自证** |
| 闭式解抽查 | `|G_engine − G_after|` 是拿数学解对拍，不是拿自己对自己 |
| 定向不可信字节测试 | 遍历所有截断前缀、每个字节位置塞 ±Inf/NaN |

**所以这个项目比大多数 vibe coding 产物扎实得多**。原因不是 AI 更聪明，
而是**验证方式选得对**：它一直在找「不依赖实现正确性的外部锚点」。

**但有两个地方确实悬空**：

1. **API 没人用过**——30 个 pub 方法的易用性、默认值是否合理、
   错误处理是否符合使用者预期，这些只能靠真实反馈。
   建议：找个真实场景（哪怕是你自己写个小工具）用一次，会发现一堆「设计上没想到」的问题。

2. **测试判别力未知**——这是 mutation testing 能回答的。
   它会告诉你「963 条测试里有多少是真正在防回归的」。
   通过率 90%+ 说明测试扎实；50% 说明一半测试是装饰。

## 6. 直接回答你的问题

**能投入工程使用吗？**

**能，但要按档用。**

| 你要做的事 | 现在能不能 |
|---|---|
| 内部原型 / 单机小规模（n ≤ 几百） | ✅ **能**，按 §4 档 1 的 5 条做 |
| 对外发布给第三方接入 | ⚠️ **先补参数护栏 + 跑一次 mutation testing** |
| 真实对抗环境（有人会攻击） | ⚠️ 上面 + **观点必须签名**（应用层做） |
| 大规模 / 跨节点声望比较 | ❌ **必须先修 P0 `total_mass`** |

**你现在处在「能给别人试用，但不能承诺 SLA」的位置。**
这个位置对开源项目很正常——Linux 0.01 也是从这开始的。

但有一条要明确：**如果你的用途是「跨节点比较声望」，这个库现在会给你错的答案**，
而且错得很严重（节点规模差 1000 倍时读数差 10 倍）。这不是精度问题，是语义问题。

## 7. 三条最具体的建议

1. **先跑 `cargo mutants`**。它花 1~2 天，但能给你「这个库的测试到底值多少分」的答案。
   这是唯一能反驳「vibe coding 产物不可信」的硬证据。

2. **写一个真实的小应用用它**（哪怕只是自己的书签/关注列表推荐）。
   30 个 pub 方法在纸面上看都合理，真接入一次会暴露「哪个默认值不对」「哪个错误都不报」。

3. **P0 `total_mass` 早修比晚修便宜**。越晚修，越多外部数据按旧语义生成，迁移越贵。
   现在还没发布过，是修它最便宜的时刻。
