# 无限规模：这个库为「理论无限大的网络」还需要改什么

> 2026-11-17。作者要求：「需要为理论无限大的网络来做准备，因为测试规模不受控，
> 而且我的目标也不只是小规模网络。」

## 0. 一句话

**现在这个库在无限网络上有四道墙，其中第 1 道是「核心正确性」问题，不是性能问题。**

| # | 墙 | 严重性 | 根因 |
|---|---|---|---|
| 1 | `total_mass` 依赖**接收方**账户表长度 ⟹ **同一份字节读出不同声望** | 🔴 **最严重**（破坏跨节点一致性） | 规格 §4.2「对已知账户求和」在无限网络里不可计算 |
| 2 | `mass_covers` 是局部编号，被当作「表态范围」上界 | 🟠 中（偏宽松，不造成漏算） | 上界不精确，随账户表变大而越来越松 |
| 3 | **`on_view` 是 O(账户表长度)** | 🟠 性能放大器（实测 50 万账户 → 70 ms/次） | 同 #1 的实现形式 |
| 4 | **`AccountTable` 内存无界**（75 B/账户，100 万 = 109 MB） | 🟠 内存 | 为「听说过」的账户分配永久编号 |

第 1、3 两道墙**同源、同一个修法**。

---

## 1. 墙 1（最严重）：`total_mass` 让同一份字节在不同节点读出不同声望

### 1.1 机制

`Engine::on_view` 计算 `total_mass` 的方式是**遍历接收方见过的全部账户**：

~~~rust
// crates/engine/src/lib.rs:565-576
let mut total_mass = 0.0f32;
for i in 0..self.accounts.len() as u32 {      // ← 遍历**我见过的全部账户**
    if let Some(k) = self.accounts.key_of(i) {
        total_mass += view.query(&k).clamp(0.0, 1.0);
    }
}
~~~

然后 `reading_of`（`lib.rs:990`）用它当分母：

~~~rust
let raw = stored.view.query(key).clamp(0.0, 1.0) / stored.total_mass;
~~~

**规格 §4.2 的原意**（`设计规格.md:154`）是「估计这份观点文件的**总质量**」——
那应该是**与接收方无关**的量（发布者写了多少内容就是多少）。

但当前实现把它变成了「**接收方的账户表长度**」。

### 1.2 实测（`examples/unbounded_mass_divergence.rs`）

发布者 P 的视图：给 **300 个**账户各 0.6 分（真实清单长度 m=300，稠密视图，40,960 字节）。
两个观察者收到**完全同一份字节**，只是自己的账户表长度不同：

| 观察者的账户表长度 | t1 读出的声望 | 相对最小节点 |
|---:|---:|---:|
| 301 | 0.00231788 | 1.00 |
| 1,297 | 0.00230263 | 0.99 |
| 10,297 | 0.00216718 | 0.93 |
| 100,297 | 0.00128913 | **0.56** |
| 1,000,297 | 0.00024114 | **0.10** |

**同一份字节，读数差 10 倍。** 这不是精度问题，是语义不一致。

### 1.3 膨胀倍数（`examples/unbounded_mass_exact.rs`，把机制摊开）

| 账户表长度 | `total_mass` | 相对真实总量（181.8） |
|---:|---:|---:|
| 300 | 181.2 | ×1.00 |
| 10,300 | 198.6 | ×1.09 |
| 100,300 | 330.6 | ×1.82 |
| **1,000,300** | **1,716.6** | **×9.44** |

噪声来自 Count Sketch 对**陌生 key** 的碰撞（`examples/unbounded_mass_mechanism.rs` 实测：
m=300 时陌生 key 非零率 0.30%、单点最高 0.6）。**每多一个「听说过」的账户，分母就多一分污染。**

### 1.4 后果

1. **跨节点声望不可比较** ⟹ S6 跨节点一致性失效（一直被当作核心性质）；
2. **新节点（账户表小）系统性看到更高声望** ⟹ 攻击者只要造一个干净节点就能放大读数；
3. **快照重放不一致**：`mass_covers` 记的是当时的账户表长度，而它本身语义就不精确（墙 2）。

### 1.5 修法（**需要作者决策**，因为会改变可观测行为）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** 发布方把总量写进字节 | `encode` 前算好 `declared_mass`，与 view 一起传输；接收方**只校验**（`Σ min(q,1)` 与声明值在容差内），不重新估计 | 视图格式 +4 字节、`SNAPSHOT_VERSION` 升级；发布方须能算准自己的总量（它是发布者，能算） |
| B 只对**我评过的人**求和 | 分母 = Σ_{owner ∈ 我的清单} view.query(key_of(owner)) | 语义变成「我在乎的那部分人」，但**跨节点仍不一致**（各人清单不同） |
| C 用固定常数 | 分母 = 1.0（视图本已归一化到 1） | 最省事，但失去「大视图摊薄」防护（S2 越线会恶化） |
| D 抽样估计 | 随机抽 N 个账户求和 × (总数/N) | 有估计误差，且**引入随机性**（破坏逐位一致） |

**A 是唯一同时保住「跨节点一致」与「影响力预算」的方案。** 但它是**协议变更**，
改变字节格式与发布方职责，**必须作者点头**。

## 2. 墙 2：`mass_covers` 的上界不精确（但它偏宽松，不造成漏算）

### 2.1 机制

`on_view` 记下 `mass_covers = self.accounts.len()`（`lib.rs:596`）——**接收方自己**的账户表长度。
`query`（`lib.rs:1065`）与闭式解（`lib.rs:889`）用它做判断：

~~~rust
let v = if target < stored.mass_covers { ... } else { 0.0 };
~~~

这里 `target` 与 `mass_covers` **都在接收方自己的坐标系**，所以没有「跨节点比较」的 bug。
真正的问题是：**这个上界把「发布者可能表态的账户」假设成「我的编号 0..我的长度」**——
而发布者的视图里可能包含我的编号更大的账户（它认识得更早/更多）。

### 2.2 实测（`examples/unbounded_index.rs`）

节点 A 认识 3 个账户（编号 0..2），节点 B 认识 7 个。B 发布观点，`mass_covers = 7`。
A 收到时把 grace 登记为编号 3，判断 `3 < 7` ⟹ 「在范围内」⟹ 去读桶值。
实测读出 0.7（**非零**）。

### 2.3 关键澄清（避免误判）

两个方向：
* 上界**偏大**（我的表比发布者的表态范围长）⟹ 多算 ⟹ **只是多给噪声，不造成漏算**；
* 上界**偏小**（发布者表态了我编号更大的账户）⟹ 少算 ⟹ 该账户的读数被当作 0。

**实测方向是偏大的那个**（A 的表短于 B 的表态范围），所以是「多算」。
这在反女巫上**不会变差**（多给约束），只是精度损失。

**但它与墙 1 是同一件事的两面**：`mass_covers` 越大，越多个「我后认识的账户」
被认为是「发布者表过态」，而它们的读数其实是碰撞噪声 —— 这正是 `total_mass` 被污染的来源。

**修法**：墙 1 修好后，`mass_covers` 可以整段删除（若总量由发布方声明，就不需要「表态范围」这个概念）。

## 3. 墙 3：`on_view` 的代价是 O(账户表长度)

### 3.1 实测（`examples/unbounded_onview_cost.rs`）

| 账户表长度 | 单次 `on_view` |
|---:|---:|
| 100 | 0.168 ms |
| 1,000 | 0.281 ms |
| 10,000 | 1.512 ms |
| 100,000 | **13.997 ms** |
| 500,000 | **70.096 ms** |

**严格线性。** 这不是优化问题，是算法复杂度：`total_mass` 的定义就是「对全部已知账户求和」。

### 3.2 这是一个可被武器化的放大器

攻击者只需让我 intern 大量**不同 key**（每个 key 只占 32 字节，写在它发给我的一条观点里，
而一条观点有 40 KB 容量），我的账户表就涨，之后**每一条** `on_view` 都变慢。

### 3.3 修法与墙 1 相同

`total_mass` 一旦改成「发布方声明 + 接收方校验」，这个 O(N) 循环**整段消失**，
`on_view` 变成 O(1)（对声明值做一次容差校验）。

**所以墙 1 的修法同时解决墙 3 —— 这是本轮最重要的结论。**

## 4. 墙 4：`AccountTable` 内存无界

### 4.1 实测（`examples/unbounded_scale.rs`）

intern 100 万个陌生账户，**峰值 RSS = 109 MB**（引擎基础约 34 MB ⟹ 账户表约 **75 B/账户**）。

| 账户表长度 | 账户表内存 |
|---:|---:|
| 1,000 | 0.1 MB |
| 100,000 | 7.5 MB |
| **1,000,000** | **75 MB** |
| 10,000,000 | 750 MB |
| 100,000,000 | 7.5 GB |

### 4.2 但这个量**不该**无限

关键观察：**`AccountTable` 是唯一的「全局面」**，其余所有量都是**局部**的：

| 量 | 上界 | 谁控制 |
|---|---|---|
| 正分清单长度 m | **我自己评过的人数** | **我** |
| 抽样位图 | 同上 | **我** |
| 视图缓存 `views` | `max_views`（应设为 ≈ m） | **我** |
| **`AccountTable`** | **我听说过的账户数** | **网络**（攻击者可推高） |
| `trust_distribution` 条目数 | = m | **我** |

**所以正确做法：`AccountTable` 必须也只装「我需要的」，而不是「我听说的全部」。**

### 4.3 修法（两个层次）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（防御性，可立即做）** 给 `AccountTable` 加 `max_accounts` 硬上限 | 满了就拒绝 `intern` | 需要淘汰策略，否则表被长期占满 |
| **B（推荐，依赖墙 1）** 账户表**只装**「我清单里的人」+「我明确要引用的人」，视图中无法解析的 key 一律忽略 | 需要 `on_view` 不再遍历全表（依赖墙 1 的修法）；「忽略陌生 key」是与现有语义一致的（`query` 对不在表里的 key 返回 0） | 无 —— **这本来就是设计意图** |

**B 与 `设计意图.md:24` 完全一致**：
> 「群体观点只覆盖自己评分为正的人，这是反女巫攻击的关键，
> 自己没评过分的账户只能通过评过分的人的链条进入自己的视野」

**当前实现为了算 `total_mass` 而遍历全表，恰恰违背了这条本意。**

## 5. 另外三条随规模恶化的已知限制（不是墙，但必须知道）

### 5.1 `k` 必须随清单长度线性增长 ⟹ 带宽墙

A10 硬约束 `k ≥ 2·m·T/H`（`审计/A10-抽样参数k与轮次节奏.md`）：

| 清单长度 m | 最小 k | 每轮带宽（40 KB/份） |
|---:|---:|---:|
| 100 | 34 | 1.3 MB |
| 300 | 100 | 3.9 MB |
| 1,000 | 334 | **13.0 MB** |
| 5,000 | 1,667 | **65.1 MB** |
| 50,000 | 16,667 | **651 MB** |

**这是设计本身的代价**（影响力预算 = 加权平均 ⟹ 必须刷新足够多来源），不是实现缺陷。
**唯一出路是「清单长度必须是常数上界」**（见 §6）。

### 5.2 桶数固定 ⟹ S1 随规模恶化

Count Sketch 碰撞噪声 ~ `sqrt(m / buckets)`。P-scale 实测（`审计/P-scale.md:198`）：
「n ≥ 2000 时桶数必须重新估值」；512 桶在 n=2000 下 **S1 = 0.0633** —— 那条路**走到头了**。

### 5.3 内存随桶数 × 账户数增长

2048 桶、n=2000 时 **183.4 MB/节点**；n=3000 时 **275.5 MB/节点**（3000 节点全网 826 GB）。
这是 **A12 定长稀疏表**要解决的问题（770~3074 B，比 Count Sketch 小 14~50 倍）。

## 6. 无限网络的正确形态（本轮最重要的推论）

> **全局账户数可以无限，但每个节点的清单长度必须是常数上界（建议 ≤ 300）。**

这不是妥协，这是**本设计已经隐含的要求**：

1. 影响力预算 = 加权平均 ⟹ 清单里每多一人，每人份额就少一份（`设计意图.md:6`「评分比值」）；
2. Count Sketch 噪声 ~ sqrt(m/buckets) ⟹ m 越大桶越不够（`审计/P-scale.md`）；
3. 抽样带宽 k ≥ 2·m·T/H ⟹ m 越大每轮拉的视图越多（`审计/A10`）；
4. `on_view` 代价 O(账户表) ⟹ 账户表必须只装局部（§4）。

**「无限网络」的正确实现是「无限多的节点，每个节点关注常数大小的邻域」，
而不是「每个节点认识全网络」。** 后者在任何 P2P 系统里都不成立
（Bitcoin 的节点也只知道邻居，不认识全网）。

这条推论也**回答了 §5.1 的带宽墙**：只要 m 是常数，k 是常数，带宽也是常数。

## 8. 本轮**没有改任何代码**

**只做了测量与归档**（6 个 example 探针 + 本报告），原因：

* P0 与 P1 都是**协议变更**（改变字节格式与可观测行为），必须作者决策；
* P2 是大工程（A12 原型已有，但替换视图表示要重跑全部 S 判据）；
* 按 `交接文档.md` §2 的纪律：**先测量，再定规格**；测量结果在这里，决策权在作者。

**如果认可 P0/P1 的方向，下一轮可以直接开工** —— 探针已经把「改前」的判据写好了；
改后应满足：

* `unbounded_mass_divergence` 的相对比值**恒为 1.00**（与账户表长度无关）；
* `unbounded_onview_cost` 的耗时**不随账户表长度变化**；
* 全部现有 S 判据（S1~S6）**逐位不变**（P0 只改归一化来源，不改权重结构）。
