# 负值模式（signed scores）实现说明

> 测于 2026-11-24。**结论**：负值是一个**独立开关**（`EngineConfig::signed_scores`，默认 `false`），
> 只影响**群体项**的值域，默认模式逐位零漂移。
> 开启后**不建议再用作反女巫** —— 但本库不提供跨层安全保证，谁能贡献由应用层的信任筛选决定。

## 1. 两种模式

| | `signed_scores = false`（**默认**） | `signed_scores = true` |
|---|---|---|
| 语义 | 分数 = **信任度** | 分数 = **带符号的观点** |
| 值域 | `[0, 1]` | `[-1, 1]` |
| 负分 | **静默夹成 0** | 生效 |
| 典型用途 | 反女巫（声望没有负数） | 资源分配（「我欠你」是正常表达） |

**两种模式互斥，不是叠加。** 它们是同一套引擎的两种语义解释，不能同时开启。

## 2. 为什么默认必须关

两条独立的理由：

**① 反女巫场景下负值是攻击面。** Count Sketch 里负分与正分落在**同一批桶里相加**，
攻击者若在信任白名单内，就能用自己的负分压低别人。实测（5 来源等权）：

```text
4 个诚实来源读 +1.0、1 个攻击者读 -1.0
默认模式群体项 = 0.56    （攻击者的负分被夹成 0，无害）
signed 模式群体项 = 0.42  （被压低 0.14 = (1-beta) × 份额 = 0.7 × 0.2）
```

⟹ 压低幅度 = **攻击者的份额**，线性可控但不是 0。

**② 零漂移要求。** 61 个 `EngineConfig` 字面量里大多数带 `..Default::default()`，
默认值若不是 `false`，这 61 处会静默变成 signed 模式，全部实验口径改变。

## 3. 实现：3 处 clamp + 1 处分母

| 位置 | 默认模式 | signed 模式 |
|---|---|---|
| `reading_of` 的输入/输出 clamp | `[0,1]` | `[-1,1]` |
| `on_view` 的 `total_mass` | `Σ min(q,1)` | `Σ abs(q).min(1)` |
| `aggregate` 出口 | `clamp01` | `clamp_signed` |
| `combine` 出口 | `clamp01` | `combine_signed` |

**内部聚合函数（weighted_mean / median / weighted_median / trimmed_mean）一行都没改** ——
它们本来就不假设值域（`weighted_mean` 是 `Σ(w·v)/Σw`，`median` 只是排序取中位），
唯一假设 `[0,1]` 的地方就是出口那个 clamp。

## 4. `total_mass` 为什么必须改成 `Σ|q|`

这是本功能里最容易被忽略、也最关键的一处。

**如果沿用 `Σ min(q,1)`：** 负值不进分母 ⟹ 一个视图写「1000 个账户各 -1.0」时
`total_mass = 0` ⟹ 落到 `.max(1e-6)` 下限 ⟹ 读数 = `-1/1e-6` ⟹ **单个视图就能把任何目标压到 -1**。

**改成 `Σ|q|` 后**（实测）：

```text
1000 个账户各 -1.0 ⟹ total_mass ≈ 1000 ⟹ 读数 ≈ -0.00092
```

⟹ 攻击者堆负值的成本是线性的，压不动。

代价：**没有增加复杂度**。仍然是同一趟 `for` 循环，只改一个表达式：

```rust
total_mass += if self.cfg.signed_scores {
    q.abs().min(1.0)
} else {
    q.clamp(0.0, 1.0)
};
```

⚠️ 注意：**P0 的 `O(N)` 缺陷在两种模式下都存在**（分母都要遍历接收方账户表）。
本功能没有加重它，也没有修复它 —— 那是 P2 的事，见 `P0-为何不能独立修复.md`。

## 5. 噪声底：按幅度判，不是按有符号值判

`reading_of` 的最后一道门：

```rust
let floor = (stored.noise.median * self.cfg.noise_multiplier).max(0.0);
if v.abs() < floor {   // ← 默认模式写 v < floor 也行（v ≥ 0 时两者等价）
    v = 0.0;
}
```

**为什么用 `v.abs()`：** signed 模式下如果写成 `v < floor`，一个 `-0.05` 的读数
会**恒小于**正的 floor ⟹ 被清零；但它可能是真实的反向信号，不该被当成噪声。
按幅度判才对。

**默认模式逐位等价：** `v` 已经 clamp 到 `[0,1]` ⟹ `v ≥ 0` ⟹ `v.abs() == v`。

### 一个实测踩过的坑（写测试的人要注意）

`noise_multiplier` 只能**放大**已有噪声，不能凭空造噪声。默认参数（2048×5）下
写几百条的视图 `noise.median` 恒为 **0** ⟹ `0 × 任何数 = 0` ⟹ 门根本不存在。
要测这条必须：

1. 用**小块**（如 64×5）让 median 非零（实测写 200 条时 median=1.0）；
2. 用**小乘数**（如 0.01）让 `floor` 小于 `|v|` —— 否则两种实现都输出 0，测试变成空转。

`tests/signed.rs` 里有两条配对测试钉住这个语义，且已验证有判别力
（把 `v.abs()` 改回 `v` 会有 4 条红）。

## 6. 默认模式零漂移的证据

三条独立证据：

**① 逐位基准探针。** 在未改动的 `dev`（174f3fe）上跑一份固定输入序列的探针，
记录 200 个账户的 `query(now=1000).to_bits()`（21 种不同值）。改完后重跑：

```text
200 个位模式 + 4 行统计（stats / rejected / account_count / positive_count）
⟹ **逐字节完全相同**
```

**② 加长探针覆盖快照与发布路径。** 除 `query` 外还覆盖：
`snapshot.encode` 的 FNV、`restore` 后 200 个 query、`restore` 后连跑 3 轮
`tick`/`on_view`、`export_view` 的桶字节 FNV、重复恢复 8 次的 export FNV。
改动前后 **identical=True**。

**③ 978 条现有测试原样全绿**（新增 13 条 signed 测试之前）。

## 7. 反女巫场景为什么**不能**用 signed 模式

作者的架构是两层：反女巫层负责筛选「谁能贡献」，资源分配层只读已信任节点的观点。
这个分层是对的，但**库不做跨层保证** —— 开启 signed 模式后：

* 任何在信任白名单内的节点都能把目标按**自己的份额**线性压低；
* 正负分在同一批 Count Sketch 桶里相加，碰撞会放大噪声；
* 库不提供「负值只在资源分配层生效」的机制（那是应用层的分支逻辑）。

⟹ 想两层共存，**推荐的落地方式**：反女巫层与资源分配层用**两个独立的 `Engine`**，
或者用同一个默认模式 `Engine` 做信任筛选，资源分配层在应用层自己读 `StoredView` 计算
（`StoredView` 字段全是 `pub`，`view` 是 `CompressedView`，应用层可以直接 `query`）。

## 9. 未做（刻意的范围限制）

作者原话：「不需要把这个地方做太复杂，只把负值的功能做好就行」。
因此以下**都不在**本功能范围内：

* 反女巫层与资源分配层的配合逻辑（应用层决定）；
* 负值的跨节点归一化（资源分配场景不需要）；
* 修复 P0 的 `O(N)` 分母（那是 P2 的事）；
* 负值下的 S1~S6 判据重测（signed 模式不用于反女巫）。
