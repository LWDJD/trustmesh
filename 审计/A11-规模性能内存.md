# A11 — 规模、性能、内存，以及「更轻量的平替」

> 工作树：`wt/a11_scale`（分支 `audit/a11-scale`）。库的默认行为未改，`crates/view` 未改；
> 稀疏观点是 `crates/exp/src/sparse_view.rs` 里的**独立对照实现**。
> 所有数字都是本机单进程 release 实测，命令见第 1 节；墙钟在共享机器上有抖动，所以同时给 CPU 时间。

## 0. 一句话结论

1. **确认为二次方**：`trust_distribution` / `export_view` 是 Θ(n·m)，固定 m 时对 n 的拟合阶数 1.00，
   固定 n 时对 m 的拟合阶数 1.00–1.15；n=1600/m=800 时一次分布 **1.43 s CPU、128 万次堆分配**。
2. **内存是更硬的墙**：每份观点 41,202 B；n=10000/m=5000 实测 **199.2 MiB 堆 / 204.0 MiB RSS**，
   构建耗时 18.5 s。按二次方外推，那时一次 `trust_distribution` ≈ **56 s**。
3. **定长稀疏表在支持度 ≤ cap 时逐位精确**：cap=512（6152 B）在 n=1600/m=800 下一次全量分布
   **0.092 ms**，比 sketch 快 **16,030 倍**，比「精确稠密」也快 597 倍；没被提到的账户精确为 0，
   total_mass 精确可算。代价是支持度 > cap 后截断，损失见第 5 节。
4. **2048×5 在稀疏观点上是过度设计**：deg=8 时 512×5（10 KB）误差已经是 0，256×5（5 KB）误差 0.3%；
   2048×5 只在**稠密**观点（deg≈512）下才值得，误差 1.7%（1024×5 为 7.5%）。
   另外 n≤1600 时，一份**稠密 f32 向量**只要 6.4 KB，比 40 KB 的 sketch 小 6.4 倍且精确。
5. **顺带发现两个安全缺陷**：
   * **S2/S5（严重）**：`on_view` 的 total_mass 估计对每账户做了 `clamp(0,1)`，发布方把整份观点
     放大 k 倍即可让质量估计饱和，而逐条查询值继续线性增长 → 配额被放大。实测 d=512 的攻击者
     用 1/200 的预算捕获 **63.5%** 的总信任（预算的 181 倍）；稀疏表的精确总质量对此免疫（放大 1e6 倍后分布不变）。
   * **S4（中）**：稠密 sketch 观点的碰撞噪声会给「从未被提到」的账户凭空发声望：
     400 个空账户里 5 个 >0，最大 1.451e-3，是平均被提及账户（2.488e-3）的 **58%**。

## 1. 环境与复现

* 机器：Windows x86_64，rustc 1.96.0，`--release`，单进程单线程。
* 每个 crate 是独立 workspace，命令都在 `crates/exp` 下执行；先设临时目录：

```powershell
$env:TMP="$PWD\.tmp"; $env:TEMP="$env:TMP"
cargo run --release --bin a11_scale -- timing
cargo run --release --bin a11_scale -- scaling
cargo run --release --bin a11_scale -- memory
cargo run --release --bin a11_scale -- sparse
cargo run --release --bin a11_scale -- degree
cargo run --release --bin a11_scale -- micro
cargo run --release --bin a11_scale -- attack
cargo run --release --bin a11_scale -- rounds
cargo run --release --bin a11_scale -- diag2
cargo test --release
```

* 计时口径：墙钟 `Instant` + 进程 CPU（`GetProcessTimes`，user+kernel，15.6 ms 量化）。
  共享机器上墙钟最多抖 2 倍（同一操作三次运行 1.17 s / 1.38 s / 1.72 s），因此**阶数一律用 CPU 时间**。
* 全局分配器带计数（每次 alloc 一个原子加），表中时间包含这点开销：n=1600/m=800 时 128 万次分配，
  估计贡献 10–20 ms（<2%）。
* 种子：timing/memory 用 `0xA110000+n`；sparse 用 `0x0A11_5EED + seed*7919 + n`（5 个 seed）；
  degree 用 `0x0A11_5EED + seed*7919 + deg`（3 个 seed）；rounds 用 `0x0A11_0000 + seed*7919`
  （n≤1024 用 3 个 seed，n=2048 用 1 个）；attack/micro 固定 `0x0A11_5EED`。
* 观点支持度 `deg`：第一阶段（评分类观点）每份观点 8 条；第二阶段的「声望观点」支持度会膨胀，
  见第 5 节。所有观点都已归一化到总和 1，除 attack 里故意放大。
* 第 2 节主表与阶数用 CPU 时间；第 4/5 节的耗时是**墙钟**均值±标准差（稀疏路径只有 0.02–0.1 ms，
  墙钟足够；sketch 路径的绝对值随负载波动 ±40%，只用于相对比较）。

## 2. 耗时曲线（sketch 2048×5，deg=8，`now=0`，无衰减）

### 2.1 主表（n 个账户，m=n/2 份观点）

| n | m | on_view 全部灌入 | query 全量 n 次 | trust_distribution | export_view | 一次 trust 的堆分配次数 |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 50 | 26.0 ms | 5.2 ms | 5.2 ms | 5.2 ms | 5,201 |
| 200 | 100 | 46.9 ms | 20.8 ms | 20.8 ms | 20.8 ms | 20,401 |
| 400 | 200 | 130.2 ms | 83.3 ms | 93.8 ms | 93.8 ms | 80,801 |
| 800 | 400 | 312.5 ms | 333.3 ms | 322.9 ms | 349.0 ms | 321,601 |
| 1600 | 800 | 864.6 ms | 1442.7 ms | **1427.1 ms** | 1416.7 ms | **1,284,801** |

（CPU 毫秒；n=100 一行的 CPU 被 15.6 ms 量化主导，只看量级。）

同一轮的**墙钟均值±标准差**（5 次）：
trust = 4.44±1.28 / 20.58±2.30 / 246.45±**104.10** / 555.92±147.14 / 1719.47±238.83 ms；
on_view = 27.16±3.37 / 60.82±4.42 / 131.86±6.42 / 416.81±43.59 / 1237.00±57.28 ms。
n=400 的 trust 墙钟被一次调度打断（CPU 只要 93.75 ms，墙钟 246 ms），这正是本报告用 CPU 定阶的原因。

分配次数精确等于 `n·m + n + 1`：每个 (目标, 来源) 一次 5 元素 `Vec`（`CompressedView::query` 里），
每个目标一次 `items` 的 `Vec::with_capacity(m)` 和一次 `valid_samples` 的收集。

### 2.2 阶数

| 指标 | 100→200 | 200→400 | 400→800 | 800→1600 | 总倍数（16×） | 拟合阶数 |
|---|---:|---:|---:|---:|---:|---:|
| trust_distribution | 4.00× | 4.50× | 3.44× | 4.42× | 274× | **2.02** |
| query 全量 | 4.00× | 4.00× | 4.00× | 4.33× | 277× | **2.03** |
| export_view | 4.00× | 4.50× | 3.72× | 4.06× | 272× | **2.01** |
| on_view | 1.80× | 2.78× | 2.40× | 2.77× | 33.2× | 1.26（见下） |

* `trust_distribution` / `export_view` 是严格的 Θ(n·m)：每个目标都要遍历全部 m 份观点。
* `query` 本身还多一层：`Engine::query` 每次都重算 `Σ ratings`（O(m)），`items` 再分配 O(m)，
  `aggregate` 又分配并排序 O(m log m)。所以单次 query 的斜率在 m 固定时略高于 1。
* `on_view` 的指数 1.26 不是算法如此，而是「每份观点有 316 µs 固定成本」把低 n 段抬平了：
  实测 `noise_floor(1000)` = 316.3 µs/份，与 n 无关；n 从 100 涨到 1600 时每份观点只从 520 µs 涨到 1080 µs。

### 2.3 单轴拆分（CPU，均值 2–3 次）

| 固定 | 变化 | trust CPU | 相邻斜率 |
|---|---|---:|---:|
| m=100 | n=200 / 400 / 800 / 1600 | 15.6 / 36.5 / 72.9 / 145.8 ms | 1.22 / 1.00 / 1.00 |
| n=800 | m=100 / 200 / 400 / 800 | 83.3 / 182.3 / 343.8 / 760.4 ms | 1.13 / 0.92 / 1.15 |

两轴都严格线性 ⇒ **Θ(n·m)** 成立，不是偶然的 4.2 倍。

### 2.4 成本拆解（micro，n=1600/m=800）

| 部件 | 实测 | 说明 |
|---|---:|---|
| `CompressedView::query`（热，同一份观点） | 352.9 ns | 5 行 × (FNV + splitmix)，含一次 5 元素 Vec 分配+排序 |
| 同上（冷，跨 800 份观点、32 MB） | 424.1 ns | 只有 1.20× 差距，主要是哈希计算而非缓存 |
| 其中「分配+排序」 | 68.6 ns | 占热查询的 19% |
| `noise_floor(1000)` | 316.3 µs | on_view 每份观点固定花掉 |
| on_view 的 O(n) 质量估计 | 0.484 ms | n=1600 次查询 |
| `aggregate(Mean)`，m=400 | 8.06 µs | 手写加权平均 0.33 µs，**慢 24×** |
| 同上，m=800 | 16.54 µs | 手写 0.64 µs，慢 26× |

把 `trust_distribution` 的 1427 ms 摊到 n·m=128 万个 (目标, 来源) 对上，是 **1.11 µs/对**；
单次 query 只要 0.35–0.42 µs，另外 ~0.7 µs/对来自 BTreeMap 评分查找、每目标重算评分总和、排序与分配。

### 2.5 外推

二次方外推 n=10000/m=5000：`1427 ms × (10000·5000)/(1600·800) = 55.8 s/次`。
同意口径的实测旁证：n=10000/m=5000 的 `on_view` 全部灌入实测 **18.53 s**（第 3 节），
与 on_view 的 m·(0.316 ms + n·0.3 µs) 模型（≈16.6 s）吻合。

|---|---:|

误差 = 归一化分布的相对 L1（`Σ|a−b| / Σ|b|`），与精确稠密参考解比较；括号内为标准差。

|---:|---|---:|---:|---:|---|

| 400 | sketch 2048×5 | 40,960 | 68.242±10.310 ms | 0 | 估计 |
| 400 | sparse cap=64 | 776 | 0.020±0.010 ms | 0 | 精确 |
| 400 | sparse cap=256 | 3,080 | 0.018±0.003 ms | 0 | 精确 |
| 400 | sparse cap=512 | 6,152 | 0.018±0.005 ms | 0 | 精确 |
| 800 | 精确稠密 | 3,200 | 0.647±0.135 ms | 0 | 精确 |
| 800 | sketch 2048×5 | 40,960 | 296.616±26.914 ms | 0 | 估计 |
| 800 | sparse cap=64/256/512 | 776/3,080/6,152 | 0.049/0.045/0.047 ms | 0 | 精确 |
| 1600 | 精确稠密 | 6,400 | 2.470±0.263 ms | 0 | 精确 |
| 1600 | sketch 2048×5 | 40,960 | **1474.810±162.835 ms** | 0 | 估计 |
| 1600 | sparse cap=64/256/512 | 776/3,080/6,152 | **0.092/0.090/0.092 ms** | 0 | 精确 |

* **deg=8 时 sketch 的精度并不差（误差 0）——它的问题是成本**：n=1600 时比稀疏表慢 **16,030×**，
  甚至比「不压缩的稠密参考」慢 **597×**。压缩没有换来速度，反而把「按目标查询」变成了 n·m 次随机访问。
* 接收端总质量：sparse 是 Σ 条目值，**精确**；sketch 的估计在 deg=8 时误差 5.5e-10（只剩浮点舍入），
  但在稠密观点下会变差：deg=512 时相对误差均值 **1.88e-3 ± 5.08e-3**，34.8% 的观点被低估。
* 稠密参考的 6.4 KB 也说明：**n≤10240 时，一份 f32 稠密向量不比 40 KB sketch 大**。

* 支持度按「每轮 ×r 左右」增长，直到饱和到 n：r=4 时 19.7 → 76.8 → 234.4 → 433.4；
  r=8、n=2048 时 70.9 → 501.9 → 1758.3 → 1652.3。
* **cap=512 只在支持度 ≤512 时无损**。n=2048/r=8 时第 3 轮支持度 1758、保留质量 77.8%，
  4 轮后 L1 已达 48.3%；n=1024/r=8 第 4 轮 L1 27.8%。
* 传播本身很便宜：capped 管线 11–270 ms/轮（其中大部分是每节点对自己 n 维向量排序），

* 对 n=10000 的含义：若每账户评 8 人，支持度第 2 轮就接近 3000–10000，
  cap=512 会丢掉 20%–50% 的质量；要无损就得 cap≈n（120 KB/份 @12 B/条），比 sketch 还大。

**所以「定长稀疏表」不是稠密声望观点的平替**：它适合**评分类/一跳观点**（支持度 ≤ cap），
不适合多跳后的声望向量。这是本报告最重要的边界结论。

## 6. 总质量与配额放大（S2/S5，严重）

### 6.1 机制

`Engine::on_view` 这样估计一份观点的总质量：

```rust
for i in 0..self.accounts.len() {
    total_mass += view.query(&key_i).clamp(0.0, 1.0);   // 对每个账户先夹到 [0,1]
}
```

`Engine::query` 再用 `v = view.query(u) / total_mass`，最后 `v.clamp(0,1)`。
发布方把整份观点的每个值乘 k：

* 分子线性增长：`query(k·x) = k·query(x)`；
* 分母被 `clamp(0,1)` 截住：`total_mass ≈ Σ min(k·q_u, 1)`，k 大到一定程度就不再增长；
* 于是 `v` 线性增长，直到被最后的 `clamp(0,1)` 顶到 1。

若一份观点有 d 条、每条 1/d，则 k ≥ d² 时所有 d 条都变成 v=1：该来源用 d 条目标，
把「总和 1」的配额放大成「总和 d」。注意这不是 sketch 碰撞问题，是**质量估计的 clamp** 问题，
与 `noise_floor` 无关（实测噪声底中位数为 0）。

### 6.2 实测（m=200 个来源，观察者给每人 1.0；A 区 = 攻击者独占的 d 个目标）

名义预算：群体项里 1/200 = 0.5%，折合总信任 0.7/200 = **0.35%**。

| d | k | A 区总信任 sumA | 放大倍数（相对 k=1） | 占总信任 | 相对 0.35% 预算 |
|---:|---:|---:|---:|---:|---:|
| 8 | 1 | 0.003500 | 1.00 | 0.35% | 1.0× |
| 8 | 16 | 0.006976 | 1.99 | 0.70% | 2.0× |
| 8 | 64 | 0.027330 | **7.81** | 2.73% | **7.8×** |
| 8 | 10⁶ | 0.027330 | 7.81 | 2.73% | 7.8× |
| 64 | 1024 | 0.053207 | 15.20 | 5.32% | 15.2× |
| 64 | 10⁶ | 0.183531 | **52.44** | 18.35% | **52.4×** |
| 512 | 1 | 0.011376 | 1.00 | 1.14% | 3.3×（含诚实观点噪声） |
| 512 | 1024 | 0.014863 | 1.31 | 1.49% | 4.2× |
| 512 | 10⁶ | 0.635452 | **55.86** | **63.55%** | **181.6×** |

* d=512、k=10⁶ 时，攻击者用 1/200 的评分预算拿走了**63.5% 的总信任**，诚实来源的 B 区从 0.683 掉到 0.253。
* d=512 的 k=1 基线 1.14% 里只有 **0.34% 来自攻击者自己**（测量值：该观点的质量估计 1.0137、
  512 条查询和 0.998，折合 0.3446%），其余 0.80% 是 199 份稠密诚实观点对 A 区的碰撞噪声。
  按攻击者自身贡献算，k=10⁶ 的放大是 0.635/0.00345 ≈ **184×**；表里的 55.86× 是以（含噪声的）
  k=1 为分母的保守值。d=8/64 的基线里没有这个噪声（0.0035 正好等于名义值），放大倍数不含水分。
* 同一攻击换成「稀疏表 + 精确总质量」：**放大 1e6 倍后 amp_A = 1.000000**（d=8/64/512 全部），
  分布逐位不变（第 4 节测试 `full_distribution_is_scale_invariant` 也钉住了这一点）。

### 6.3 佐证：sketch 路径不是尺度不变的

micro 模式把同一网络中**所有**观点整体乘 factor：

| factor | max abs diff | L1 |
|---:|---:|---:|
| 0.1 | 4.66e-10 | 1.83e-8 |
| 10 | 2.998e-4 | 4.69e-2 |
| 1000 | 1.687e-3 | **2.486e-1** |

缩小 10 倍几乎逐位不变（说明数学上 total_mass 可约），放大就崩——正是 clamp 的上界在起作用。

**建议修复**（未改库，只写结论）：质量估计改成 `Σ max(query, 0)`（去掉上界 1.0），
或直接让发布方声明总质量并由接收方抽样校验。前者一行改动即可恢复尺度不变性；
后者要求发布方声明，但需要防谎报的校验机制。

## 7. 空账户噪声（S4）

n=800/m=400，deg=512（稠密观点），target pool 之外的空账户从未被任何观点提到：

| 空账户数 | 引擎输出 >0 的个数 | 最大声望 | 空账户均值 | 平均被提及账户 | 单份观点正噪声率 |
|---:|---:|---:|---:|---:|---:|
| 400 | 5（1.25%） | 1.451e-3 | 1.178e-5 | 2.488e-3 | 79/8000（0.99%） |
| 200 | 5（2.50%） | 8.358e-4 | 1.386e-5 | 1.662e-3 | 58/4000（1.45%） |
| 100 | 0 | 0 | 0 | 1.429e-3 | 0/2000 |
| 40 | 0 | 0 | 0 | 1.316e-3 | 0/800 |

* 稠密观点下，**约 1%–2.5% 的空账户会被碰撞噪声抬起**，最高可达平均被提及账户的 **58%**。
* 40/100 的小样本恰好全 0（概率上正常），所以小样本实验会漏掉这个现象——这也是要跑够样本量的原因。
* deg=8（评分类观点）时 0/40，噪声远小于噪声底；稀疏表则**按构造精确为 0**
  （只累加被列出的哈希，见测试 `unmentioned_accounts_stay_exactly_zero`）。
* 与 S4 的关系：空账户拿到的不是「与真实账户相当」的声望（58% 只是最坏个例，均值 0.5%），
  但「凭空出现正声望」这件事本身违反了 S4 的严格表述，且随观点变稠密而变严重。

## 8. 缺陷清单

| 编号 | 严重度 | 缺陷 | 最小复现 | 影响判据 |
|---|---|---|---|---|
| D1 | **严重** | `on_view` 的 total_mass 用 `clamp(0,1)` 逐账户求和；发布方整体放大观点即可让分母饱和、分子线性增长，配额被放大到 d 倍 | `a11_scale attack`，d=8,k=64 → amp 7.81；d=512,k=1e6 → 63.5% 总信任 | **S2、S5** |
| D2 | 中 | 稠密 sketch 观点对未提及账户泄漏声望（碰撞噪声） | `a11_scale diag2` → 5/400 空账户 >0，最大 1.451e-3 | S4 |
| D3 | **高** | `trust_distribution`/`export_view` Θ(n·m)：每个目标遍历全部观点 | `a11_scale timing` n=1600 → 1427 ms、n=10000 外推 55.8 s | S1–S5 的可验证性 |
| D4 | 中 | `on_view` 每份观点做 O(n) 质量扫描 + 1000 次噪声标定（316 µs + 0.48 ms） | 同上，on_view 864.6 ms @ n=1600 | 部署成本 |
| D5 | 中 | `CompressedView::query` 每次分配 5 元素 Vec 并排序；一次分布 128 万次分配 | `a11_scale timing` allocs_trust=1,284,801 | 部署成本 |
| D6 | 低 | `aggregate(Mean)` 仍收集+排序（O(m log m)），比手写均值慢 24–26× | `a11_scale micro` | 部署成本（总时长 2–5%） |
| D7 | **高** | 40,960 B/份 × m：n=10000/m=5000 实测 199.2 MiB 堆 / 204 MiB RSS | `a11_scale memory` | 部署成本 |
| D8 | 低 | `export_view` 内部先算一遍全量分布再压缩，成本≈`trust_distribution` + n 次写入 | `a11_scale timing` export≈trust | 部署成本 |
| D9 | 中（设计取舍） | 定长稀疏表在支持度 > cap 时截断：n=2048/r=8 第 3 轮丢 22% 质量，4 轮后 L1 48% | `a11_scale rounds` | S1–S5 的精度基础 |
| D10 | 低（口径） | total_mass 在 Mean 模式下数学上可约（factor=0.1 误差 1.8e-8），O(n) 估计对精度无贡献，只在 D1 里帮倒忙 | `a11_scale micro` | S2 |

> 说明：D3–D8 不改变任何判据的结论，但决定了这些判据能不能在 n≥10⁴ 的真实规模上被验证；
> D1 是唯一直接推翻既有安全结论的缺陷。

## 9. 最小可用配置建议

### 9.1 2048×5 是不是过度设计？

**分场景，答案相反：**

* **评分类观点（支持度 ≈ 本地点评数，实测 8）**：是，过度 8–40 倍。
  512×5（10 KB）误差 0，256×5（5 KB）误差 0.3%；稀疏 cap=64（776 B）误差 0 且快 4 个数量级。
* **多跳后的声望观点（支持度 ≈ n/2）**：不是。1024×5（20 KB）误差 7.5%，512×5 已 20%；
  要 <2% 只能 2048×5。但此时 40 KB×m 的内存（n=10000/m=5000 → 200 MB）不可接受。
* **n≤10240 时还有第三个选项**：直接存 f32 稠密向量（4n B），n=1600 只要 6.4 KB、精确、
  一次分布在 2.5 ms（比 sketch 快 597×）。「定长与账户数无关」的收益要到 n>10240 才真正兑现。

### 9.2 建议配置

| 场景 | 格式 | 字节/份 | 一次全量分布（n=1600/m=800） | 预期误差 |
|---|---|---:|---:|---|
| 只发布本地点评（支持度 ≤64） | sparse cap=64，8 B/条 | **520 B** | **0.09 ms** | 0 |
| 点评较多（支持度 ≤256） | sparse cap=256，8 B/条 | 2,056 B | 0.09 ms | 0（≤256 时） |
| 一跳声望、可接受 512 截断 | sparse cap=512，12 B/条 | 6,152 B | 0.09 ms | 0（支持度≤512），否则见 5.3 |
| 稠密声望、精度优先 | sketch 2048×5 | 40,960 B | 1,427 ms | 1.7%（deg=512） |
| 稠密声望、可接受 7.5% | sketch 1024×5 | 20,480 B | ~1,300 ms | 7.5% |
| 稠密声望、只要 20% | sketch 512×5 | 10,240 B | ~1,250 ms | 20% |

推荐落地顺序：

1. **先修 D1**（total_mass 去掉上界 clamp）。这是一行改动、直接关掉 181× 的配额放大；
   稀疏表的精确总质量天然免疫，可作为修复后的对照基线。
2. **评分类观点改用定长稀疏表**（cap=64/256，8 B/条，520–2056 B）。这一步同时解决 D3/D4/D7：
   一次分布从 1.4 s 降到 0.1 ms，内存从 200 MB 降到 3.7–14.7 MB，且没有碰撞噪声（D2 也消失）。
3. **声望观点保留 sketch，但按实际需要选尺寸**：若接受 7.5%，2048×5 → 1024×5，内存减半；
   若必须 <2%，保留 2048×5，但不要常驻全部 m 份（可按需解码/淘汰）。
4. **热路径三处小改**（D5/D6/D4）：query 去掉 Vec 分配（-19%）、aggregate(Mean) 跳过排序（-2–5%）、
   on_view 的 1000 次噪声标定改成可配置或一次性标定（-316 µs/份）。
5. **不要**把 sketch 换成稀疏表去承载多跳声望：cap=512 在 n=2048 第 3 轮就丢 22% 质量，
   n=10000 时更差；除非接受「只保留 top-cap、其余归零」的语义。

## 10. 局限与未做

* 共享机器，墙钟抖动可达 2×；阶数与主表用 CPU 时间，单次绝对值仍受内存带宽竞争影响。
  同一条 `trust` 在三次运行中为 1.17 / 1.38 / 1.72 s（n=1600/m=800），报告取最后一次完整运行的 CPU 值。
* 多轮传播是**独立仿真**（每账户评 r 人、观点=上一轮声望、β=0.3、无衰减），不是 `Engine` 本身；
  它只用来度量「观点支持度如何膨胀、cap 在哪里开始丢信息」，不复现 Engine 的噪声底/clamp 行为。
* n=2048 的多轮实验只跑了 1 个 seed（sd 记为 0）；n=512/1024 为 3 个 seed。
* 没有实测 n=10000 的 `trust_distribution`（按二次方外推 55.8 s/次），只实测了同规模的构建与内存。
* 攻击实验固定 m=200 个来源、观察者每人 1.0；更大 m 只会让「占总信任比例」的绝对值变小，
  放大倍数（相对预算）不变。
* 未测 f32 稠密向量作为线上格式的编码/解码成本（只在 bin 内做内存与累加计时）。
