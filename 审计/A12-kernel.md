# A12 · 最小反女巫内核（原型）与现行实现的正面对照

**判据**：S1~S6 + 体积 / 耗时 / 代码量。**同一张社会图**（`tm_sim::World`）、**同一批 seed**（1..=20）、
**同一批观察者**。原型在 `crates/mincore/`，现行实现在 `crates/{store,view,agg,engine}`。
本报告里的每一个数字都来自本目录下的可复现实验，没有估算值；跑不出来的地方明确写「没跑」。

## 1. 原型是什么

### 1.1 四个部件

| 文件 | 生产代码行 | 做什么 |
|---|---|---|
| `src/fixed.rs` | 22 | u16 定点：夹到 `[0,1]` + 四舍五入，NaN/∞/负数在入口消化 |
| `src/list.rs` | 110 | 正分清单 `(账户, 正分, 上次成功取到观点的时间, 连败计数)` |
| `src/round.rs` | 129 | 轮次位图抽样：不放回 / 抽完重置 / **不退避** / 整轮全取 |
| `src/view.rs` | 196 | 定长稀疏表：`cap × 6` 字节 + 2 字节条数，规范形式编码 |
| `src/node.rs` | 275 | 权重、群体项、β 合成、全局归一化、发布 |
| `src/lib.rs` | 12 | 模块声明与再导出 |
| **合计** | **744** | 只依赖 std |

### 1.2 与现行的五点差别

1. **观点不再压缩成草图**，而是一张定长稀疏表（`u32 账户号 + u16 定点分数`，每槽 6 字节）。
   `Σ 分数` 是**精确整数和**，接收端不再「遍历全部已知账户猜总质量」。
2. **归一化顺序反过来**：先夹到合法区间（u16 定点天然合法），再除以**声明集合自己的**总质量。
   于是 `Σv ≡ 1`、单条 `v ≤ 1` 自动成立，没有「每一条都饱和到 1.0」的路径。
3. **不退避**：连败计数只记账，抽样器不看它（用例 `t07b` 钉死：改不改连败，抽样序列逐位相同）。
4. **格式即防御**：u16 表达不了 NaN / ∞ / 负数 / 超量；槽位严格升序、0 分不占槽、填充区必须全零，
   畸形负载**拒绝**而不是尽力解析。
5. **没有账户表**：分布只定义在「有人提到过」的账户上，空账户不是「值很小」，而是**不存在**。

### 1.3 归一化的顺序（这一节是全部重点）

现行实现（`Engine::query`）：

```text
v = clamp( 草图读数 / 接收端估计的总质量 , 0, 1 )
总质量 = Σ_全部已知账户 clamp(草图读数, 0, 1)      // 估计值
```

mincore（`SparseView::normalized` + `Node::group_term`）：

```text
q ∈ [0, 65535]                // 入口已经夹过，之后不再夹
v = q / Σ_声明 q               // 精确整数和，不是估计
```

区别在**夹紧发生在除法之前还是之后**。夹在除法之后，只要一条读数大于「总质量」，
它就会撞上 1.0 的上限；K 条各自撞一次，预算就从 1 变成 K（下表 S2 实测）。

### 1.4 「声明了但本机不认识」的账户

**定义**：计入分母（花掉来源的预算），但**不产生任何声望**。

后果是保守的：想用「1000 个我不认识的女巫」占预算，代价是它对我认识的人的话语权等比缩小。
反过来（只按认识的部分归一化）会让「声明陌生人」变成免费操作——那正是 S5 第三行 engine 的行为。

## 2. 实验设置

* **图**：`SimConfig { n_initial: 400, steps: 120, join/leave/dormancy: 0, enable_rhythm: false,
  follow_min: 120, follow_max: 200, max_follows: 256, attack_ratio: 0.1 }`。
  静态人口、全员在线，每人约 105 条正分（**清单中位 101、p95 163、最大 202**）。
* **场景**：女巫 `AttackKind::Sybil { cluster: 2 }`（440 人：400 诚实 + 40 女巫）；
  渗透 `AttackKind::Infiltrator`（400 人 + 1 个被推广账户，第 40 步买通 40 个高声誉账户）。
* **seed**：1..=20，全部指标报 **均值 ± 样本标准差**（n = 20）。
* **观察者**：出度最大的 **3 个**诚实账户（出度降序、账户号升序，完全确定）。
* **传播深度 1**（**必须说清楚**）：每个来源发布的观点 = **它自己的正分归一化**
  （即「一个刚上线、还没收到任何观点的节点」会发布的东西）。两个系统拿到的是**同一批**观点。
  这样两边完全对称，比较的是**接收与聚合**，不是传播动力学。
* 两种实现用同一个 `账户号 -> 32 字节公钥` 映射（`key(i)`），比的不是编码。
* 现行实现一律用 `EngineConfig::default()`（β = 0.3、H = 72、2048×5 草图、Mean 聚合、两级衰减全关）。

复现：

## 3. S1~S6 逐条

### S1 女巫集群在诚实观察者眼里的声望（女巫自评 1.0）

| 指标 | Engine | mincore |
|---|---|---|
| 平均 | 0.000007 ± 0.000004 | **0.000000 ± 0.000000** |
| 最大 | 0.000370 ± 0.000258 | **0.000000 ± 0.000000** |
| 非零占比 | 2.458% ± 0.186pp | **0.000%** |

两边都远低于诚实账户均值（2.5e-3），**结构性结论一致：女巫拿不到声望**。
差别只在泄漏：engine 有 2.46% 的女巫拿到了 1e-6~3.7e-4 的读数，来源是 Count Sketch 的桶碰撞；
mincore 精确 0，因为**没有任何人在表里提过它们**。

> 注意这是 sim 的设计性质：`draw_from_pool` 明确把女巫排除在社交发现之外
> （「没有背书就没有曝光」）。所以 S1 在深度 1 下本来就是 0 对 0，这一条**不是**本内核的功劳。

### S2 / S5 单来源接收端的 Σv

测法：`beta = 0` 的引擎 + 单个来源（我对它打 1.0，权重恰为 1），
`Σv = Σ_{声明账户} query(·)`。合规值见最后一列。

| 场景 | Engine | mincore | 合规 |
|---|---|---|---|
| 合规：10 条各 0.1 | 1.0000 | 1.0000 | 1.0 |
| 超量：2 条各 1000 | **2.0000** | **1.0000** | 1.0 |
| 超量：5 条各 1000 | **5.0000** | **1.0000** | 1.0 |
| 超量：10 条各 1000 | **10.0000** | **1.0000** | 1.0 |
| 超量：50 条各 1000 | **50.0000** | **1.0000** | 1.0 |
| 超量：200 条各 1000 | **199.0000** | **1.0000** | 1.0 |
| 伪造：10 已登记 + 10 未登记（各 1.0） | 1.0000 | **0.5000** | ≤ 1.0 |
| 伪造：同一账户声明 10 次（各 1.0） | 1.0000 | 1.0000 | ≤ 1.0 |
| 伪造：NaN | 0.0000 | 0.0000 | 0 |
| 伪造：1 条 1.0 + 200 条 −1.0 | 1.0000 | 1.0000 | 1.0 |

读法：

* **S2 是这一轮最硬的一条**。engine 的预算 = K，与声明的条数一一对应；
  mincore 恒为 1.0000。合规视图两边都是 1.0000——**没有为修这个 bug 付代价**。
* 「未登记账户」：engine 完全不为陌生人付预算（1.0），mincore 要付（0.5）。
  这是 §1.4 那个定义带来的**有意**行为：声明陌生人不再免费。
* 「同一账户声明 10 次」：两边都压到 1.0（engine 靠除法后的夹紧，mincore 靠「取最大值」），打平。
* **负数**：`CompressedView::add` 允许负分落桶（该 crate 文档明说「协议层不允许，本 crate 不截断」）。
  本次实验里**没有观测到污染**（5 个估计取中位数，把单行污染投出去了），所以这一条只算
  **结构性差别**：mincore 的 u16 格式根本表达不出负值，engine 需要协议层自觉。

### S3 被渗透者抬举的账户 ÷ 诚实账户均值

| 指标 | Engine | mincore |
|---|---|---|
| 倍数 | 0.894433 ± 0.123745 | 0.894631 ± 0.123746 |

**打平（+0.02%）**，而且**两边都小于 1**——在这个图与深度 1 的传播下，渗透攻击根本没有抬起来。
原因很直接：被买通的账户有 ~105 条正分，给被推广账户的那一条只占 1/105 的话语权，
而观察者要对 198 个来源做加权平均，最终贡献 ~1e-5 量级；诚实账户靠入度拿到的更多。

这一条**没有测出差异，我不把它算作 mincore 的胜利**。要让它有区分度，需要
「攻击者清单很短」（例如只保留 5 条正分 + 目标）这种集中攻击形态——那是另一轮实验，本轮没做。

### S4 1000 个只注册不评分的账户

宏观口径：把这 1000 个账户 intern 进 engine 的账户表 / 在 mincore 里作为已知账户号查询，
看它们在**最终分布**里的占比。

| 指标 | Engine | mincore |
|---|---|---|
| 出现率（值 > 0） | 0.5200% ± 0.0661pp | **0.0000%** |
| 拿走的总信任 | 6.762e-4 ± 4.18e-4 | **0** |
| 最大值 ÷ 真实均值 | 0.113295 ± 0.083128 | **0** |

微观口径（**单份视图**，1000 个陌生 key）：

| 视图条数 | 20 | 50 | 105 | 200 | 512 |
|---|---|---|---|---|---|
| 读数非零的比例 | 0.00% | 0.00% | 0.10% | 0.30% | 2.80% |

诊断（seed = 1，观察者 133，198 个来源）：

* 每份视图的**噪声中位数全部为 0**（198/198）——所以 `on_view` 里的噪声阈值没有起作用；
* 接收端估计的总质量在 **0.9948 ~ 1.0158** 之间（中位 1.0000）——在这个规模上它其实估得挺准；
* 198 份视图合计命中 49 次，但**只落在 8 个空账户上**（其中 5 个被命中 ≥5 次）。
  也就是说噪声不是均匀撒在 1000 个人头上，而是**集中**在极少数账户上；
* 最终只有 5 个空账户活下来（3 个的碰撞中位数为负，被 `clamp(0,1)` 清零）。

**必须说清楚的一点**：审计背景里「Count Sketch 在清单 ≥200 人时让空账户拿到真实量级分数」
——在我的宏观口径下**没有复现**。复现到的是它的**微观源头**：单份视图内部，一个陌生 key 的读数
就是 `~1/L`，与一个真实条目同量级（512 条时 2.8% 的陌生 key 会这样）。它被 198 源的加权平均
摊薄了约 200 倍，于是宏观上只剩 0.113 倍。这个差别不影响「mincore 精确 0」的结论，但
**审计里那个描述需要限定为「单份视图内」**。

### S6 确定性

同一组逻辑输入，分别按**正序 / 逆序 / 随机序**装配（intern、rate、on_view 三处都换序），
比较最终分布的 **f32 位模式**。

| 实现 | 逐位相同的 seed 数 | 最大相对差 |
|---|---|---|
| Engine | **0/20** | 1.017e-6 |
| mincore | **20/20** | 0 |

engine 的差异量级是 1e-6，来源是 f32 累加顺序（账户表按 intern 序、草图桶按写入序）。
这不是「算法不确定」，而是「**结果依赖插入顺序**」——同一份输入换个到达顺序，
第 6 位有效数字以后就不一样了。mincore 全走 f64 + BTreeMap 升序累加，逐位相同。

## 4. 三张表

### 4.1 体积

| 实现 | 每份视图字节 | 相对 | n = 1600 份合计 |
|---|---|---|---|
| Engine（2048×5 f32） | 40960 | 100% | 64000 KB |
| mincore cap = 128 | **770** | 1.9% | 1203 KB |
| mincore cap = 256 | **1538** | 3.8% | 2403 KB |
| mincore cap = 512 | **3074** | 7.5% | 4803 KB |

代价说明：稀疏表是**定长**的，与条目数无关。一份只有 10 条的观点也要 3074 B（其中 98% 是零填充），
而真实信息只有 62 B。engine 对 10 条观点同样要 40960 B，所以仍然是赢，但**赢的比例随清单变短而缩小**。

| 200 | on_view | 189.9 µs | 0.8 µs | 244× |
| 200 | 单账户 query | 99.4 µs | 4.2 µs | 24× |
| 200 | 一次全量分布 | 14.25 ms | 0.05 ms | 284× |
| 400 | on_view | 221.0 µs | 0.8 µs | 284× |
| 400 | 单账户 query | 202.5 µs | 8.6 µs | 24× |
| 400 | 一次全量分布 | 81.38 ms | 0.14 ms | 596× |
| 800 | on_view | 301.8 µs | 0.8 µs | 371× |
| 800 | 单账户 query | 477.5 µs | 21.2 µs | 22× |
| 800 | 一次全量分布 | 382.00 ms | 0.32 ms | 1208× |
| 1600 | on_view | 699.0 µs | 1.8 µs | 388× |
| 1600 | 单账户 query | 1609.6 µs | 143.0 µs | 11× |
| 1600 | 一次全量分布 | **2385.81 ms** | **1.02 ms** | **2329×** |

三条结构性的原因：

1. `on_view` 现行要 `O(n)` 扫全部已知账户估总质量，再加 `noise_floor(1000)`（1000 次草图查询）；
   mincore 只是解一张定长表 + 校验。
2. `trust_distribution` 现行是 `O(n · m)`（每个目标都要过一遍全部来源的草图）；
   mincore 是 `O(Σ cap)`（每份视图只扫一遍自己的槽位，与账户总数无关）。
3. 单账户 `query` 现行 `O(m)`、mincore `O(m · log cap)`——实测快 11~25×，因为常数小得多。

> 审计说「n = 800 时一次 181 ms」；我在 n = 800 量到 382 ms（本图 m = n = 800，每条目 10 条）。
> 同一量级、同一结论（O(n·m)），差异来自图密度不同。

### 5.2 清单超过 cap 怎么退化

**截断策略**：按 `(分数降序, 账户号升序)` 保留前 `cap` 条，再按账户号升序落表。
全序、无歧义，因此**与输入顺序无关**（用例 `t04` 用逆序输入验证过逐字节相同）。

**信息损失（实测，真实视图）**

| cap | 平均丢掉的质量 | 被截断的视图占比 |
|---|---|---|
| 128 | 1.4902% | 20.8% |
| 256 | 0 | 0% |
| 512 | 0 | 0% |

本图清单中位 101、p95 163、最大 202，所以 cap = 256 已经零损失。

**外推（合成 Zipf(s = 1.2) 分布，⚠ 不是实测，只说明形状）**

| 清单长度 | cap = 128 | cap = 256 | cap = 512 |
|---|---|---|---|
| 256 | 6.20% | 0% | 0% |
| 512 | 11.01% | 5.12% | 0% |
| 1024 | 14.82% | 9.19% | 4.28% |
| 2048 | 17.96% | 12.54% | 7.81% |

**退化的性质**（比数字更重要）：

* 丢掉的是**尾巴**，保留部分的**相对**权重不变（会重新归一化到 1），所以这个来源的**排序**基本不变；
* 但被丢掉的账户在这个来源眼里**直接变 0**（不是变小）——这是硬截断，不是平滑降权；
* 因此误差的方向是**系统性的**：清单越长的人，其观点对「榜单尾部」的覆盖越差。
  这不会造成女巫优势（女巫本来就在尾部），但会让**长尾账户**更难被看见。

**给建议**：cap = 512 覆盖到「清单 512 人」。超过 512 的正分清单应该**分片**（多份视图、按账户号前缀分），
而不是把 cap 加大——cap 加倍就是体积加倍，而定长表的全部好处来自 cap 小。

### 5.3 u16 定点够不够

**理论上界**（构造性，见用例 `t03`）：设声明集合有 K 条、真实分数 `s_i`（Σs = 1），
`q_i = round(65535·s_i)`，`v_i = q_i / Σq`，则

```text
|v_i − s_i| ≤ s_i · K / 131070 + 7.63e-6
```

* **绝对**误差上界 7.63e-6（= 0.5/65535）；
* 条目**消失**阈值 `s_i < 1/131070`：等价于「清单里超过 131070 个等权条目」才开始丢尾巴
  （用例 `t03b`：`quantize(1/131070) = 1`，`quantize(1/131071) = 0`）。

**实测**（相对精确 f64 参考，20 seed × 观察者视角的全部账户）

| cap | 平均相对误差 | p95 | 最大 | S3 倍数相对偏移 |
|---|---|---|---|---|
| 4096（只量化，不截断） | 5.509e-5 | 1.727e-4 | 9.511e-4 | 5.527e-5 |
| 512 | 5.509e-5 | 1.727e-4 | 9.511e-4 | 5.527e-5 |
| 256 | 同上 | 同上 | 同上 | 同上 |
| 128 | 同上 | 同上 | 同上 | 同上 |

（四个 cap 的误差完全一样，说明本图上误差**全部来自量化**，截断没有影响被测账户。）

**对 S3 的影响**：把「u16 结果」与「f64 精确参考」的 S3 倍数相比，相对偏移 **5.5e-5**——
也就是在第 5 位有效数字之后。S3 本身是 0.894 量级的比值，u16 带来的抖动是 ±0.00005。

**结论：够用**，而且余量很大。它撑不住的场景只有两个：
① 单来源清单 > 13 万人（等权条目开始归零）；
② 需要分辨 1e-5 以下的分数量级。反女巫不需要这两件事——
一个来源的预算是 1，一条分数的典型量级是 `1/清单长度`。

## 6. 局限与没做的事

1. **传播深度只有 1**。观点 = 发布者自己的正分归一化，不是「发布者的声望向量」。
   这让 S1/S3 结构性偏保守（攻击没有二跳放大），也因此 S3 没测出差异。
   做深度 2 需要为每个来源再跑一遍它的聚合并把结果当输入——本轮没做（按现行 `on_view` 的开销，
   198 源 × 198 源的深度 2 会超出 10 分钟预算）。
2. **只有一个图**（400 人 / 清单 ~105 条）。清单 > 512 的截断用的是合成 Zipf 外推，**不是实测**；
   报告里已用 ⚠ 标注。
3. **S3 没测出差异**，我没把它写成胜利。要让 S3 有区分度，需要「攻击者清单很短」的集中攻击形态。
4. **S4 的结论与审计背景有出入**：宏观口径下空账户只拿到 0.113 倍真实均值，不是「真实量级」；
   微观（单份视图）才复现到那个量级。已在 §3 S4 里写清楚。
5. **没有做网络层的实验**：抽样退避的「+14pp 轮首曝光」这一条，本轮只证明了「mincore 的抽样与连败无关」
   （用例 `t07b`），**没有**在同一张图上重测退避带来的偏置（那需要按轮次回放，超出本轮范围）。
