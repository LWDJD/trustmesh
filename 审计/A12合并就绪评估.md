`dev` 的 `verify-all.ps1` 第 4 步是 `cargo fmt --check`，**合进来会直接红**。

### 3.3 `cargo clippy` 有 7 条 warning

全部是同一类：`!(x > 0.0)` 应写成 `x <= 0.0` 或用 `partial_cmp`。

~~~
src/fixed.rs:34     if !(score > 0.0)
src/list.rs:57      if !(score > 0.0)
src/node.rs:280     if !(share > 0.0)
src/node.rs:290     if !(w > 0.0)
src/node.rs:306     if !(wsum > 0.0)
src/node.rs:326     if !(wsum > 0.0)
src/node.rs:392     if !(mass > 0.0)
~~~

`dev` 的 `verify-all.ps1` 第 3 步是 `clippy -D warnings`，**合进来会直接红**。

**注意**：这 7 处不能机械改成 `x <= 0.0` —— `!(x > 0.0)` 对 NaN 返回 `true`，
而 `x <= 0.0` 对 NaN 返回 `false`。**改法要逐处判断 NaN 应该走哪个分支。**

### 3.4 **跨平台逐位一致没有验证**（这条最要命）

`dev` 的 `tools/wasm-smoke` 只对 `tm_engine` 做 wasm32 对拍。
`tm_mincore` **完全没有** wasm 验证。

而它的核心性质正是「逐位可复现」（S6 20/20）。**这个性质恰恰是换架构时最容易丢的。**

## 4. 建议：不 merge 分支，先在分支上补齐门槛

### 4.1 为什么不能直接 merge

| 问题 | 后果 |
|---|---|
| `cargo fmt --check` 红 | `verify-all.ps1` 失败 |
| `clippy -D warnings` 红 | 同上 |
| 生产代码零单测 | 后续改这个内核时没有任何单元级护栏 |
| wasm 对拍缺失 | 丢掉本仓最值钱的性质而不自知 |

### 4.2 建议的做法（分三步）

**第 1 步**：把 4 项门槛补在 `a12_kernel` 分支上，而不是在 `dev` 上补救。

| # | 做什么 | 工作量 |
|---|---|---|
| 1 | `cargo fmt` + **逐处判断** clippy 的 7 处 `!(x > 0.0)` | 小 |
| 2 | **给 6 个模块加单元测试**（重点：`fixed.rs` 量化边界、`view.rs` 编码边界、`node.rs` 归一化退化） | **中～大（主要工作量）** |
| 3 | 给 `tm_mincore` 加 **wasm32 对拍**（照 `tools/wasm-smoke` 的模式，36 个 f32 位模式） | 小～中 |
| 4 | 把 `a12_compare` 的 S1~S6 输出改成**带断言的测试**（不是 bin），让 CI 能守住 | 中 |

**第 2 步**：4 项绿了之后，把 `crates/mincore` 作为**第 7 个 crate** 加入 `dev` 的 CI 矩阵。

**第 3 步**：**再决定**要不要把 `tm_engine` 换成 `tm_mincore` 的架构。
这一步才是真正的架构决策，需要你拍板（见 `审计/有损压缩架构.md` §6）。

### 4.3 为什么值得投入（而不是放弃）

因为它**一次性解掉前三份评估里所有需要大改的问题**：

| 问题 | mincore 的解 |
|---|---|
| `无限规模.md` 墙 1（同一份字节读出不同声望） | `total_q` 是**精确整数和**，没有估计 |
| 墙 3（`on_view` O(N)，50 万账户 70 ms） | **O(1)** |
| 墙 4（`AccountTable` 75 B/账户无界） | **没有账户表** |
| 生产测试内存墙（183 MB/节点） | **770~3074 B**（小 14~50 倍） |
| S4 空账户（m=1000 时 30.4%） | **精确 0** |
| 桶数决定 S1（512 桶 0.0633） | **不存在** |

而且它的 S1~S6 数字**刚被我实跑复现**（§2），不是纸面承诺。

### 7.2 补门槛时发现并修掉的一个真缺陷

`SparseView::normalized_slots()` 与 `normalized()` 在 `total_q > 2^24` 时差 **1 ulp**：
前者先把 `total_q` 转 f32 再除（丢低位），后者走 f64 除法。构型 256 条满额 + 1 条 q=257
→ `total_q = 16_777_217`，`16777217 as f32 = 16777216`，结果 257 个槽位**全部**差 1 ulp。

Σv 仍在 1e-6 内（S2 不受影响），但「同一份视图、两条读数 API 位模式不同」
会直接破坏本库最值钱的「逐位可复现」性质。已统一到 f64 路径。
实测这个修复不影响 wasm 对拍（探针走 `normalized()`，本来就正确）。
