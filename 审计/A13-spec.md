## 1. 审计方法与范围

### 1.1 陈述怎么拆

按 `设计规格.md` 的节序，把可执行的规范性语句拆成 142 条；每条只判定一件事，避免「一节一条」掩盖局部偏差。经验性段落（§4.9.1 的 L4 表、§4.9.7 的验收数字）不进入合规率，单列在 §9.1。

四种状态：

| 状态 | 含义 |
|---|---|
| **符合** | 代码行为与规格文字一致；给出代码位置或测试名 |
| **未实现** | 规格写了，代码里没有（含只有接口没有调度、只有测量没有使用） |
| **不一致** | 代码做了，但与规格文字不符；给出规格原文、代码位置、差异、可测后果 |
| **无法判定** | 规格文字有歧义或自相矛盾，必须作者表态；不硬判 |

「不一致」额外标注**责任方**：代码／规格／仓库。责任在规格时，建议改规格而不是改代码。

### 1.2 代码路径

* `crates/store`：`AccountTable`、`PositiveList`、`RoundSampler`、`Rng`。
* `crates/view`：Count Sketch、`from_pairs/query/encode/decode`、`noise_floor`。
* `crates/agg`：`decay`、`aggregate`、`combine`。
* `crates/engine`：`tick/probe/on_view/on_view_failed/query/trust_distribution/export_view`，4.9 的 `coverage/live_count/avg_source_age/group_scale`。
* `crates/exp` 是集中式实验场，不是 runtime；只用于 §0.2 banlist 残留核查。

### 1.3 测试策略

* **绿测试 33 条**：钉住当前符合规格的行为（含 §4.3 的意图口径）。
* **`#[ignore]` 10 条**：记录缺陷，断言的是**正确期望**；默认 `cargo test` 不跑，`--ignored` 时全部失败。失败信息里带规格小节和实测值。
* 全部 crate（store/view/agg/engine/sim/exp）在本分支跑过，绿。
* 只新增测试文件，没有改任何既有测试或库代码。

## 3. 不一致与意图分岔（按反女巫影响排序）

### A13-01 一个来源可声称 >1 的分数，突破「总配额恒为 1」（责任：代码）

**规格原文**（§4.2，132-136）：

> **每个账户的传播配额恒为 1**：它打分的对象越多，每个对象分到的份额越少。
>
> 份额[v] = 评分[v] ÷ Σ_全部正分 评分       // 总配额恒为 1

**代码位置**：`crates/engine/src/lib.rs:824-826`（`query`）、`:355-361`（`on_view` 的 `total_mass`）。

```rust
// on_view：估计总质量时逐项夹紧到 1
total_mass += view.query(&k).clamp(0.0, 1.0);
let total_mass = total_mass.max(1e-6);

// query：先除，再夹紧
let mut v = stored.view.query(&target_key) / stored.total_mass;
v = v.clamp(0.0, 1.0);
```

**差异**：`total_mass` 在估计时把每个读数夹到 1，分子却没有先夹紧。发布方声称 2.0 时，`mass = 10`（10 个目标各被夹成 1），每个目标算得 `2/10 = 0.2`，群体项总量 = **2.0**，而不是 1.0。声称 500 时更极端：每个目标 0.7，总量 10.0。夹紧顺序应当是「先夹分子、再除」。

**可测后果**：一个来源给 10 个目标各写 2.0，每个目标的声望是 0.14（=0.7×0.2），群体项总量 2.0；按规格应为每个 0.07、总量 1.0。最终 `trust_distribution` 会把它重新归一化，所以**单看最终分布看不出来**；被破坏的是归一化前的声望（跨账户比较、与诚实账户的 3:7 混合、S3 的比较基准）。一个女巫来源可以给任意多个账户发 0.7 的声望。

**测试**：`spec_4_2_one_source_total_influence_must_not_exceed_one`（ignored；实测每个 0.14，断言 ≤0.07）。

**影响 S**：S1（女巫自吹拿高分）、S2（1/N 预算）、S5（单来源伪造观点抬配额）。

**建议（只改代码，不改规格）**：`v = query.clamp(0,1) / total_mass`；保持 `total_mass = Σ clamp(query,0,1)`。这样对固定已知账户集，`Σ v = 1` 严格成立。

### A13-07 `total_mass` 在接收时固化，结果依赖登记顺序（责任：代码）

**规格原文**（§8 不变量 1，494）：

> 同样输入必然得到同样输出（**不依赖随机、不依赖调用顺序**）

**代码位置**：`on_view:355-361`（把 `total_mass` 存进 `StoredView`）、`query:824`（只用存下来的值）。

**差异**：`total_mass` 是「收到观点那一刻，我对已知账户求和」的**快照**。之后 `intern` 新账户，快照不更新。于是两个引擎可以拥有**完全相同的最终语义状态**（3 个账户、同一评分、同一观点、同一 `last_check`），只因「先 on_view 再登记第二个目标」与「先登记第二个目标再 on_view」的区别，查询结果不同。

**可测后果**：观点是 `{t1:0.5, t2:0.5}`，两个引擎最终都有 `t1/t2`：

* 引擎 A：`on_view` 时只知道 `t1`，`mass=0.5` ⇒ `q(t1)=0.7`、`q(t2)=0.7`（群体项总量 **2.0**）。
* 引擎 B：`on_view` 时知道 `t1/t2`，`mass=1.0` ⇒ `q(t1)=0.35`、`q(t2)=0.35`（总量 1.0）。

这**同时**是 S6 违反和 S2/S5 预算突破：A 里一份**单位区间内**的观点也给出了 2.0 的总配额。应用层若懒加载账户（先收观点、后登记账户），就会稳定触发。

**测试**：`spec_8_1_query_must_not_depend_on_registration_order`（ignored；0.7 vs 0.35）。

**影响 S**：S2、S5、S6。

**建议**：在 `intern` 新账户时，对每个已缓存观点增量更新 `total_mass += clamp(view.query(new_key),0,1)`（O(#views) 次，可接受）；或存原始观点、在查询时按当前账户集重算（更贵）。同时采纳 A13-01 的「先夹分子」。

### A13-13 已评分但没取到观点的来源不进分母（责任：代码；与 A1 同源）

### A13-02 §4.3「只对观点里含 u 的来源求和」与设计意图冲突（责任：规格）

**规格原文**（§4.3，162）：

> 只对「观点里含 u」的来源求和；份额与衰减都已在 `w[v]` 里。

**代码位置**：`query:803-833`。每个有观点的来源都会 push 进 `items`，读数 0 也进；`aggregate(Mean)` 的分母包含它们。两个等权来源、只有 A 提到 u 时，代码给 **0.35**（`group=0.5`）。

**判定：代码在这一点上是对的，规格文字是错的。** 注意：代码只在「沉默来源进分母」这一点上正确；「已评分但无观点」的来源仍然漏掉，见 A13-13——两者方向相反，合起来才是完整的分母口径。三条依据：

1. 意图第 33 行「缺失和未打分无需区分」⇒ 沉默来源按 0 处理、进分母。
2. 意图第 24 行「群体观点只覆盖自己评分为正的人」⇒ 来源集合是正分清单，不是「提到 u 的人」。
3. 代数上，包含沉默来源恰好给出 S3 的下限。设我评了 N 个等权来源、u 的份额是 1/N、一半来源支持 u，基准账户 w 无人提及：

```text
包含沉默：group[u] = 0.5
  D[u] = β/N + (1−β)·0.5      D[w] = β/N
  比值 = 1 + (1−β)·0.5·N/β = 1 + 1.1667N
不包含：  group[u] = 1.0
  比值 = 1 + (1−β)·N/β     = 1 + 2.3333N
N=2, β=0.3：包含 3.33×，不包含 5.67×
```

**可测后果**：如果照规格字面去改代码，单份支持就能把 u 的群体项从 0.5 抬到 1.0，抬举收益比值从 3.33× 恶化到 5.67×——**规格这一句会让 S3 更糟**。

**测试**：`s4_3_silent_sources_count_as_zero_per_intent`（**绿**，断言意图口径 0.35）。

**建议（只改规格，不改代码）**：§4.3 改为：

> 分母 = 我评过的**全部来源**的权重和（含没有观点的，贡献 0；含没提到 u 的，贡献 0）；
> 分子 = 其中给出了非零读数的来源的加权和。

### A13-03/10 噪声底的量纲错配：空账户拿 3%，真实目标被清零（责任：代码）

**规格原文**（§4.5，203-212）：

> 取其中位数作为该观点的**噪声底**……
> 2. 判断某个分数是否「显著高于噪声」（**低于噪声底的分数应视为 0**）
> 3. 作为反女巫的下限：只有当真实账户的分数显著高于噪声底时，反女巫才成立

**代码位置**：`on_view:353` 计算原始量纲的 `noise`；`query:824` 先除以 `total_mass`；`query:828-831` 拿**原始** `noise.median` 和**归一化后的 v** 比。

**差异**：噪声底是在「观点原始数值」上测的（`view::noise_floor` 直接 `query` 草图），而比较对象 `v = query/total_mass` 已经归一化。两边量纲不同。正确阈值应是 `noise.median / total_mass`，或者先比原始 `query` 再除。

**可测后果（两个方向）**：

* **过度清零**（A13-03）：观点 10000 条 1.0，接收方认识其中 200 个账户。目标被明确打了 1.0，原始查询约 5.0，**高于**原始噪声底 1.0；但 `v=5/200=0.025 < 1.0` ⇒ 被清零。整份观点里 200 个真实目标全部归零。
* **过滤不足**（A13-10，S4）：观点 10000 条各 1/10000（总量 1），接收方只认识 20 个账户。一个**从未被写过**的空账户查询到纯噪声 1e-4；`mass≈0.0021` ⇒ `v≈5e-2`，噪声底 1e-4 完全没有拦住。空账户最终声望 **0.0304（3.0%）**——这是「真实量级」，直接违反 S4。

**测试**：`spec_4_5_noise_floor_must_use_the_same_units_as_the_value`（ignored；稠密观点下真实目标 0）、`spec_s4_empty_account_must_not_gain_real_magnitude_reputation`（ignored；空账户 0.0304）。

**影响 S**：S4（空账户拿真实量级）；A13-03 的过度清零还会让诚实目标消失（S1 的对照基准也没了）。

**建议**：`floor_norm = noise.median / total_mass`；或比较原始 `query` 与 `noise.median`。同时修 A13-04（median=0）和 A13-07（mass 必须与当前账户集一致）。

### A13-04 默认参数下噪声中位数恒为 0，§4.5 的门限空转（责任：代码＋规格设计）

**规格原文**（§4.5，203）：

> 取其中位数作为该观点的**噪声底**。

**代码位置**：`view::noise_floor:395-411`（median 取 5 个带符号估值的中位数）；`query:828`（`v < floor`）。

**差异**：`noise_floor` 查询 5 个桶后取**带符号**估值的中位数，再取绝对值。默认 2048×5 下，稀疏观点的 5 个估值里通常至少 3 个是 0，所以中位数精确为 0。实测：

| 观点条目数（总量归一） | median | p95 | max |
|---:|---:|---:|---:|
| 100 | 0 | 0 | 0 |
| 400 | 0 | 0 | 0.0025 |
| 1000 | 0 | 0.001 | 0.001 |
| 1500 | 0 | 0.000667 | 0.001333 |
| 2048 | 0 | 0.000488 | 0.000976 |
| 3000 | 0 | 0.000333 | 0.000667 |
| 10000 | 0.0001 | 0.0002 | 0.0004 |

**可测后果**：`floor = 0`，`v < 0` 永远不成立；§4.5 的「低于噪声底视为 0」在现实规模下**根本不执行**。更糟的是，等 median 终于非零（10000 条），A13-03 的量纲错配又占主导。

**测试**：`spec_4_5_median_noise_floor_must_be_nonzero_at_default_params`（ignored；median=0）。

**影响 S**：S4（没有可用的空账户下限）。

**建议（需作者表态）**：把「噪声底」的统计量从 median 换成在稀疏观点下也非零的量（p95 或 max，或 median 与 p95 的保守组合）；或规定「条目数低于某阈值时不启用门限」。这是 §9-8 的标定问题，不能在实现里偷偷换。

### A13-05 `avg_age` 用裸份额而非规格写的 `w`（责任：代码／规格文字）

**规格原文**（§4.9.2，349-351）：

> avg_age = Σ_{live} w[v]·age[v] ÷ Σ_{live} w[v]      只对 live 集合求

其中 `w[v] = 份额[v] × factor(t[v])`（§4.2）。

**代码位置**：`live_summary:746`：`share = rating / total`，**不乘 fs**；测试 `two_level_decay.rs:375-404` 明确钉住「未衰减份额」。

**差异**：两个等份额来源，一个 age=0、一个 age=72（fs=0.5）：

* 规格字面：`(0.5·0.5·72)/(0.5·0.5+0.5) = 24`。
* 代码：`(0.5·0 + 0.5·72)/1 = 36`。

于是 `s` 也不同：`0.5^(24/120)=0.870` vs `0.5^(36/120)=0.812`。

**可测后果**：群体级衰减比规格字面**更强**（s 更小），§4.9.7 的 L4/D 系列验收数字会整体偏移。对反女巫是保守方向（群体项更轻），但不是规格写的行为。

**测试**：`spec_4_9_2_avg_age_uses_decayed_weight_per_spec_text`（ignored；36 vs 24）。

**影响 S**：S2/S3 的调参与复现；不是直接漏洞。

**建议**：代码的理由是「用 fs 加权会让老来源的年龄被自己的衰减压低 → avg_age 偏小 → s 偏大 → 群体级衰减自我失效」。这个理由成立，建议**改规格**为「裸份额」并写明理由，而不是改代码。
