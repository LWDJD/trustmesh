# A3 — crates/view 压缩观点精度审计（40KB Count Sketch 是不是过度设计）

- 分支：`audit/a3-view`　工作树：`wt/a3_view`
- 审计对象：`crates/view`（Count Sketch，2048×5，40 KiB），以及它在 `tm_engine` 里被消费的那一段
- 支撑代码：`crates/view/src/bin/a3_audit.rs`、`crates/engine/src/bin/a3_s4_empty.rs`
- 原始输出：`审计/raw-view-all.txt`、`审计/raw-engine-s4.txt`
- 全部数字由固定种子生成，重跑逐位可复现；总计算量约 3 分钟单核

**一句话结论：40 KiB 不是过度设计，而是在它唯一想解决的问题（S4）上不够；而且同一份体积预算下，精确表在所有维度上都更好。**

---

## 0. 结论

1. **S4 在默认配置下已经失败，只是失败得不均匀。** 真实 `tm_engine` 里注册 1000 个空账户（没人评分、没人列入清单），当每个来源的清单有 1000 人时：**30.4% 的空账户进了 trust_distribution，合计拿走 2.14% 的信任，其中最好的一个空账户拿到真实账户均值的 1.33 倍**（10 个种子，N=2000，S=30）。清单 300 人时仍有 7.0% 出现、0.41% 份额；只有清单 ≤100 人时才压到 0.44%。
2. **失败原因不是「精度不够」，而是「0 与不存在不可区分」。** 空账户的分数分布是**离散的、大 mass 在 0**：n=1000 时 89.2% 的空账户精确查到 0，另外 10.8% 非零、5.4% 为正，最大的那个达到 1.65× 平均账户。任何阈值都只能在这两个峰之间切一刀，而这两个峰是重叠的（AUC 0.973 看着高，尾巴完全重合）。
3. **噪声底（设计规格 §4.5）作为门限完全失效。** 清单 ≤1000 条时 `noise.median` **恒等于 0**，门限 `v < 0` 一个空账户都挡不住（FPR = 100%）；到 10000 条时它变成 0.85×均值，把 **51% 的真实条目**也一起清零（TPR 0.49 / FPR 0.20）。规格里「低于噪声底视为没表态」这条在两端都不成立。
4. **缩小体积全部立刻失败，而且 d 必须是奇数。** 同样清单 100 人：2048×5 → 0.44% 出现；1024×4 → **25.3%**；512×3 → 41.4%；256×3 → 82.4%。其中 1024×4 的灾难**不是桶少**，而是 **d=4 是偶数中位**：排序取中间两个求平均，任何一行碰撞都直接注入 `x/2`，等于没有多数投票。同样 16 KiB 不可得，但 1024×5（20 KiB）在同一场景是 2.66%，相差 9.5 倍。
5. **小清单下精确表全面碾压。** n=500 时 `HashMap<[u8;32],f32>`：序列化 18 KB（比 40 KB 小 2.2 倍）、100% 精确、**查询快 10.7–12.0 倍**、构建快 6 倍。n=1000 时精确表 36 KB，**仍然比 40 KB 小**，误差为 0，而 sketch 此时 10.5% 的条目是错的。
6. **总质量不可验证，而且 clamp 之后系统性偏大。** 未截断的 Σq 基本守恒（2048×5 在 n=10000 时 1.000±0.016），但接收方实际用的是 `Σ clamp(q,0,1)`：2048×5 在 n=10000 时 **1.180**，512×3 是 1.876，256×3 是 2.400。同一份观点，接收方只认识 60% 的账户时每条目被放大 **1.66 倍**。
7. **定向注入很便宜。** 已知参数时，磨一个能命中受害者 3/5 行的 key：2048×5 单核 **19–24 分钟**，512×3 **36–48 ms**，256×3 **9–13 ms**。而这还是「必须由真实 key 导出」的受限场景——协议不校验观点是否由评分表导出，直接构造 40KB 的 f32 数组就能把任意受害者的读数设成任意值（见 D7）。
8. **S6 只在「同一插入顺序」下成立。** 同一集合打乱顺序重建，最多 37/10240 个桶差 1 ULP 量级（2.38e-7）；`encode→decode→encode` 逐位相同。

## 1. 方法与环境

| 项 | 值 |
| --- | --- |
| 平台 | Windows，Rust 1.96.0，`--release`（opt-level 3），单线程 |
| 视图参数 | 除特别说明外 `ViewParams::default()` = 2048×5，view seed 0 |
| 随机源 | 自写 xorshift64*，种子写在每节；**不是**库里的 `XorShift64`，避免与 `noise_floor` 采样重叠 |
| 重复口径 | 每节都写「重复 R 次 × 每次一个汇总量 → 均值 ± 样本标准差」 |
| 复刻校验 | 审计程序把 `src/hash.rs` 的定位函数逐位复刻，启动时与库的 `encode()` 比对；不一致直接 panic（每节开头打印一行 `[自检]`） |
| 计时 | 每格 5 轮取最小；整表再取 **4 次独立进程**的最小值（机器负载会把绝对值抬高 1.5–2 倍，见 §5.4） |

评分分布三选一：

- **原始分**：`0.1 + 0.9·U(0,1)`（与 `crates/view/README.md` 的实测口径一致）
- **归一化分**：同上再除总和（= `Engine::export_view` 的发布形态，Σ=1）
- **重尾分**：`0.05 + 0.95·U³` 再归一化（多数人被低分、少数满分，更贴近真实评分）

> 尺度不变性已实测：同一份评分表归一化前后，50 组 × 1000 条目的相对误差**最大差异 7.998e-7**。所以「相对误差」类指标与分布尺度无关；有量纲的指标（噪声底、门限）必须在 Σ=1 的形态下比较，否则会差 5500 倍——这一点我在第一版 E2 里踩过，已修正。

| 300 | 0.9957 ± 0.0290 | 0.1114 ± 0.2066 | 0.0030 ± 0.0018 | 0.0026 ± 0.0017 | 4.90e-4 ± 6.43e-4 | 0.9987 ± 0.0017 |

| 1000 | 0.9993 ± 0.0186 | **−0.9697 ± 0.2285** | 0.0505 ± 0.0074 | 0.0464 ± 0.0069 | 0.0088 ± 0.0029 | 0.9728 ± 0.0041 |
| 10000 | 0.9994 ± 0.0235 | **−4.447 ± 0.4494** | 0.4399 ± 0.0166 | 0.8358 ± 0.0146 | 0.2132 ± 0.0133 | 0.7063 ± 0.0087 |

两个附带发现：

- **真实账户也会被噪声打成负分**：n=1000 时最差的真实账户估计值是 −0.97×均值，n=10000 时 −4.45×均值。经 `clamp(0,1)` 后它们变成 0——**sketch 既给不存在的账户发分，也把存在的账户抹掉**。
- AUC 0.973（n=1000）看起来「可分」，但它衡量的是随机抽样；S4 关心的是尾巴：5.05% 的空账户分数超过真实账户里的最低分。用 1000 个女巫去抽，抽到「高于最低真实账户」的那一批是必然事件。

### 3.3 噪声底能不能把它们分开（与 Engine 默认 `noise_multiplier=1.0` 同口径）

门限 = `noise.median`；TPR = 真实条目通过率，FPR = 空账户通过率。

| n | noise.median/均值 | noise.p95/均值 | 门限 TPR | 门限 FPR | p99门限 TPR | p99门限 FPR |
| ---: | --- | --- | --- | --- | --- | --- |
| 100 | 0 ± 0 | 0 ± 0 | 1.000 | 1.000 | 1.000 | 1.000 |
| 300 | 0 ± 0 | 0 ± 0 | 1.000 | 1.000 | 0.9989 | 0.9208 |
| 500 | 0 ± 0 | 0 ± 0 | 1.000 | 1.000 | 0.7746 | 0.0100 |
| 1000 | 0 ± 0 | 0.5580 ± 0.0770 | **1.000** | **1.000** | 0.4143 | 0.0100 |
| 10000 | 0.8461 ± 0.0320 | 2.499 ± 0.0794 | **0.4876** | **0.2037** | 0.0435 | 0.0100 |

- n ≤ 1000：`noise.median = 0`（因为一半以上的随机 key 精确查到 0），门限失效，**FPR = 100%**。
- n = 10000：门限变成 0.85×均值，把 51% 的真实条目一起清零，同时仍放 20% 的空账户进来。
- 换 p99 当门限也不行：n=1000 时为了挡住 99% 的空账户，要牺牲 **59% 的真实条目**；n=300 时 p99 本身就是 0（99.4% 的空账户精确为 0），门限退化。

**结论：噪声底不可能同时满足「挡住空账户」和「保留真实账户」，因为它俩的分布重叠。这是结构性的，不是调参问题。**

### 5.4 计时口径与噪声

- 同一进程内，**库的 `query` 比精确 HashMap 慢 10.7–12.0 倍**（n=100/500/1000 三种规模，4 次运行一致）。
- 构建：库 0.119–0.138 µs/条 vs HashMap 0.020 µs/条 → **6–7 倍**。
- 绝对值随机器负载在 1.15–3.75 ms/万次 之间波动（整轮 `all` 跑时最慢，单独跑时最快）。报告采用 4 次独立运行的最小值；**比值稳定，绝对值只作量级参考**。
- `query` 每次分配一个 `Vec`（`lib.rs:264`）。用定长 5 元中位替掉后，同一草图快 **1.2–1.4 倍**（`compare` 的 E4b 段，逐位结果相同）。
- `noise_floor(1000)` ≈ 0.18 ms/次，`Engine::on_view` 每收一份观点都跑一次（占单份观点接收成本的 ~75%，因为 1000 次查询 ≫ 实际条目数）。

**怎么定、能不能验证**：

1. 观点里的值 = `评分 / Σ评分`，Σ 由发布端自己算，**负载里没有质量字段**（`encode` 只有桶，`lib.rs:335-341`）。接收端只能拿自己的账户表重算（`engine/src/lib.rs:352-366`）。
2. 未截断的 Σq 守恒得很好（±1.6% @ n=10000），**说明 sketch 的线性没问题**；坏在接收端用的是 `clamp(q,0,1)`：负噪声被砍成 0，Σ 就单边膨胀。2048×5 在 n=10000 时 +18%，512×3 +88%，256×3 +140%。
3. 这个偏差直接稀释每条真实观点：`v = q / mass`，mass 偏大 ⇒ 所有真实条目被同比例压低。**注册 1000 个空账户还能把 mass 再抬高 4%（1.180→1.229）**：女巫除了自己拿分，还能顺带稀释所有人。
4. **同一份观点，不同接收方算出不同数值**：接收方只认识 60% 的账户时 mass ≈ 0.60，每条可见条目被放大 1.66 倍。所以 S6（同样输入同样输出）只在「同一个接收方的同一份账户表」内成立，跨接收方不成立。
5. 反向也成立：512×3 在 n=10000 时 mass_C = 1.126 > 1（clamp 噪声已经超过真实总量），`v/s = 0.885` —— 可见条目被**压缩**。此时质量归一化已经不是恒等变换，而是一个依配置而变的随机缩放。

## 8. E6 定向注入成本（S5 旁证）

## 9. S6 确定性

命令：`cargo run --release --bin a3_audit -- s6`

| 检查 | 结果 |
| --- | --- |
| 同输入、同顺序构建两次 → 编码逐位相同 | ✅ |
| encode → decode → encode 逐位相同 | ✅ |
| 同一集合、打乱插入顺序（5 次） | 最多 **37/10240** 个桶不同，最大桶差 **2.384e-7**，最大查询差 2.384e-7 |

结论：S6 在「同一顺序」下成立。发布端目前没有规定顺序（`export_view` 按账户编号升序，恰好确定）；一旦有人用 `HashSet` 遍历顺序构建，就会出现 ULP 级差异。**建议把「按账户编号升序写入」写进格式约定**，或干脆在 `from_pairs` 里排序（代价：一次性 O(n log n)）。

## 10. 「多小还能保证 S4」——阈值结论

判据（本文采用，也是最宽松的）：**空账户出现率 ≤1% 且 空账户合计份额 ≤0.1% 且 空账户最大值 ≤ 真实均值**。

| 配置 | 体积 | 满足 S4 的最大清单长度 m | 依据（出现率/份额/max） |
| --- | ---: | ---: | --- |
| 4096×5 | 80 KiB | **200** | 0.50% / 0.034% / 0.31 |
| 2048×5 | 40 KiB | **100** | 0.44% / 0.059% / 0.35 |
| 1024×5 | 20 KiB | < 100（m=100 已 2.66%） | — |
| 1024×4 | 16 KiB | **无**（m=100 已 25.3%） | — |
| 512×5 | 10 KiB | **无**（m=100 已 15.6%） | — |
| 512×3 | 6 KiB | **无**（m=100 已 41.4%） | — |
| 256×3 | 3 KiB | **无**（m=100 已 82.4%） | — |
| 精确 HashMap | 36 B × m | **任意 m（只要有内存）** | 0% / 0% / 0 |

**经验规律：要满足 S4，需要 `k ≳ 20·m`。** 40 KiB（k=2048）对应 m ≤ 100；而正分清单 200–500 人是常态（`exp` 里的来源清单就在这个量级），此时：

- 40 KiB sketch：出现率 2.7%–17.2%，份额 0.2%–0.9%；
- 同等人数的精确表：**10.8 KB（m=300）/ 18 KB（m=500）**，误差 0，出现率 0。

也就是说，**在 S4 需要它的那个区间里，精确表比 sketch 更小**。精确表的体积上限由「清单长度」决定，而清单长度本身已经被影响力预算约束（打得越多每份越轻），并不是无限的——「体积与账户数无关」这个卖点在这个场景里换不到任何东西。

## 12. 建议：删 / 改 / 留

### 删

1. **删掉「噪声底用来把空账户读数判 0」这条用法**（`engine/src/lib.rs:827-830` 的 `v < noise.median` 分支，对应设计规格 §4.5 用途 2/3）。实测它在稀疏时恒为 0（FPR=100%），在密集时误杀一半真实条目（TPR=0.49）。留着它只会让规格写着一个不成立的性质。若要保留，只能降级为「判断这份观点是否整体可用」（用途 1），且必须写清它不区分空账户。
2. **删掉偶数 d 的配置**（1024×4 / 任何 d 为偶数的组合），或在 `ViewParams::is_valid` 里直接禁止 `hashers % 2 == 0`。理由：偶数中位的单次碰撞注入是 `x/2`，比 d=5 差 9.5 倍（D3），且这是「静默失效」——配置合法、文档合规、结果错。
3. **删掉「定长压缩是唯一形态」的假设**：为 n ≤ 1000 提供精确稀疏表路径（36 B/条）。它在所有指标上更好，而体积在 n ≤ 1100 时还更小。

### 改

4. **`CompressedView::query` 去掉每次分配**（`lib.rs:264`）：用 5 元定长中位，快 1.2–1.4 倍，逐位结果相同，零风险。
5. **把 S4 的适用条件写进设计规格**：`k ≥ 20·m`（m = 发布端正分清单长度），或直接规定「清单超过 100 人时不得只用 sketch」。现在的规格只写了「噪声底是动态的，不能写死」，没有写「它根本分不开」。
6. **负载加头部**：`buckets / hashers / seed / 版本 / 条目数上界`，并让 `decode` 拒绝参数不符。现在传错 seed 会静默返回噪声（D7）。
7. **总质量改为「发布端声明 + 接收端区间校验」**：接收端重算的 mass 与发布端声明的 mass 若相差超过阈值就拒绝该观点。现在两边各算各的（D5）。
8. **固定写入顺序**（按账户编号升序），或让 `from_pairs` 内部排序，消掉 f32 累加顺序带来的 ULP 差异（D9）。

### 留

9. **中位数聚合（d=5 奇数）**——这是唯一有效的抗碰撞结构，别动奇偶性。
10. **2048×5 / 40 KiB 作为「大清单兜底」**——它的体积与账户数无关，n=10000 时仍只有 40 KiB（精确表要 360 KB）。但要清楚它在这个区间的 S4 已经失败，只能用在不依赖 S4 的场景（例如只做粗排）。
11. **f32、逐桶线性 merge、encode/decode 的定长布局**——线性性实测成立（Σq 守恒 ±1.6%），merge 语义正确，没有发现问题。
12. **`noise_floor` 的采样实现**——它算得对（1000 个新 key 的中位/p95/max），问题在「用它当门限」，不在它本身。

## 14. 未做与局限

- **没有测 4096×5 以上的配置**（8192×5 = 160 KiB）：按 `k ≳ 20m` 规律它能把 S4 撑到 m≈400，但 160 KiB/份观点对带宽不可接受，没有实际意义。
- **没有测多级/分层 sketch**（例如先按前缀分桶再压缩）：属于「换算法」而不是「调参数」，超出本次审计范围。
- **计时是单线程、单机**：绝对值受负载影响 1.5–2 倍，报告只采信「同一进程内的比值」和「4 次运行的最小值」。
- **E7 只有一个网络形状**（N=2000、S=30、均匀评分）：来源更少或观察者只认识几十个账户时，空账户份额会更高（分母更小）；没有做敏感性扫描。
- **没有在真实网络流量下测**：所有观点都是本地构造的，未经过序列化/传输/丢包。
