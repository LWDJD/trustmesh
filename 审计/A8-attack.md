# A8 — 边界攻击面审计：伪造观点、投毒、时钟、输入校验

> 审计对象：`tm_engine` / `tm_view` / `tm_agg` / `tm_store`（本工作树，分支 `audit/a8-attack`）
> 方法：只用公开 API，不改库、不改 `EngineConfig` 默认值。
> 全部数字来自 `crates/exp/src/bin/a8_attack.rs` 的一次运行（wall 4.3 s），
> 端到端部分为 20 个 seed × 400 账户（mean ± sd）。
> 代码：`crates/engine/tests/a8_attack.rs`（10 条通过 + 2 条 `#[ignore]` 记录缺陷）。

## 0. 一句话结论

规格 §4.2 那条注「接收方要自己估计总质量，再按估计值归一化」——**实现了，但只实现了一半**：

- `on_view` 确实自己估计了 `total_mass`（对已知账户求和），发布方无法直接伪造它；
- 但 `query` 里是 **先除、后夹紧**：`v = query(key) / total_mass` 再 `clamp(0,1)`。
  分子没有先夹到 `[0,1]`，于是**声明值只要 ≥ 受影响的账户数 K，归一化就完全失效**：
  一个来源的预算从 1 变成 K。

这一条同时打穿 S2 / S3 / S4 / S5。修法是**一个表达式的顺序**（见缺陷 D1），
对合规视图逐位不变。这是本次审计唯一的「必须在库内修」的核心项。

## 1. 接收端归一化：代码核对

| 位置 | 事实 |
|---|---|
| `crates/engine/src/lib.rs:352-370` | `on_view` 里 `total_mass += view.query(&k).clamp(0.0, 1.0)`，遍历 `0..accounts.len()`，再 `.max(1e-6)` 存进 `StoredView.total_mass` |
| `crates/engine/src/lib.rs:824-826` | `let mut v = stored.view.query(&target_key) / stored.total_mass; v = v.clamp(0.0, 1.0);` ← **分子未夹紧** |
| `crates/engine/src/lib.rs:828-831` | 噪声底门限：`v < noise.median × noise_multiplier` 视为没表态 |
| `crates/engine/src/lib.rs:840` | 群体项 = `aggregate(&items, Mean)`，即 `Σ(w·v)/Σw` |
| `crates/exp/src/lib.rs:192-195` | 实验框架是 **先夹紧再除**（`v.clamp(0,1) / view_mass`）——**与库不一致** |

最后一行很重要：既往所有端到端实验（含 S2 的 16632 次注入、S3 的 2.29×）
走的是 exp 框架，而框架的接收端归一化**恰好是正确的那一版**。
所以**既往实验没有测到库里这个缺陷**，S2/S3 的既有结论都是在「正确的预算」下得到的。

## 2. 关键数字

### 2.1 声明值放大：一个来源能注入多少质量（单来源、β=0、N=400，`query` 精确等于 `v`）

| 视图变体 | 声明总量 | `total_mass` | `Σv`（库） | `Σv`（修法模拟） | `max v` |
|---|---:|---:|---:|---:|---:|
| 合规 Σ=1 摊在 18 个女巫 | 1 | 1.0000 | **1.0000** | 1.0000 | 0.0556 |
| 18 个女巫 × 1e3 | 1.8e4 | 18.0000 | **18.0000** | 1.0000 | 1.0000 |
| 18 个女巫 × N(=400) | 7.2e3 | 18.0000 | **18.0000** | 1.0000 | 1.0000 |
| 18 个女巫 × 1e6 | 1.8e7 | 18.0000 | **18.0000** | 1.0000 | 1.0000 |
| 400 个账户全部 × 1e6 | 4.0e8 | 397.0000 | **397.0000** | 1.0000 | 1.0000 |
| 全桶 MAX | 3.4e38 | 203.0000 | 203.0000 → 引擎实测 0（噪声底） | 1.0000 | 1.0000 |

阈值扫描（K = 18 个女巫，`total_mass` 恒为 18）：

| 声明值 c | 1 | 10 | 18 | 19 | 50 | 400 | 1e6 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 女巫 v | 0.0556 | 0.5556 | **1.0000** | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| Σv | 1.0 | 10.0 | 18.0 | 18.0 | 18.0 | 18.0 | 18.0 |

**解析式**：`v_i = clamp(c_i / T)`，`T = Σ_j min(c_j, 1) = K·min(c,1)`。
于是 `c ≥ K` 即 `v = 1.0`——**阈值只取决于「我声称抬举几个账户」，与接收方账户数 N 无关**。
合规发布方（`export_view` 归一化到 1）永远走不到这条路；恶意发布方一行代码就能走。

### 2.2 全桶 MAX / 噪声底

| 项 | 值 |
|---|---|
| 任意 key 的原始查询值 | 3.4028e38 |
| 噪声底（1000 随机 key） | median = **inf**，p95 = 3.4028e38，max = 3.4028e38 |
| 噪声底（999 随机 key） | median = 3.4028e38（偶数样本才溢出，见 D6） |
| 单来源 Σv，噪声底开（默认） | **0.0000** |
| 单来源 Σv，噪声底关（`noise_multiplier=0.0`） | **203.0000**，max v = 1.0 |
| 31 来源混合（1 MAX + 30 诚实） | 女巫均声望 **0.000e0** |

结论：**均匀灌满的投毒被噪声底自己抵消**（噪声底用同一份草图在随机 key 上实测，
全 MAX 图的 median 就是 MAX，于是所有 `v ≤ 1 < floor` 全被判成「没表态」）。
这条防线是真的、且很关键——但它只对**均匀**投毒有效。定向投毒（只填自己那 K 个 key）
的噪声底中位数实测为 **0.000e0**，完全不设防（§2.4）。

### 2.3 恶意标量

| `rate(A, x)` | 存下来的值 | A 的份额 | A 的声望（β=0.3） |
|---|---:|---:|---:|
| 1.0 | 1.0 | 0.500000 | 0.150000 |
| NaN | 条目被删除 | None | 0 |
| −1.0 | 条目被删除 | None | 0 |
| +Inf | **1.0e9** | 1.000000 | 0.300000 |
| −Inf | 条目被删除 | None | 0 |
| 0.0 | 条目被删除 | None | 0 |
| 1e30 / f32::MAX | 1.0e9 | 1.000000 | 0.300000 |

- 负分在默认配置下是**静默撤销**（等价 `allow_negative=false`），不报错、不残留
  （`crates/store/src/lib.rs:266-293`）。这是对的。
- `+Inf` 不是 NaN 污染，被截到 `MAX_SCORE = 1e9`。这是对的。

时间戳：

| 输入 | 结果 |
|---|---|
| `published_at = u64::MAX` vs `0` | `query` 逐位相同（1.000000 vs 1.000000） |
| `on_view(now = u64::MAX)` 后 `query(now=0)` | 1.000000，factor 被钉在 1.0 |
| `decay_factor(dt)` 全量程扫描 | 最大 **1.000000**（无 >1 分支） |

→ **伪造未来时间戳零收益**（`published_at` 只存不用）；Δt 为负被 `saturating_sub` 夹到 0，
factor 永远不会 >1。这一条设计是对的，必须保留。

### 2.4 端到端：400 账户 / 31 个来源 / 1 个攻击来源 / 18 个女巫 / 20 seeds

结构：观察者(0) 给 30 个诚实账户 + 攻击者(381) 各 1.0（份额 1/31）；
诚实来源各摊 1/30 给 30 个诚实账户（Σ=1）；女巫(382..399) 没有任何诚实来源认识。

| 攻击者视图 | 女巫均声望 | 诚实全体(380) | 被评分诚实(30) | 女巫/诚实全体 | 女巫/被评分 | 女巫占分布合计 | 榜首 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 合规 Σ=1 | 1.254e-3 ± 5.2e-11 | 2.547e-3 | 1.141e-2 | 0.49 | 0.11 | 0.0226 | 0/20 |
| 女巫 ×1e3 | 1.632e-2 ± 8.3e-10 | 1.840e-3 | 8.247e-3 | **8.87** | **1.98** | **0.2937** | **20/20** |
| 女巫 ×1e6 | 1.632e-2 ± 8.3e-10 | 1.840e-3 | 8.247e-3 | **8.87** | **1.98** | **0.2937** | **20/20** |
| 女巫 ×N | 1.632e-2 ± 8.3e-10 | 1.840e-3 | 8.247e-3 | **8.87** | **1.98** | **0.2937** | **20/20** |
| 全部 400 账户 ×1e6 | 2.271e-3 ± 5.1e-10 | 2.509e-3 | 3.412e-3 | 0.91 | 0.67 | 0.0409 | 0/20 |
| 抬自己 + 女巫 ×1e6 | 1.606e-2 ± 8.3e-10 | 1.811e-3 | 8.114e-3 | 8.87 | 1.98 | 0.2890 | 0/20（**攻击者自己榜首**） |
| 全桶 MAX | 0 ± 0 | 2.606e-3 | 1.168e-2 | 0.00 | 0.00 | 0.0000 | 0/20 |

- 18 个女巫 = 账户总数的 **4.5%**，却拿走 **29.37%** 的信任（均匀应为 4.5%），**超配 6.5 倍**。
- `×1e3 / ×1e6 / ×N` 三行数字**完全一致**：说明只要过阈值就饱和，量级大小无所谓 —— 这是 `clamp` 的签名。
- 「全部 400 账户 ×1e6」反而**没有优势**（0.91×）：因为诚实账户也被同样抬高，相对差被抹平。
  **有效的是定向放大**，而定向只需要知道受害者会登记哪些 key（公开身份），零成本。
- 标准差 5e-11 ~ 8e-10 极小，因为女巫的群体项是结构性的 `w_A/Σw`；20 个 seed 只改变图，
  不改变这个结构。这不是样本不足，而是机制确定。

### 2.5 「引入越多每个越弱」还成立吗（20 seeds 均值）

| 引入数 k | 合规视图 女巫均 | 放大视图(×1e6) 女巫均 | 放大/合规 |
|---:|---:|---:|---:|
| 1 | 2.258e-2 | 2.258e-2 | 1.00 |
| 5 | 4.516e-3 | 2.071e-2 | 4.59 |
| 18 | 1.254e-3 | 1.632e-2 | **13.01** |

合规列精确按 1/k 下降；放大列**几乎不随 k 下降**，比值 ≈ k。
规格 §4.2 那张「引入 50 个每个 0.01」的表，在放大视图下会变成「引入 50 个每个仍接近满额」。

### 2.6 重放 / 覆盖

| 场景 | 结果 |
|---|---|
| t=720 不重放（全体一起旧） | group = 0.250000 |
| t=720 每 72 重放一次同一份旧观点 | group = **0.997079**（×4.0） |
| 攻击者权重 | 2.441e-4 → **2.500e-1** |
| t=600 收到「不抬举」新观点 | query = 0.000000 |
| t=700 又收到 `published_at=0` 的旧观点 | query = **0.996461**（旧观点回滚新观点） |
| `on_view` 未评分来源后 `stats()` | 命中=1，缓存视图=1，评分条目=0 |

重放不累加（`views` 是 BTreeMap，insert 覆盖）、结果确定，这两点是对的；
但**同一份旧字节可以无限刷新 `last_check`**。

### 2.7 时钟

`now` 依次取 0 / 1 / 72 / 720 / 1e6 / u64::MAX/2 / u64::MAX / 0（回拨）：

| now | query(target) | Σ分布 | 最小 | 最大 |
|---|---:|---:|---:|---:|
| 0 … u64::MAX（全部 8 个取值） | 0.700000 | 1.000000 | 0.300000 | 0.700000 |

回拨被 `saturating_sub` 夹到 0（factor = 1.0，更「新」）；前跳 factor → `DECAY_FLOOR` 但永不为 0；
从 u64::MAX 拨回来立刻恢复（`last_check` 没被改写）。**整表 Σ 恒为 1，无异常、无 panic、无 NaN。**

两来源（1.0 / 0.0）时钟前跳：t=0 → 0.350000；t=1e6（都旧）→ 0.350000（不变）；
t=1e6 只刷新其中一个 → 0.700000（2.0×）。时钟前跳不破坏「全体一起旧」的不变性，
但会放大「谁在线」的相对优势——这是设计使然，不是缺陷。

### 2.8 确定性

正序 vs 逆序 / 正序 vs 随机序：`trust_distribution` **逐位相同**（`f32::to_bits` 比较）。
S6 成立。

## 3. 输入校验的另外两个洞（可用性，不是 S 判据）

| 项 | 实测 |
|---|---|
| `on_view` 是否校验 `view.params()` | **否**。引擎配 2048×5，收下 1×5（20 B）视图；结果被噪声底挡成 0（拿不到放大收益） |
| 单视图体积上限 | `MAX_CELLS = 2^26` 单元 × 4 B = **256 MiB**，直接进 `views` 缓存，条数无上限 |
| N=4000 时一次 `on_view` 耗时 | 正常 2048×5（40960 B）= **0.9 ms**；恶意 16×4096（262144 B）= **572.1 ms**（**×609**） |

代价 = `(N + 1000 次噪声采样) × hashers`，而 `hashers` 由**对端**选（上限 4096）。
32 KiB 的负载能换几百毫秒 CPU。库内没有防线，属应用层限流/限长。

## 4. 缺陷清单

严重度：**S** = 反女巫不成立；**A** = 需要修但可被应用层兜住；**B** = 数值/健壮性。

| 编号 | 严重度 | 缺陷 | 最小复现 | 影响 S 判据 |
|---|---|---|---|---|
| **D1** | **S** | 接收端归一化**先除后夹紧**，声明值 ≥ K 即让 `Σv = K`（预算 1 → K） | `crates/engine/tests/a8_attack.rs::budget_must_be_one_even_for_oversized_claims`（`#[ignore]`，跑起来 Σv=8/8） | **S2、S3、S4、S5** |
| **D2** | **S** | `total_mass` 只是「`on_view` 时刻已知账户」的快照；只声明未登记账户时它 = 1e-6，这些账户**后来**被登记时 `v` 饱和到 1.0 | `crates/engine/tests/a8_attack.rs::claims_about_unknown_accounts_must_not_saturate_later`（`#[ignore]`，Σv=8、单个 v=1）；bin §1f（50 个未登记账户各 1.0 → 登记后 Σv=50，合规应 1.0） | **S2、S4、S5** |
| **D3** | A | `on_view` 不校验 `view.params()`，也不限体积/`hashers` | bin §4b：1×5 视图被接受；16×4096 @N=4000 → 572 ms/次（×609）；256 MiB/视图 | 可用性（间接毁全部） |
| **D4** | A | 重放同一份旧观点可无限刷新 `last_check`（伪造新鲜度）；`on_view` 也不比较 `published_at`，旧观点可回滚新观点 | bin §5：0.25 → 0.997（×4.0）；`replay_refreshes_last_check` | 衰减线（S1~S4 的时效前提） |
| **D5** | B | `on_view` 不校验非有限值：`total_mass` 为 NaN 时被 `max(1e-6)` 收成 1e-6。当前全 NaN 视图会被 `tm_agg::valid_samples` 整条剔除（**不污染全表**，实测分布长度 5、Σ=1、全有限），但「部分行 NaN + 其余有限」理论上可把别的 key 的 `v` 抬到 1.0 | bin §4（`decode` 拒绝 NaN/Inf；进程内可用 `merge(self,0,0)` 造出 0×inf=NaN） | S6（不确定）；主要是防御纵深 |
| **D6** | B | `tm_view::median_sorted` 偶样本 `(a+b)*0.5` 溢出成 inf；`noise_floor(1000)` 正是偶数样本 → 大数值视图的噪声底 = inf | bin §2：`noise_floor(999).median = 3.4028e38`，`noise_floor(1000).median = inf` | 数值健壮性（本次它反而多挡了一层） |
| **D7** | B | 未评分来源的 `on_view` 照样进 `views`，缓存无上限、无淘汰 | bin §5：`stats() = (命中 1, 缓存 1, 评分条目 0)` | 可用性 |

### D1 的最小修法（一行，推荐）

```rust
// crates/engine/src/lib.rs:824  现在是
let mut v = stored.view.query(&target_key) / stored.total_mass;
v = v.clamp(0.0, 1.0);

// 改成（分子先夹紧，与分母同一口径）
let mut v = stored.view.query(&target_key).clamp(0.0, 1.0) / stored.total_mass;
v = v.clamp(0.0, 1.0);
```

- 对合规视图（全部查询值 ≤ 1）**逐位不变**：`q ≤ 1` 且 `T = Σq ≥ q` ⇒ `q/T ≤ 1`，两种写法同值。
- 对超发视图只会变小（实测 `Σv` 从 18 → 1.0000）。
- 与 `crates/exp/src/lib.rs:192-195` 已有的写法一致，消除框架与库的不一致。
- 同时把 §4.2 的文字补一句：「估计值必须与分子同口径（先夹紧再归一化）」。

### D2 的最小修法（O(1)）

```rust
// StoredView 增加一个字段
pub mass_covers: u32,          // on_view 时的 accounts.len()

// on_view 里
StoredView { view, published_at, last_check: now, noise, total_mass,
             mass_covers: self.accounts.len() as u32 }

// query 里，在算 v 之前
if target >= stored.mass_covers { continue; }   // 这条声明没进过分母
```

`AccountIdx` 由 `intern` 单调递增分配，所以 `target >= mass_covers` 精确等价于
「该账户是在这份观点缓存之后才登记的」。代价 O(1)、不改变任何既有行为
（现有测试里所有 target 都在 `on_view` 之前登记）。

### D3 的最小修法（一行）

```rust
// on_view 开头
if view.params() != self.cfg.view_params { return; }   // 参数不一致 = 无法解释的字节
```

参数一致后体积自动被锁死在 40 KiB、`hashers` 锁死在 5，CPU 放大同时消失。
限流/限长仍应由应用层做（库不做 I/O，也不该决定带宽策略）。

### D4：不能只靠库修

`last_check` 是「我什么时候拿到」，不是「内容有多新」——这是拉取式模型的结构性缺陷。
库内能做的只有**单调性检查**（`published_at` 变旧且内容不同则丢弃），
但它挡不住伪造 `published_at`，只能挡网络层的重复投递。
真正的裁决权在应用层（签名时间戳、内容版本号、每来源的更新速率限制）。

### D5 的最小修法（两行）

```rust
let total_mass = total_mass.max(1e-6);
if !total_mass.is_finite() { return; }   // 拒绝整份视图，而不是把它归一化到 1e-6
```

## 5. 分层：必须在本库修 vs 属于应用层

**必须在本库修**（否则反女巫不成立）：

1. **D1** —— 预算的分子必须与分母同口径。这是 S2/S3/S4/S5 的共同地基。
2. **D2** —— 预算的分母不能对「后来登记的账户」失效。同一个根因的第二个入口。
3. **D3 的 `params` 那一行** —— 便宜、零风险，顺手把 256 MiB / 609× CPU 两个洞一起堵上。

**属于应用层**（规格已明确归应用层，本次实测确认库内确实没有、也不该有）：

- **签名与 owner 绑定**：`on_view(owner, view, ...)` 完全信任调用方传的 `owner`，
  视图负载里没有 owner、没有签名。把 A 的观点说成 B 的，库不会发现。
  应用层必须自己在负载里放 owner 并验签。
- **D4 重放/新鲜度的最终裁决**：见上。
- **D3 的限流/限长**：带宽、请求速率、每来源的视图大小配额。
- **D7 观点缓存的淘汰策略**：库只提供 `prune_stale`，什么时候调、允许多大，是业务判断。
- **banlist / 黑名单 / 女巫名单**：已在 commit 7376990 移出库，本次审计确认库内确实没有残留。

## 8. 建议：删 / 改 / 留

**删**：无。本次审计没有发现「该删的机制」——恰恰相反，最危险的是**改错顺序**。

**改**：
1. `query` 里把 `clamp` 挪到除法**之前**（D1，一行）。
2. `StoredView` 记录 `mass_covers`，`query` 对后来登记的账户置 0（D2，两行）。
3. `on_view` 开头校验 `view.params() == cfg.view_params`（D3，一行）。
4. `on_view` 拒绝非有限 `total_mass`（D5，两行）。
5. `tm_view::median_sorted` 改成 `a*0.5 + b*0.5`（D6，一行，与 `tm_agg` 已有写法对齐）。

**留**（这些是真正在挡攻击的，别动）：
- **噪声底**：实测把全桶 MAX 的 `Σv` 从 203 打到 0。关掉它（`noise_multiplier=0`）就是灾难。
- **`last_check` 作为衰减基准**（而不是 `published_at`）：伪造未来发布时间零收益。
- **`saturating_sub`**：时钟回拨永不产生负年龄、永不回绕。
- **`BTreeMap` 存 views**：S6 逐位确定性的来源。
- **`tm_agg::valid_samples` 过滤非有限值**：NaN 来源被整条剔除，不会一处污染全表。
- **`MAX_SCORE = 1e9` 截断**：+Inf 变有限值而不是 NaN。

- 16 632 次注入的 S2 原实验没有重跑（不在本任务范围）。本报告只指出它用的是合规视图，
  没有覆盖放大路径。
