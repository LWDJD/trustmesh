# P-scale —— 规模、耗时，以及一个关于 S1 的重要发现

> 装置：`crates/exp/src/bin/p_scale.rs`（提交 `5cad463`）
> 环境：Windows x86_64，rustc 1.96.0，`--release`，单进程单线程
> 参数：k=16、4 轮传播、每轮 24h、半衰期 72h、8% 女巫（4 个集群）
>
> **为什么做这个**：B0 基线只跑了 n=200，回答不了「真实应用（几千人）能不能用」。
> A11 给过单次操作的复杂度，但没把完整传播流程 + 攻击场景一起跑过。

## 1. 耗时与内存（buckets=512，n=200/600/1000）

| n | 边数 | 诚实观察者 | 建引擎 | on_view 合计 | export 合计 | query 合计 | dist 合计 | 视图内存 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 200 | 1,613 | 104 | 2.5 ms | 306 ms | 71 ms | 21 ms | 20 ms | 4.2 MB |
| 600 | 4,772 | 275 | 16 ms | 1,090 ms | 473 ms | 152 ms | 152 ms | 11.1 MB |
| 1000 | 8,343 | 452 | 45 ms | 4,111 ms | 2,209 ms | 755 ms | 797 ms | 20.1 MB |

**单次调用（buckets=512）**：

| n | tick | on_view | export_view | query |
|---:|---:|---:|---:|---:|
| 200 | 0.64 µs | 43.7 µs | 163 µs | 0.83 µs |
| 600 | 0.83 µs | 57.9 µs | 401 µs | 0.78 µs |
| 1000 | 1.31 µs | 136.8 µs | 1,135 µs | 1.41 µs |

**读法**：
* `on_view` 与 `export_view` **随 n 线性增长**（它们都要遍历全部已知账户估总质量 / 发布全量观点），
  这是设计使然，不是实现低效。
* `query` 与 `tick` 基本**与 n 无关**（0.8~1.4 µs / 0.6~1.3 µs），因为它们只按清单长度算。
* `trust_distribution` 是 Θ(n·m)，n 从 600 到 1000 时 dist 合计从 152 ms 涨到 797 ms（5.2 倍，
  接近 n² 的 2.8 倍 × 观察者数增长的 1.6 倍 = 4.5 倍）。
* **内存是更硬的墙**：每份观点 10,240 B（512×5 f32），n=1000 时 2,056 份缓存 = 20.1 MB/节点。
  用默认 2048×5（40,960 B）时同样规模是 **80.3 MB/节点**。

### 1.1 桶数与耗时的关系

| buckets | 每份观点 | n=1000 的 on_view 合计 | n=1000 的 export 合计 | n=1000 内存 |
|---:|---:|---:|---:|---:|
| 256 | 5,120 B | 4,111 ms | 2,362 ms | 10.0 MB |
| 512 | 10,240 B | 4,181 ms | 2,208 ms | 20.1 MB |
| 1024 | 20,480 B | 4,111 ms | 2,364 ms | 40.2 MB |
| 2048 | 40,960 B | 4,159 ms | 2,498 ms | 80.3 MB |

**桶数对耗时几乎无影响**（差异在噪声范围内），只影响内存和精度。这是个重要结论：
**「把桶数调大」是免费买精度，代价只有内存**。

## 2. **重要发现：S1 的「严格为 0」不是无条件的**

B0 基线（8 seed，buckets=2048）报 **S1 = 0.00000000 ± 0**。
但这里 n=200 是 **0.0122**、n=600 是 **0.0097**、n=1000 是 **0.0166**。

**这不是算法变了，是桶数变了。** 把桶数扫一遍（每格 1 seed，n=200/600/1000）：

| buckets | n=200 | n=600 | n=1000 |
|---:|---:|---:|---:|
| 256 | 0.02073 | 0.03452 | 0.06294 |
| 512 | 0.01223 | 0.00970 | 0.01661 |
| 1024 | 0.00762 | 0.00135 | 0.00410 |
| **2048** | **0.00000** | **0.00014** | **0.00214** |

### 2.1 机制

Count Sketch 的碰撞噪声会给**从没被任何来源评过分的账户**凭空造出一份朗读数
（这与 S4 是同一个根因）。女巫正好是「谁都没评过」的那批账户，于是：

~~~text
S1 = 女巫均值 / 诚实均值
    = 碰撞噪声 / (真实声望 + 噪声)
~~~

桶越少，碰撞越频繁，噪声越大 ⇒ S1 越偏离 0。**分母里诚实账户的真实声望被噪声摊薄，
分子里女巫只有噪声**，比值就上去了。

### 2.2 结论（这条要改判据）

**「S1 应恒为 0」是错的验收线。正确口径是：**

> S1 必须与 `view_params` 绑定。在 buckets=2048×5 下实测 ≤ 0.002；
> 在 buckets=512×5 下实测 0.010~0.017；**桶数越少 S1 越大，且与网络规模正相关**。

这不是 bug，是 Count Sketch 的固有精度代价。但它意味着两件事：
1. **部署时必须把 buckets 写进威胁模型和验收条件**，不能只说「我们的 S1 是 0」；
2. A12 提的**定长稀疏表**能彻底消除这个问题（「没被提到」精确为 0，不是噪声）。

### 2.3 反证：噪声底乘数**完全无效**

我原以为可以靠 `noise_multiplier`（「低于噪声底视为没表态」）把碰撞噪声清掉。
把乘数从 0 扫到 8（buckets=512）：

| noise_multiplier | n=200 S1 | n=600 S1 | n=1000 S1 |
|---:|---:|---:|---:|
| 0（关闭） | 0.012227 | 0.009701 | 0.016616 |
| 1（默认） | 0.012227 | 0.009701 | 0.016615 |
| 2 | 0.012227 | 0.009701 | 0.016609 |
| 4 | 0.012227 | 0.009701 | 0.016596 |
| 8 | 0.012227 | 0.009701 | 0.016551 |

**五项几乎逐位相同**（只在小数点后第 6 位有千分之几的漂移）。

**原因**：`noise_floor(1000, seed)` 是对 1000 个**随机 key** 采样后取中位数。
稀疏观点下绝大多数随机 key 查询结果为 0 ⇒ **中位数恒为 0** ⇒ 乘多少倍都是 0 ⇒ 门限从不触发。

这正是审计 `A13-spec.md` 记的「§4.5 用途 2/3 门限恒为 0，等于没做」。
**现在有了定量证据**：这个机制在当前实现下**完全惰性**，调它不会有任何效果。

## 3. S2 / S6 在大规格下仍成立（除极少数情形）

| 配置 | n=200 | n=600 | n=1000 |
|---|---:|---:|---:|
| buckets=256 | 0 | 0.001364 | 0.001327 |
| buckets=512 | **0** | **0** | 0.000166 |
| buckets=1024 | **0** | **0** | **0** |
| buckets=2048 | **0** | **0** | **0** |

（分母：n=1000 时 452 个诚实观察者 × 34 个女巫 = 15,368 对）

S2 越线率在 buckets≥1024 时严格 0；512 桶下 n=1000 出现 **2 对越线 / 12,058 对**，
量级 1.7e-4，来源同样是碰撞噪声把某些女巫的读数推过了 hm。

**S6（同输入重跑，全部声望矩阵最大绝对差）在所有 4 种桶数 × 3 种规模下都是 0。**

## 4. 复现

~~~powershell
$env:TMP="<仓库根>/.tmp"; $env:TEMP=$env:TMP
cd crates/exp
cargo build --release --bin p_scale

# 默认 512 桶
./target/release/p_scale.exe 200 600 1000

# 扫桶数
foreach ($b in 256,512,1024,2048) { $env:P_SCALE_BUCKETS="$b"; ./target/release/p_scale.exe 200 600 1000 }

# 扫噪声底乘数（会看到它完全无效）
foreach ($n in 0,1,2,4,8) { $env:P_SCALE_NOISE="$n"; ./target/release/p_scale.exe 200 600 1000 }
~~~

## 4.1 n=2000 的实测（补做，2026-11-16 深夜）

> 上面 §2 的桶数扫描只到 n=1000。按作者「仿真要做满」的要求，补跑 n=2000。

| buckets | 建引擎 | on_view 合计 | export 合计 | query 合计 | dist 合计 | 单次 on_view | 内存 | S1 | S2 越线率 | S6 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 512 | 171 ms | 12,624 ms | 9,723 ms | 3,509 ms | 3,251 ms | 205 µs | 45.8 MB | **0.06326** | **0.002991** | 0 |
| 2048 | 173 ms | 13,232 ms | 11,540 ms | 3,816 ms | 4,050 ms | 215 µs | **183.4 MB** | **0.00322** | **0.000042** | 0 |

**读法**

1. **S1 与 S2 在 n=2000 时都开始明显地恶化**：
   * 512 桶：S1 = 0.0633（是 n=1000 的 0.0166 的 **3.8 倍**），S2 越线率 0.30%（是 n=1000 的 18 倍）
   * 2048 桶：S1 = 0.0032（n=1000 的 0.0021 的 1.5 倍），S2 越线率 0.004%（是 n=1000 的 0 的「第一次非零」）
2. **规模效应是明确的**：碰撞噪声的分子是「随机桶里被撞进来的他人声明」，而分母（诚实账户真实声望）
   随 n 增大而摊薄。**n 越大，同样桶数的相对噪声越大。**
3. **内存是硬墙**：2048 桶在 n=2000 时每节点 **183.4 MB**，512 桶只有 45.8 MB（4 倍差）。
   2000 节点的全网视图缓存总量是 2000 × 183.4 MB = **358 GB**（2048 桶）/ 89.6 GB（512 桶）。
   **这个量级对大部分部署是不可接受的**，这是「桶数取舍」成为必答题的直接原因。
4. `query` 与 `tick` 仍然稳定（1.7~1.8 µs / 1.3 µs），**与 n 近乎无关**——瓶颈始终是视图的字节量。

**为什么 S2 越线率在 512 桶下反而更高**：越线率的分子是「女巫读数超过 hm 的对数」。
n 越大，hm 因为被摊薄而趋近 0，于是「任何一点碰撞噪声都能让它超过 hm」。
这与 S1 是同一个机制的两种表现。

## 5. 给部署者的三条结论

1. **n ≤ 1000 完全跑得动**：单次 on_view 137 µs、query 1.4 µs，一轮传播 4.1 s（1000 节点的全网一轮）。
   瓶颈不在 CPU，在**视图带宽**（每份 40 KB × k=16 × 每轮 = 640 KB/节点/轮）。
2. **内存是更硬的墙**：2048×5 时每节点 80 MB（1000 份缓存）。要省内存就减桶数，
   代价是 S1 从 0 涨到 0.017 ——**这是精度和内存的直接权衡，必须显式决策**。
3. **`noise_multiplier` 旋钮是假的**，调它没有任何效果。别指望它。
4. **n ≥ 2000 时桶数必须重新估值**：512 桶在 n=2000 下 S1 = 0.0633（n=1000 的 3.8 倍），
   S2 越线率也从 0 涨到 0.30%。要么上 2048 桶（代价 183 MB/节点内存），
   要么换 A12 的定长稀疏表（支持度 ≤ cap 时逐位精确，且体积只有 770~3074 B）。
5. **别在 2000+ 规模上继续用 Count Sketch**：内存与精度两头都不划算。
   这是 A11/A12 早就得出的结论，现在有了 n=2000 的实测支撑。
