# 决策矩阵：要不要把 `tm_engine` 换成 `tm_mincore`

> 2026-11-19。这是 5 项工程缺口补齐**之后**才该看的文档。
>
> **本文不给结论，只给判断依据。** 这是架构决策，必须作者拍板。

## 0. 先看清这两者是什么关系

它们**不是「新旧版本」**，而是**两种不同的产品定位**：

| | `tm_engine` | `tm_mincore` |
|---|---|---|
| 定位 | **一个完整的库** | **一个纯内核** |
| 视图表示 | Count Sketch（2048×5 f32 = 40,960 B） | 定长稀疏表（`cap×6+2` = 770~3,074 B） |
| 账户表 | 有（`AccountTable`，75 B/账户） | **没有**（`Acc` 是不透明 `u32`） |
| badlist | 有 | **没有** |
| 抽样预算 | 有（`freshness_budget`/`recommended_k`） | **没有**（应用层自己定 `k`） |
| 快照 | 有（`SNAPSHOT_VERSION=2`） | 正在补 |
| 测试 | 206 | 128（正在补到 200+） |
| 代码行数（生产） | 2,315（全 4-crate closure） | 744 |

⟹ **换掉 engine = 把责任推给应用层，换体积和确定性。**
这不是「升级」，是「换定位」。

---

## 1. 决策矩阵

按你的场景逐行打分，最后看哪一列得分高。

| 你的情况 | 选 `tm_engine` | 选 `tm_mincore` |
|---|---|---|
| **要防陌生人刷分**（主要威胁是纯女巫、批量注册） | 可用，但有噪声底（S1 2.46% 非零） | ✅ **精确 0**，结构性优势 |
| **要防内部串谋**（熟人背叛） | ❌ 两者都挡不住（β=0.3 的算术后果，4.37×/最坏 8.14×） | ❌ 同上 —— **换实现不解决这个问题** |
| **账户规模 ≤ 300** | ✅ 现成可用 | ✅ 可用但没必要（体积优势不明显） |
| **账户规模 > 2,000** | ❌ 四道墙全中（同一份字节读出差 10 倍的声望） | ✅ **四道墙全解** |
| **内存受限（每节点 < 50 MB）** | ❌ `AccountTable` 75 B/账户，1M 账户 = 109 MB | ✅ **770~3,074 B/视图，无账户表** |
| **要求逐位可复现**（跨平台/跨节点） | ❌ S6 = 0/20 seed | ✅ **S6 = 20/20 seed，wasm 与 native 逐位相同** |
| **需要账户表 / 公钥映射** | ✅ 内置 | ❌ 你要自己做 |
| **需要 badlist（受害者反馈）** | ✅ 内置 | ❌ 没有（不在 A12 设计范围） |
| **需要抽样预算策略** | ✅ 内置 `recommended_k` | ❌ 你要自己定 |
| **清单很长（> cap）** | ✅ 无截断（估计器天然有损） | ⚠️ **截断**（cap=128 时 20.1% 视图被截、平均丢 2.81%） |
| **关注上限不固定 / 会增长** | ✅ 无影响 | ⚠️ 要预留 `cap >= max_follows` 并可能需要全网同时改 |
| **只有浏览器 / 边缘节点** | ⚠️ 体积大（40 KB 视图） | ✅ 体积小 14~50 倍 |
| **不想改协议** | ✅ 现成 | ❌ 视图格式、快照版本、发布方职责全要改 |

## 2. 三条最容易被忽略的权衡

### 2.1 「精确 0」的价值取决于你的威胁模型

mincore 的 S1 是**精确 0**（不是「很小」）。这在什么场景下值钱？

- **值钱**：如果你的产品逻辑是「声望 > 0 才显示」。engine 下 2.46% 的女巫会拿到
  `1e-6` 量级的非零值 —— 如果代码写的是 `if score > 0.0 { show() }`，那 2.46% 就漏了。
  实际上你不会这么写（会设阈值），但**「结构保证」比「阈值约定」可靠**。
- **不值钱**：如果你总是用相对排序或阈值判断，噪声底本来就被压掉了。

### 2.2 「截断」是 mincore 唯一的实质损失

Count Sketch 的误差是**噪声**（不可预测但有界），定长表的误差是**截断**（只丢低分的、确定性的）。

| | Count Sketch | 定长表 |
|---|---|---|
| 误差性质 | 随机噪声（每份字节都不同） | 确定性截断（同一份输入永远丢同样的条目） |
| 能不能「修」 | ❌ 无解（信息已被压掉） | ✅ **加大 cap 就能零损失** |
| 代价 | 恒定 40 KB | cap 越大越贵（线性） |

⟹ **mincore 的损失是「可调的」，engine 的噪声是「不可调的」。**
这是我认为 mincore 在架构上更优的唯一一条**真论据**。

### 2.3 「更纯的内核」意味着你要多写多少代码

换 mincore 之后你要自己实现：

| 能力 | 大概工作量 |
|---|---|
| 账户号 ↔ 公钥映射（可验证派生） | 小（如果已有 PKI） |
| 视图验签 | 小 |
| 投递 / 超时 / 重试 | 中 |
| 节点发现（含 eclipse 防护） | **大**（这是最危险的一块） |
| 抽样节奏（`k` 怎么定） | 小（但有调参成本） |
| badlist（如果原来用 engine 的） | 中（要重新设计） |

**「大」那一条是真正的成本**：engine 的 `PROTOCOL.md` §0.5 那三条硬要求，
换成 mincore 之后一条都不能少，但**它不再帮你做任何一件**。

## 3. 三种可行的路径（不是二选一）

### 路径 A：保持 engine，不换

适合：账户规模 ≤ 300、主要威胁是纯女巫、不想改协议。

代价：接受四道墙（尤其是「同一份字节在不同节点读出差 10 倍」）。
**缓解**：把 `k` 和 `max_views` 设小，控制规模。

### 路径 B：两者并存，按场景选

适合：大部分部署用 engine，内存/规模敏感的场景用 mincore。

代价：维护两套 API、两套协议、两套测试。**但要共享同一套威胁模型**（已在做）。

### 路径 C：换成 mincore，重写应用层

适合：新项目、或者应用层本来就要重写、或者目标是「浏览器/边缘节点」。

代价：工作量大（见 §2.3），且要接受一次协议变更。

**收益**：一次性解掉四道墙 + 体积小 14~50 倍 + 逐位确定性。

---

## 4. 我的建议（仅供参考，最终你定）

> **短期内（现在）走路径 A 或 B。**
> **长期如果要支持「理论无限大的网络」，必须走 C。**

理由：

1. **四道墙里只有墙 1（`total_mass` 依赖接收方账户表）是致命的**——它破坏「同一份字节读出同一个声望」。
   如果你的网络规模确定不会超过 300 个账户，墙 1 不会触发，engine 够用。
2. **但作者已经明确说「需要为理论无限大的网络做准备」**（2026-11-17）。
   那么按这个目标，**engine 的墙 1 是必须解决的**，而 mincore 恰好一次解决它。
3. **C 的成本主要在应用层，不在库本身** —— mincore 已经 128 个测试、5 项缺口在补、
   有 PROTOCOL.md 和 DEPLOY.md。剩下的「发现协议」本来就是应用层的活（engine 也不做）。

⟹ **如果目标是无限规模，选 C 是对的；如果只是「先能跑」，路径 A 更省事。**

**这一条必须你来定**：我不知道你的部署目标规模、也不知道你愿不愿意改协议。
