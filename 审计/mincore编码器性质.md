# mincore 编码器性质测试：P1~P6 落地报告

> 2026-11-19。对应缺口 #5（见 [`mincore缺口进度.md`](mincore缺口进度.md)）。
> 测试文件：[`crates/mincore/tests/codec_props.rs`](../crates/mincore/tests/codec_props.rs)。
> **零生产代码改动**——本项只补测试。

---

## 0. 一句话

`SparseView` 的字节编码是**协议边界**（收到的每一份视图都是不可信字节）。
`view.rs` 原有的 29 个单测都是「针对具体构造」的逐条规范性检查；
本项补的是**普遍性质**层：一个独立参考实现做差分、系统性的拒绝完备性扫描、
以及会持续跑的确定性模糊测试。

**结论：未发现缺陷。** 110 万模糊样本（旧格式 100 万+10 万、前缀格式 50 万+5 万）
全部满足「接受 ⟺ 规范形式」，参考解码器与被测解码器在**全部**样本上判据一致。
两个已知的 API 面差异被钉住现状（见 §6），按项目既定口径**不判为缺陷**。

## 2. 六组性质：每条怎么测

### P1 规范性 / 唯一性

核心判据是「**同一份观点只有唯一一种字节串**」：

* `encode(decode(b)) == b` —— 被接受的负载必须**已经**就是规范形式（逐字节外环）；
* `decode(encode(v)) == v` —— 合法视图往返后语义与字节都闭合；
* **单字节变异注入性**：对合法字节串的**每一个**字节位置改成任意不同值，
  只要 decode 成功，结果视图必与原来不相等（逐位比较 `encode`）。
  实现上对 cap=2/8 做「全部位置 × 255 个候选值」全扫，
  对 cap=128 做「全部位置 × 4 个典型脏值」；
* **编码是单射**：400 个随机合法视图按编码字节去重，同一字节串不能解出两个视图；
* **稠密小域全枚举**：cap ∈ {1,2,3}、条数 ∈ [0, cap+1]、账户号/分数的全部小域组合，
  与参考解码器逐条对拍（接受/拒绝必须完全一致）；
* **输入顺序无关**：同一批 `(账户, 分数)` 的逆序 / 随机打乱 / 重跑，
  编码逐字节相同。

### P2 拒绝完备性

`decode` 的 **6 条拒绝条件**逐条系统扫（`view.rs` 里原有的 4 个拒绝测试
各只用了 1~2 个固定样例，填充区那条只扫了 cap=2 的 6 个偏移）：

| # | 拒绝条件 | 本报告的扫描范围 |
|---|---|---|
| 1 | `cap == 0 \|\| cap > MAX_CAP` | cap ∈ {0, 4097, 4098, 100000, u32::MAX, usize::MAX} × 6 种长度 |
| 2 | 长度 ≠ `cap×6+2` | cap 1..=4096 **逐值** × 短1/短2/短6/多1/多2/多6 |
| 3 | `count > cap` | cap=1/2 时 count 从 `cap+1` **全扫描到 65535**；其余容量取 7 个边界值 |
| 4 | 任一槽 `q == 0` | cap ∈ {1,2,3,8,128} × 每个 count × **每个槽位** |
| 5 | 账户号非严格升序（含相等/降序/逆序） | cap ∈ {2,3,8,128} × 每个 count × **每个相邻位置** × 3 种破坏 |
| 6 | 填充区任一非零 | cap ∈ {1,2,3,8,128} × **全部 count** × **全部字节位置**；cap=512 抽 5 个 count 全位置 |

全部用 `std::panic::catch_unwind` 包住，断言「**绝不 panic**」。

### P3 模糊测试

xorshift64 确定性模糊器（零外部依赖，同一种子给同一条序列，测试不会 flaky）。

* **CI 口径**：2 万随机负载（4 种构造交替：长度随机 / 长度恰好但内容全随机 /
  合法构造 / 合法后变异）+ 2 万变异。
* **全量 `#[ignore]`**：100 万随机 + 10 万变异，
  跑法 `cargo test --release --test codec_props -- --ignored --nocapture`。

每个样本都做三方差分；被接受的样本还要求：
`encode` 逐字节等于输入 ∧ 所有读数 `is_finite()` ∧ 单条 `v ∈ [0,1]` ∧
非空时 Σv ≡ 1（1e-5 内）∧ 规范字节再解码幂等。

### P4 交叉验证

测试内**独立慢速实现**：BTreeMap 合并（重复账户取最大、0 分丢弃）
→ `(分数降序, 账户号升序)` 截断 → 按账户号升序落表。
与 `from_scores` 逐条对拍 300 轮（cap ∈ {1,2,3,5,7,13,32,128,512}，含 NaN/负数/超大值/
归零小值/并列分数）：

* 槽位表 / `len` / `total_q` 全等；
* 手工装配的规范字节串 == `encode()`；
* 截断不变式：保留的是合并集合的子集、被丢的读作 0、`len == min(合并条数, cap)`；
* `truncated_mass` 口径独立重算后**逐位**比较。

> 注：`from_slots` 不是公开 API（只有私有的 `from_slots_unchecked`，契约「不校验」），
> 所以「与 `from_slots` 对比」实际落成「与测试内独立慢速实现对比」。

### P5 codec 层定点往返（**不与 `fixed.rs` 重复**）

`fixed.rs` 的 `quantize_dequantize_往返恒等` 已**穷举 65536 个定点值**，
那是定点**数学**层。P5 只测 **codec 层**：`q` 以小端 u16 写进字节载荷、
`decode` 读回、`encode` 再写回，`q` 取 `1..=65535` **全量**逐字节不变；
`q=0` 必须拒绝（0 就是「没表态」）。

### P6 前缀格式（cap 自描述）

dev 新合并的 `encode_prefixed` / `decode_prefixed` / `decode_prefixed_result`
是**新增的协议边界**，同样需要性质测试：

* **布局与「只差一个头」**：`encode_prefixed() == [cap(LE u16)] ++ encode()`，
  总长 `cap×6+4`，`prefixed_bytes() == bytes() + 2`（前缀是裸 u16，**没有魔数**）；
* **往返逐字节闭合** + **单字节变异注入性**（同 P1 口径，走前缀入口）；
* **撒谎的 cap**：0 / `MAX_CAP+1` / 65535 / 与长度不符 —— 一律拒绝且不 panic；
* **截断与多余字节**：0 到 `len-1` 的每一种截断、尾部追加 0/1/0xFF 都拒绝；
* **两种格式互不误判**：独立验证 ENCODING.md §4 的模 6 同余类
  （旧 `L ≡ 2`、新 `L ≡ 4`），并断言「长度不等就拒绝」而不是「靠同余类」；
  两个边角（旧空表 `[0;8]`、首账户号低 16 位为 0 的旧负载）落在 `BadCap`；
* **每条规范检查都有独立错误码**：`DecodeError` 的 7 个变体各自在对应违规上出现一次，
  且 `as_str` 标签互不相同（日志可定位）；
* **前缀模糊**：CI 1 万随机 + 1 万变异；全量 `#[ignore]` 50 万 + 5 万。

## 3. 参考解码器的独立性（本项最有价值的部分）

如果用被测的 `decode` 去验证 `encode`，那是循环论证：两边同一个 bug 就互相掩护。
所以测试文件内**手写**了两个参考解码器，并刻意与生产实现不同：

| # | 生产实现 | 参考实现 | 目的 |
|---|---|---|---|
| 1 | 先查 cap，再 `checked_mul` 算长度 | 先用 **u128** 算期望长度**再**比长度 | 检查顺序相反，避免同构 |
| 2 | `u16::from_le_bytes` / `u32::from_le_bytes` | 手工 `b[i] + 256 * b[i+1]` | 不共用便利函数 |
| 3 | 共享 `SLOT_BYTES` / `VIEW_OVERHEAD` / `MAX_CAP` | 写死 `REF_SLOT=6` / `REF_OVERHEAD=2` / `REF_MAX_CAP=4096` | 不共用格式常量（另有 `p1_格式常量钉死` 把两者焊在一起） |
| 4 | `prev` 变量判升序、`.iter().any()` 判填充区 | 与上一槽比较、`while` 逐字节推进 | 写法不同 |

差分断言（`xcheck_decode` / `xcheck_prefixed`）：

* 两边都拒绝 ⟹ 判据一致；
* 两边都接受 ⟹ cap / 条数 / 槽位 / `total_q` 全等，且 **`encode(decode(b)) == b`**；
* **一边接受一边拒绝 ⟹ 立即失败**（这是差分要抓的分歧）。

## 4. 模糊测试实际跑了多少

| 层 | 随机 | 变异 | 总样本 | 接受率 | 耗时（release） |
|---|---:|---:|---:|---|---:|
| 旧格式（P3，CI 口径） | 20 000 | 20 000 | 40 000 | 25.59% / 2.54% | 2.61 s（debug） |
| 旧格式（P3，全量） | 1 000 000 | 100 000 | **1 100 000** | 25.71% / 2.77% | **4.66 s** |
| 前缀格式（P6，CI 口径） | 10 000 | 10 000 | 20 000 | 25.51% / 2.51% | 1.33 s（debug） |
| 前缀格式（P6，全量） | 500 000 | 50 000 | **550 000** | 25.63% / 2.37% | **2.52 s** |

合计 **171 万**样本（其中 165 万来自全量）。随机样本的接受率稳定在 ~25.6% ——
这不是全部构造都能被接受（4 种构造里有 3 种是半合法/非法），
接受面与拒绝面都被充分打到。

> 「变异样本接受率只有 2.4~2.8%」是正确的：合法负载改 1~3 个字节后，
> 绝大多数会破坏规范性（升降序、q=0、填充区、长度），只有少数落在
> 「仍合法」的窄带里。**变异接受 > 0 是必要的**——否则「改字节仍合法」这条面没被覆盖。

## 5. 发现了什么

**没有发现缺陷。** 具体地：

* 参考解码器（旧格式 + 前缀格式两个）与被测解码器在**全部** 171 万样本上
  接受/拒绝完全一致，接受时 `cap/len/slots/total_q` 全等、字节逐位闭合；
* `decode_prefixed` 与 `decode_prefixed_result` 的判据在全部前缀样本上一致
  （前者 == 后者的 `.ok()`，这正是 `view.rs` 文档写明的契约）；
* 前缀格式与旧格式的互不误判在全部 9 个容量档上成立；
* 6 条拒绝条件在全部容量/条数/字节位置上**没有一条漏网**；
* 无一处 panic（全部走 `catch_unwind`）。

## 6. 两处已知 API 面差异（钉住现状，不判为缺陷）

### 6.1 同一个非法 cap，三个入口行为不同

| 入口 | `cap = 0` | `cap > MAX_CAP` | 契约 |
|---|---|---|---|
| `SparseView::new` | **panic** | **panic** | 配置错误，不是运行时输入 |
| `SparseView::decode` | `None` | `None` | 不可信输入 |
| `SparseView::truncated_mass` | 返回 `1.0` | 返回 `0.0` | 报告侧估算，不校验 |

`new` 的 panic 与 `truncated_mass` 的不校验已分别由 `view.rs` 的既有测试钉住；
本文件只额外钉住「**同一个**非法 cap 上 decode 拒绝而 truncated_mass 静默出数值」
这个对照（`附_非法cap三入口行为不同_现状钉住`）。

**风险口径**：这是 API 面一致性问题（运维/报告侧可能把非法配置的静默读数当真），
不是安全缺陷 —— 三个入口的契约本来就不同。按项目既定口径记录现状、不断言为缺陷。

### 6.2 `encode` 的条数无校验，但公开路径不可达

`encode` 里 `self.slots.len() as u16` 没有校验。要造出「自家 `decode` 都拒收」
的条数（`len > 65535`）必须走私有 `from_slots_unchecked` ——
而所有公开构造器都把条数压在 `cap ≤ MAX_CAP = 4096 < 65536` 以内。
本文件钉住这个算术前提（`附_encode条数无校验但公开路径不可达`）。
