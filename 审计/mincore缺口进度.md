## 每项的关键结论

### 1. 状态快照

没有快照的节点重启后会在**下一步就分叉**（同一次抽取抽到不同的人）。

补齐后：`Node::snapshot()` / `Node::restore()`，恢复后 `query`/`distribution`/`tick` **逐位一致**。
关键在 `RoundBitmap` 的 **5 个字段**（`order`/`drawn`/`remaining`/`version`/`ready`）都要入档 ——
少存 `version` 或 `ready`，恢复后 `sync()` 会判定「未同步」并重建 `order`，把本轮进度抹掉。

### 2. 资源上限

之前 `views` 无界：cap=512 时 100 万条 ≈ 3 GB。

补齐后：`Config::max_views`/`max_list`（默认 4096，`0`=无上限）。
**策略是「拒绝新增」而非 LRU** —— LRU 的淘汰顺序依赖历史到达顺序，
`snapshot→restore` 只恢复当前状态、不恢复隐式淘汰序 ⟹ 破坏逐位确定性。

实测峰值（A12 口径）：`|views|` 均值 99.3 / p95 162 / 最大 210 ⟹ 默认 4096 有 20~40 倍余量。

### 3. cap 自描述

旧格式不自描述 cap ⟹ cap 不一致时长度不符 ⟹ 整条视图被拒 ⟹ **网络分裂成孤岛**。

补齐后：`encode_prefixed()` 前 2 字节写 cap，总长 `cap*6+4`。
**两种格式不会互相误判，可证明**：旧格式 `L ≡ 2 (mod 6)`、前缀格式 `L ≡ 4 (mod 6)`，
两个解码器都要求长度严格相等 ⟹ 无整数解 ⟹ 必被拒。
但这依赖「精确长度匹配」，若未来出现第三种格式**必须加带内魔数**。

### 4. 性能基准

**engine 撑不住的路径是唯一的**：`trust_distribution` n=100→1600 = 3.00 ms → **1914.79 ms（638×）**，
比 O(n²) 应有的 256× 还陡。外推门槛：**100 ms ≈ n=366**、1 s ≈ n=1156。

**mincore 同区间不涨**：`distribution` 0.022 → 0.826 ms，与「网络有多少人」无关。

**但 mincore 有一段会输**：n=100 + 清单 100 + 视图 4096 条 + cap=4096 ⟹ `publish` 慢 **17.1×**。
机制：`export_view` 按 `n×|清单|×hashers` 付钱，`publish` 按 `Σ 视图条目` 付钱。
⟹ 部署规则：**`cap` 不要比 `max_follows` 大太多**（第二个理由：别让 publish 变慢）。

### 5. 编码器性质测试

**171 万样本**模糊测试（旧格式 110 万 + 前缀格式 55 万），全部实跑。
**独立参考解码器**（检查顺序相反、手工拼小端、不共享常量）差分 —— 避免「用被测的 decode 验证 encode」的循环论证。

**结论：未发现缺陷。** 参考解码器与被测解码器在全部样本上接受/拒绝完全一致；
接受时 cap/len/slots/total_q 全等且 `encode(decode(b)) == b` 逐字节闭合。

## 为什么把这 5 项放在一起做

它们不是「代码质量」问题，是「能不能上线」问题：

| 缺口 | 不补的真实后果 |
|---|---|
| 状态快照 | 重启后节点**下一步就分叉** |
| 资源上限 | `views` 无界；cap=512 时 100 万条 ≈ 3 GB |
| cap 自描述 | **网络分裂成孤岛** |
| 性能基准 | 不知道「在什么规模开始撑不住」⟹ 不敢上线 |
| 编码器性质 | 协议边界是不可信字节，29 个单测不够 |

**这 5 项全绿之后，`tm_mincore` 才从「数学内核」变成「能上线的库」。**

但它仍然缺 badlist、抽样预算接口、账户表 —— 见 `审计/威胁模型.md` §8.4.5。
