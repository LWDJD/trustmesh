# 历史遗留盘查（2026-11-22）

> 作者说：「我现在还没有发布第一版的正式版，还没有历史遗留问题，你要不再检查一下有没有历史遗留问题。」
>
> 本文是那次盘查的完整结论。**「没发布过」是本次盘查最关键的判据** —— 它让「向后兼容」这个
> 最常见的遗留理由直接失效。

---

## 0. 判据

**「历史遗留」的定义**：只因为「过去是那样」而存在的代码/文件/分支，删掉不会损失任何当前能力。

判据问三个问题：
1. 它存在的理由，在**当前**事实上还成立吗？（「没发布过」⟹ 外部用户依赖 = 0）
2. 删掉后要改多少东西？改动是机械的还是有风险的？
3. 保留它会不会让**未来**更贵（每次改 API 都要维护）？

**「没发布过」推翻了什么**：三个兼容层空壳 crate 的**唯一**正当理由。

## 2. A 项：删兼容层空壳（本次最大的一件事）

### 2.1 为什么昨天的判断错了

昨天合并时我留了三个 23 行的转发空壳，理由写进文档是：

> 「仓内有 60+ 个文件引用旧路径（`crates/exp` 的实验 bin、`crates/mincore` 的对照实验、`tools/` 的 wasm 对拍）。留一层转发能让「合并结构」和「改 68 处 import」分成两步。」

**这个理由的一半是错的**：
- 「仓内有 60+ 文件引用」——**对**，但那是**仓内自引用**；
- 「所以需要兼容层」——**不对**。兼容层是为**外部用户**准备的，而本库从未发布过。

**外部用户数 = 0 ⟹ 旧 import 路径没有任何人依赖 ⟹ 空壳的唯一价值消失。**

留着它的真实代价：每次改动 `store`/`view`/`agg` 的公开 API，都要同步维护三条 `pub use` 转发；
每个新人读到 `crates/store/` 会先困惑「这里怎么只有 23 行」。

### 2.2 做了什么

| 动作 | 数量 |
|---|---|
| 删除 crate 目录 | 3 个（13 个被跟踪文件） |
| 改 `use tm_store::X` → `use tm_engine::store::X` 的文件 | 35 个 |
| 改完全限定名（`tm_view::CompressedView` 之类）的地方 | 11 处 |
| 改 `Cargo.toml` 的 path 依赖 | 3 个（exp / mincore / tools-wasm-smoke） |
| 改 `verify-all.ps1` | 删 `$shims` 与其编译检查段 |
| 改 `ci.yml` | 删昨天加的 `shims` job |
| 改文档 | README / 索引 / 交接 / engine lib.rs 模块文档 |

分布：exp 30 个 bin/lib + 11 处限定名、mincore 3 个、tools/wasm-smoke 1 个。

### 2.4 守卫 6 的一个真问题：「通过」可能是假的

**昨天那份 c1_badlist 对比是无效的。**

两个输出都在 120 秒的工具超时处被**截断**，而且在同一个字节位置截断，于是比对显示「逐字节相同」。
真相是：只比了前 1123 个字符，剩下的根本没比。

**本次修正**：用后台 job 跑完整版，两边各约 970 秒（`973.8s` vs `959.3s`）。
结果为 **5902 字符逐字节相同**，覆盖：

- 8 个 seed × 5 种 badlist 配置 × 6 个指标
- 闭式解抽查（`|G_engine − G_after|` 最大 3.80e-4）
- 网络均值表、中心对照表、跨 seed 汇总

唯一差异是末尾的 `总耗时 973.8s` vs `959.3s`（wall clock，非计算结果）。

**教训**：端到端「逐字节相同」这类守卫，必须确认**比较的两份输出都是完整的**。
截断的输出互相相等是巧合，不是证据。检查方法：先看输出长度是否吻合预期，或看结尾标记是否都在。

## 4. J 项：一个真实的 .gitignore 脆弱点

**现象**：
```text
根 .gitignore 最后一行：native.txt
tools/wasm-smoke/.gitignore：native.txt / /target / /Cargo.lock
tools/mincore-wasm/native.txt：73,273 B，git ls-files 显示**已跟踪**
```

**为什么不冲突**：gitignore **不影响已跟踪文件**。所以 mincore 的金标准没被忽略。

**但这是脆弱的**：
1. 根规则 `native.txt`（无路径）匹配**所有**同名文件 ⟹ 将来 `tools/foo/native.txt` 会被静默忽略；
2. 两处规则重复，读者会以为是有意的；
3. 一旦有人 `git rm --cached` 了 mincore 的 native.txt，它就会被忽略，金标准机制静默失效。

**修正**：根 `.gitignore` 里改成 `/tools/wasm-smoke/native.txt`，语义明确。

## 6. 明确「不是遗留」的四项

### 6.1 根目录 v1.0（6,277 行）
作者 2026-11-11 明确要求保留。它是**对照物**（新架构能不能比它好），不是死代码。

### 6.2 两套 RNG
195 行里的 55 行是两套实现。**不能合并**，理由**不是**「历史架构」：
- 两套的**输出序列逐位相同**（`rng_consistency.rs` 第 1 条断言就是钉死这个）
- 但**能力集不同**：`view::XorShift64` 有 `next_key()`（造 32 字节 key），
  `store::Rng` 有 `from_state()/state()`（快照精确恢复）与 `next_below()`（拒绝采样）

**这次盘查纠正了我昨天犯的错**：我昨天在交接文档里写「两套 RNG 输出序列逐位不同，
合并会破确定性」——**这是错的**。真实理由是能力集不同。已改正（交接文档 §7.3 + `rng_consistency.rs` 模块文档）。

### 6.3 根目录 14 个实验输出
476 KB，被 6 份实验报告 + `审计/A7-debt.md` + `索引.md` 引用。
它们是**证据**（报告里的数字来自这些文件）。移到 `审计/原始输出/` 要改 8 份文档共 14 处引用，
收益只是「根目录整洁」，风险 > 收益 ⟹ 不动。

### 6.4 两个 native.txt 策略不同
- `tools/wasm-smoke/native.txt`：不跟踪，每次重生成 ⟹ 验「当下 wasm==native」
- `tools/mincore-wasm/native.txt`：入库金标准 ⟹ 还能验「跨提交不自相矛盾」

**检查强度不同**，不是不一致。不动。
