## 1. P0 · 三个根因

### 1.1 分母只算「已取到观点」的来源 —— 影响最大的一条

```rust
// crates/engine/src/lib.rs:803  query() 的 items 循环
for (owner, stored) in &self.views {      // ← 只遍历「已缓存观点」
    let w = self.ratings.get(*owner) * decay;   // 我评过但没取到的来源，根本不进分母
    ...
}
```

于是 `D[T] = β/N + (1−β)/M`，M = 已缓存观点数：

| M（取到几份观点） | 被背书账户 ÷ 同样评过的诚实账户 |
|---:|---:|
| 1 | **236.67×** |
| 5 | 48.1× |
| 50 | 5.7× |
| N（全覆盖） | **3.33×** |

**M=N 时那个 3.33 就是 `1/β`**：因为 `D[T] = β/N + (1−β)/N = 1/N` 而 `D[诚实] = β/N`。
β=0.3 ⇒ 任何一次背书都值我自己判断的 3.33 倍。这是 3:7 配比的算术后果，不是 bug。

**分母其实有两个方向相反的错：**

| 集合 | 现状 | 后果 |
|---|---|---|
| 我评过、但一份观点都没取到 | **不进分母** | 单份观点独占群体项 → 236.67× |
| 有观点、但没提到 u | **进了分母**（贡献 0） | 稀释 —— **但这是对的** |

规格 §4.3 原话「只对『观点里含 u』的来源求和」，按字面第二条应该被**排除**。
**错的是规格，不是代码**，三条理由：

1. `设计意图.md` 第 33 行（作者原话）：「缺失和未打分无需区分」⇒ 沉默来源必须进分母。
2. 代数上，包含沉默来源恰好给出 S3 下限：

```
包含沉默：group[u]=0.5 → 比值 = 1/β = 3.33
排除沉默：group[u]=1.0 → 比值 = 1+(1−β)/(β·0.5) = 5.67
```

规格那句会让 S3 **从 3.33 恶化到 5.67**。

3. 两条错方向相反，正确的口径只有一个：

```
分子 = 我评过、且给出了非零读数的来源贡献
分母 = 我评过的全部来源的 份额×衰减 之和
```

**修法**：分母计入全部已评分来源（没观点、没提到都按 0 算）。实测把 236.67× 压到 3.33×。
注意：**这个修正等价于把 §4.9 的覆盖率项按权重算**，但不需要它的任何旋钮。

### 1.2 归一化先除后夹紧

```rust
// crates/engine/src/lib.rs:824
let mut v = stored.view.query(&target_key) / stored.total_mass;  // 分子没夹紧
v = v.clamp(0.0, 1.0);                                           // 先除后夹
```

声明值 ≥ K（受影响的账户数）时 `v = 1.0`，预算 `Σv = K`。**阈值与接收方账户数无关。**

| 场景 | Σv |
|---|---:|
| 合规视图 | 1.0000 |
| K 条各声明 1e3 / 1e6 / N | **K**（三行完全相同，说明已饱和） |

端到端（400 账户 / 31 来源 / 18 女巫 / 20 seed）：

| 攻击者视图 | 女巫/诚实全体 | 女巫占分布 | 榜首 |
|---|---:|---:|---:|
| 合规 | 0.49 | 2.26% | 0/20 |
| 放大 ×1e6 | **8.87** | **29.37%** | **20/20** |

18 个女巫占账户 4.5%，拿走 29.37% 信任，**超配 6.5 倍**。

**修法**：分子先夹紧，再除。对合规视图逐位不变（`q ≤ 1` 且 `T ≥ q`）。
或（A11 的另一版）：分母去掉上界 clamp，用 `Σ max(q,0)`。

### 1.3 Count Sketch：S4 结构性失败

| 发布端清单长度 m | 空账户出现率 | 拿走的总信任 | 最好的空账户 ÷ 真实均值 |
|---:|---:|---:|---:|
| 100 | 0.44% | 0.059% | 0.35 |
| 300 | 6.96% | 0.408% | 1.04 |
| 1000 | **30.4%** | **2.14%** | **1.33** |

- 这些账户**不消耗任何影响力预算**——旁路。
- 根因不是精度不够，是「精确的 0」与「不存在」在压缩视图里不可区分：m=1000 时 89.2% 的空账户查到精确 0，另 5.4% 为正。
- 噪声底当门限**在两端都失效**：m ≤1000 时 `noise.median = 0`（一个都挡不住）；m=10000 时把 51% 真实条目一起清零。

**重要限定**：仿真里清单约 100 人，所以实测只有 0.52%（A12 用真引擎复现出 0.113 倍、总信任 0.068%）。
**真人在 300~1000 人区间会掉进 7%~30%。**

## 6. 需要拍板的五个决策

这些不是缺陷，是设计选择。**前三个直接与 `设计意图.md` 的原文冲突，我不会自己动。**

### 决策 1 · β

| β | S3 收益方（渗 / 背） | 群体意见权重 |
|---:|---:|---:|
| 0.3（现行） | 1.695 / 4.105（**失败**） | 70% |
| 0.5 | — | 50% |
| 0.7（设计意图的「7:3」） | — | 30% |
| 0.9 | **0.355 / 0.728（通过）** | 10% |

交接文档「提高 β 无效」出自副仿真器，已被 A6 证伪。

### 决策 2 · 衰减

- **删**：S1/S2/S3 全部不变（CI 跨 0）。
- **留**：唯一能压攻击残余——一次结束的攻击在 600h 后留 **0.250（72h）/ 0.990（关闭）**。

它应该被定位成「伤害时效机制」，不是「反女巫机制」。

### 决策 3 · 份额

`设计意图.md` 原文：「权重是群体评分的权重」「按照自己观点的评分比值确定每份观点的权重」。

| 方案 | ΔS3 渗 | ΔS3 背 | 代价 |
|---|---:|---:|---|
| 等权（1/n） | **−0.542** | **−2.152** | S2 −38% |
| cap 2× 均值 | −0.004 | −0.025 | **完全无效** |
| cap 1.2× | −0.514 | −1.384 | — |

### 决策 4 · 视图表示

`设计意图.md` 原文：「对端不论装了多少账户，配额是固定的……想要提高精度就必须提高文件体积」。

sketch 保住了「体积与账户数无关」，但 S4 在 m≥300 就崩；稀疏表 S4 归零、快 2329 倍，但体积随清单增长。

### 决策 5 · 根目录 v1.0

6,838 行、58 个测试全绿，但描述的是**被推翻的算法**（β=0.7、线性衰减、按评分加权有放回抽样），
且 `crates/` 对它零代码引用。删还是留？
