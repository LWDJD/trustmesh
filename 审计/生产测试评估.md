# 生产测试评估：这个库能不能上生产

> 2026-11-17。回答作者：「现在这个库还差什么东西吗，能不能进行生产测试」。

## 0. 一句话

**能进行生产测试，但只能放在「受控环境」里——不能直接上公网。**

三条理由，全部有实测支撑：

1. **它的形态是纯计算库**：无 IO、无网络、无存储、无线程、无 unsafe（`engine` 本轮补上 `#![forbid(unsafe_code)]`）。
   所以「生产测试」的正确含义是 — **把它嵌进一个真实应用，跑真实数据，而不是指望它自己跑起来**。
2. **有 3 条数学上不可能修的失败项**（S3 背书 4.37×、S4 空账户、S5 自吹 83%），必须由应用层接受或兜住。
3. **有 2 条部署参数陷阱**（清单长度 m 决定 S4 崩不崩；k 决定衰减失不失效），配错了会「看起来能跑但其实失效」。

## 2. 它还差什么（生产前必须补的）

### 2.1 库内**永远**修不掉的三条（只能由应用层兜）

| 缺陷 | 实测 | 谁来兜 |
|---|---|---|
| **S3 背书**：8% 渗透者抬举同伙 | 4.374×（地板 3.333 的 1.31 倍），最坏观察者 **8.14×** | 应用层：**不要用声望做「唯一」准入依据**；或把 β 提到 0.9（代价是圈子化） |
| **S4 空账户**：碰撞噪声给空账户白送声望 | m=100 时 0.44%；**m=1000 时 30.4%**，最好空账户 **1.331×** 真实均值 | 应用层：**清单长度必须 ≤ 300**（否则 S4 崩） |
| **S5 自吹**：视图只写自己 1.0 | **+83%** 收益（「塞壳」防线有效，纯自吹无效） | 应用层：限制单来源影响力上限；或接受 |

**这三条是数学结论，不是 bug。** 报告在 `审计/威胁模型.md` §2。

### 2.2 部署参数陷阱（配错会让库「看起来能跑但实际失效」）

| 参数 | 正确值 | 配错的后果 |
|---|---|---|
| **清单长度 m** | **≤ 300** | m=1000 → S4 出现率 30.4%、空账户能拿到 1.331× 真实均值 |
| **k（每轮抽样数）** | `k ≥ 2·m·T/H`（用 `recommended_k()` 问） | A10 实测：m=600/k=8/T=30h ⇒ 刷新周期 93.75 天，**90.7% 来源衰减因子 < 0.1** |
| **`max_views`** | **必须显式设**（如 1000） | 默认 0 = 无限制 = 内存可被撑爆（10000 个 owner 时 **394.3 MiB vs 39.4 MiB，差 10 倍**） |
| **`beta`** | 默认 0.3 | 提到 0.9 可压 S3 但圈子化；**作者明确否过 9:1** |
| **桶数** | 2048（内存够时） | 512 桶在 m≥2000 时 S1 = 0.0633（**不可用**） |

### 2.3 规模硬墙（这条决定你能不能上）

| 网络规模 | 内存/节点（2048 桶） | 可部署？ |
|---:|---:|---|
| 200 | 16.7 MB | ✅ |
| 1000 | 80.3 MB | ✅ |
| **2000** | **183.4 MB** | ⚠️ 勉强 |
| **3000** | **275.5 MB** | ❌ 3000 节点全网 826 GB |

**500~1000 个账户的真实社区**是这个库现在的甜点区。更大的网络需要 A12 的定长稀疏表（体积降 14~50 倍）。

## 3. 本轮实际做了什么（可验证的增量）

### 3.1 补上 `#![forbid(unsafe_code)]`（engine）

`store`/`view`/`agg`/`sim` 早就有，`engine` 漏了。现在**全部生产 crate 都是零 unsafe**。

### 3.2 新增 `crates/engine/tests/untrusted_bytes.rs`（7 个测试）

瞄准**唯二**接收不可信字节的入口（`CompressedView::decode` / `EngineSnapshot::decode`）：

| 测试 | 守什么 |
|---|---|
| 长度不对的随机字节一律 `None` | 长度校验 |
| 长度恰好时：要么 `None`，要么「回编码逐字节相等 且 读数全有限」 | decode 唯一的语义承诺 |
| 每一个截断前缀都 `None` | 不部分恢复 |
| NaN / ±Inf 出现在**任意**单元位置都被拒 | 一条 NaN 会让所有 query 变 NaN |
| 极端 f32（sNaN / subnormal / -0.0 / MAX）**任何位置**都不 panic | 不崩 |
| 随机快照字节一律 `None` | 快照入口 |
| 合法快照的每一个截断前缀都 `None` | 不部分恢复 |

**⚠️ 这几个测试抓到了一个真实的理解偏差，值得记下来：**

> 我最初写的是「**随机字节一律必须 `None`**」，然后测试**红了**。
> 查下来发现这不是 bug，是我对 `decode` 契约的理解错了：
>
> `decode` 只校验三件事——参数合法、**长度恰好**、**每个 f32 有限**。
> 而一个 4 字节随机模式是 NaN/Inf 的概率是 0.39%（指数位全 1），
> 一份 64×3 = 192 单元的视图「全部有限」的概率是 (1−0.0039)^192 ≈ **47%**。
> 所以随机字节**经常**能通过长度与有限性校验——这是设计如此，不是漏洞。
>
> 语义边界在**引擎那侧**：`on_view` 把 `total_mass` 做 `clamp(0.0, 1.0)`、对非有限读数整条拒绝（P2 加固）。
> 所以正确的测试应该是「长度不对 ⇒ 必拒；长度恰好 ⇒ 要么拒、要么内容可解且有限」。

### 3.3 新增 `.github/workflows/ci.yml`（7 个 job，130 行）

| job | 做什么 | 为什么必须 |
|---|---|---|
| `test`（6 crate 矩阵） | `cargo test --all-targets` | 六个 crate 是**各自独立的 workspace**，根目录 `cargo test` 不会递归进去 |
| `test-legacy` | 根包 v1.0 | 作者要求保留 v1.0 |
| `doctest`（5 crate 矩阵） | `cargo test --doc` | 抓「文档漂移」——README 里的例子必须真能跑 |
| `lint`（6 crate 矩阵） | `cargo fmt --check` + `clippy -D warnings` | 风格与 lint 门禁 |
| **`wasm-parity`** | 编 wasm32 + native，`node run-compare.mjs` 逐位对拍 | **本库最值钱的性质，必须每次验证** |
| **`no-external-deps`** | 扫所有 `Cargo.toml`，非 `path` 依赖即失败 | 守住「零外部依赖」（供应链攻击面最小化） |

零依赖守卫的**正向与负向都验证过**：
* 正向：7 个 `Cargo.toml` 全部通过（`tm_engine`/`tm_exp` 的 3+5 个 `path` 依赖是合法的）；
* 负向：伪造一个含 `serde = "1.0"` 的 toml，守卫报 `EXTERNAL dependency: serde = "1.0"` 且 `exit=1`。

**`wasm-parity` job 的命令链已在本机逐条跑通**：

```
cargo build --release --lib --target wasm32-unknown-unknown   → exit 0
cargo build --release --bin tm_wasm_smoke_cli                 → exit 0
./target/release/tm_wasm_smoke_cli > native.txt                → 405 B, count=36
node run-compare.mjs native.txt                               → exit 0
  *** IDENTICAL: 36 个 f32 位模式，native x86_64 与 wasm32 逐位相同 ***
```

## 4. 能不能进行生产测试：三档答案

### 档 1：**可以立刻做** — 受控环境 / 小规模（≤ 300 个账户）

前提：
* 清单长度 **≤ 300**（保住 S4）；
* `max_views` **显式设上限**（如 1000）；
* `k` 用 `recommended_k()` 问，别自己拍；
* 应用层**验签**（库不做）+ **从 `shares()` 起步做节点发现**；
* 接受 S3（4.37×）/ S5（+83%）这两条，或用 β=0.9 换（代价：圈子化）。

**这档适合：内部试点、小社区、单机/局域网、受信节点之间。**

### 档 2：**可以做，但需要先补一件事** — 中等规模（300~1000 个账户）

需要先确认 **内存预算**（1000 账户 = 80.3 MB/节点）和**带宽预算**（`k×40KB/轮`）。
**这档适合：有资源规划的私有部署。**

### 档 3：**不能做** — 大规模（> 2000 个账户）

**内存硬墙**：2048 桶时 183 MB/节点（n=2000）、275.5 MB（n=3000）。3000 节点全网 826 GB。
**必须先把视图表示换成 A12 的定长稀疏表**（770~3074 B，比 Count Sketch 小 14~50 倍），
这一件事同时解决 S4、让「距离折扣」可实现、为 ZKP 铺路。

## 5. 生产测试应该测什么（给应用层的清单）

| # | 测什么 | 怎么判「过」 |
|---|---|---|
| 1 | **`freshness_budget()` 不报 `DecayDiluted`** | 跑满一个半衰期后 `verdict == Healthy` |
| 2 | **`rejected_count() == 0`**（或已知原因） | 攻击期间只有 `Capacity`；`NonFinite` 应恒为 0 |
| 3 | **快照 round-trip 逐位一致** | `restore` 后 `query` 位模式与原引擎相同 |
| 4 | **跨节点一致** | 两个节点对同一批 `(cfg, seed, 输入)` 给出**逐位**相同的声望 |
| 5 | **`shares()` 抗篡改** | 攻击者狂发观点后 `shares()` 内容不变 |
| 6 | **`max_views` 上限生效** | `rejected_count` 增长而 RSS 不涨 |
| 7 | **S1 = 0** | 纯女巫场景下女巫声望恒为 0 |
| 8 | **S3 符合预期** | 背书场景比值落在 [1/β, 1.31/β]（3.33~4.37） |
