# 耦合度评估（2026-11-22）

> 作者问：「组件之间的耦合度怎么样，是否恰到好处。我不想发正式版之后，改一个小东西需要牵一发动全身。」

> **结论**：耦合度**恰到好处偏低**。最坏情况（加一个运行状态字段）只破 1 个文件，且**编译期捕获**。
> 但有两处「改了会很痛」的地方需要知道：`SNAPSHOT_VERSION` 和 `ViewParams`。

---

## 0. 一句话

| 你要改的东西 | 要动几处 | 会不会漏 |
|---|---:|---|
| 加一个 **配置项**（EngineConfig 字段） | **1 处** | 编译器保证不漏 |
| 加一个 **运行状态**（Engine 字段） | **1 处**（snapshot.rs） | 编译器保证不漏 |
| 改 **衰减公式** | 1~2 处 | 有 3 条单元测试钉着 |
| 改 **快照格式** | 3 处 + 升版本号 | ⚠️ **没有测试锁**（见 §3.2） |
| 改 **ViewParams 字段** | 4 处（engine/src）+ 16 处（自己的测试） | 编译器保证不漏 |
| 加一个**内部模块** | 1~2 处 | 看它依赖谁 |

**没有「牵一发动全身」的情况。** 最坏的一个是改快照格式，代价不是「改很多地方」，而是「旧快照作废」。

## 1. 模块依赖图：干净的 DAG

实测的**生产代码**跨模块依赖（不含 tests/examples）：

```text
  store     -> (叶子，无依赖)
  view      -> (叶子，无依赖)
  agg       -> (叶子，无依赖)
  badlist   -> store
  budget    -> store, agg
  runtime   -> store, view, agg, badlist, budget
  criteria  -> runtime
  snapshot  -> store, view, runtime
```

**形状判定**：

| 指标 | 值 | 评价 |
|---|---|---|
| 有环吗 | 否 | ✅ 是 DAG |
| 层深 | 4（叶子 → badlist/budget → runtime → criteria/snapshot） | ✅ 合理 |
| `store`/`view`/`agg` 互相依赖 | **0** | ✅ 完全独立的原语 |
| fan-in 最高 | `store` = 4 | ✅ 合理（它是基础数据类型） |

**fan-in / fan-out 全表**：

| 模块 | fan-out | fan-in | 被谁依赖 |
|---|---:|---:|---|
| `store` | 0 | 4 | runtime, badlist, budget, snapshot |
| `view` | 0 | 2 | runtime, snapshot |
| `agg` | 0 | 2 | runtime, budget |
| `runtime` | 5 | 2 | criteria, snapshot |
| `badlist` | 1 | 1 | runtime |
| `budget` | 2 | 1 | runtime |
| `criteria` | 1 | 0 | （无人依赖） |
| `snapshot` | 3 | 0 | （无人依赖） |

**这是教科书级的 DAG**：叶子模块（store/view/agg）零依赖、零反向耦合；
只有一个汇聚点（runtime）；两个出口（criteria/snapshot 无人依赖，纯终点）。

## 2. 实测：三个「加东西」的场景

不是推测，是真的改了代码编译一遍然后还原。

### 2.1 加一个配置字段（最轻的情况）——**0 编译错误**

实验：在 `EngineConfig` 加 `new_field: u32`（含 default）。

结果：**`cargo check --all-targets` 退出码 0，0 错误。**

原因：全仓 **63 处** `EngineConfig { ... }` 字面量构造里，**61 处带 `..`**（`..Default::default()` 或 `..EngineConfig::default()`），
剩下 2 处一处是 `Default` 实现本身、一处是「先 `default()` 再逐字段赋值」。
所以加字段**只改 `struct` 定义 + `Default` 实现共 2 处**，其余调用方零影响。

⟹ **配置项的可加性很好。** 这是最常见的改动类型。

### 2.2 加一个运行状态字段（要进快照）——**只破 1 个文件**

实验：在 `Engine` 加 `pub(crate) new_stat: u64`。

结果：**4 个编译错误，全在 `snapshot.rs:815`**。

```text
error[E0063]: missing field `new_stat` in initializer of `Engine`
  --> src\snapshot.rs:815:14
```

⟹ 耦合确实存在（**Engine 的字段结构 = 快照格式**），但：
- **只影响 1 个文件**，不是「牵一发动全身」
- **编译期强制捕获**，不会静默出错
- 加字段的真实成本 = 字段 + 序列化 + 反序列化 + 升 `SNAPSHOT_VERSION` + 文档

**为什么只破 1 个文件**：`snapshot.rs` 是**唯一**直接读写 `Engine` 私有字段的模块
（实测：它访问 `accounts`(10) / `ratings`(10) / `views`(10) / `penalties`(8) / `clock`(3) /
`sampler`(2) / `cfg`(1) / `rng`(1) / `stat_requests`(4) / `stat_hits`(4) /
`stat_rejected_view`(4) / `stat_rejected_capacity`(4) / `stat_rejected_nonfinite`(4)，共 **13 个字段 65 次**）。
其余模块全走 `Engine` 的**公开方法**。

⟹ 这是**清醒的设计**：把所有"直接碰内部字段"的需求**收敛到一个文件**里。
加字段时你只需要改这 1 个文件，而且编译器会把 13 个字段的所有初始化点指出来。

### 2.3 改衰减公式（最容易出微妙的错）——**被测试钉住**

实验：把 `decay` 的 `0.5f64.powf(exponent)` 改成 `powf(exponent * 1.01)`（1% 系统性偏差）。

结果：**5 条测试失败**，其中 3 条是 `agg` 的单元测试：
- `decay_never_reaches_exact_zero`
- `decay_half_life_is_the_classic_value`
- `decay_integer_half_lives_are_exact`

⟹ **改核心数学有测试兜底。**

## 3. 两个「改了会很痛」的地方

### 3.1 `ViewParams` —— 50 处全字段字面量

`ViewParams { buckets, hashers, seed }` 是纯数据 struct，字段全 pub，
全仓有 **50 处**用字面量构造（**0 处**用 `..Default::default()`），另有 **87 处**走 `ViewParams::new(...)`。

但真实的破坏面比 52 小得多：

| 位置 | 处数 | 影响谁 |
|---|---:|---|
| `engine/src`（发布物内） | **2** | 会破坏源码内的用法（外部使用者走 `new()` 不受影响） |
| `engine/tests`（我们自己的） | 16 | 自己改 |
| `crates/exp`（实验，不进发布物） | 32 | 自己改 |

**关键缓冲**：外部使用者主要走 `ViewParams::new(buckets, hashers, seed)`（全仓 **87 处**用它，是字面量的 1.7 倍）。
加字段时只要让 `new` 保持兼容（新字段给默认值），**外部使用者零破坏**。

⟹ **建议**：如果你打算改 `ViewParams`（比如加个 `layout` 字段），
  1. 给 `ViewParams` 加 `#[non_exhaustive]`（阻止外部字面量构造，强制用 `new`）
  2. 或保持 `new` 的签名、新字段给默认值 —— 外部零破坏
  3. 改动真实代价 = `engine/src` 2 处 + 自己的 16 处测试（编译器会全部指出来）

### 3.2 `SNAPSHOT_VERSION` —— 改动会作废旧快照，且**没有测试锁**

这是**唯一一个「改了会静默出问题」**的地方。实测：

```text
把 SNAPSHOT_VERSION: 2 → 3
结果：479 条测试全绿，0 失败
真实后果：所有已存的 v2 快照文件全部解不开了
```

为什么测试没抓住：所有测试都用**同一个常量**（编码用 VERSION，解码也检查 VERSION），
常量一改两边一起变，永远自洽。

**这正好是你担心的那种风险**——但它的表现形式不是「牵一发动全身」，
而是「改一处，测试全绿，但线上数据读不出来」。

**补法（1 小时）**：

```rust
#[test]
fn v2_snapshot_bytes_are_still_decodable() {
    // 硬编码一段 2026-11-22 生成的 v2 快照字节
    const V2: &[u8] = &[/* ... */];
    let snap = EngineSnapshot::decode(V2).expect("v2 快照必须仍能解");
    assert_eq!(snap.version, 2);
}
```

有了这条之后，改 `SNAPSHOT_VERSION` 就会立刻红 —— 那时你必须显式决定「是否要破坏旧快照」。

## 4. 唯一真正「过度暴露」的地方

`lib.rs` 把四个模块全 `pub mod` 了，于是**146 个 pub 项全部成为对外契约**（含 impl 块里的方法）：

| 模块 | pub 项（含 impl 内方法） | |
|---|---:|---|
| `store` | 51 | |
| `view` | 23 | |
| `agg` | 7 | |
| `runtime` | 42 | |
| `budget` | 10 | |
| `criteria` | 13 | |
| **合计** | **146** | |

**这本身不是问题**（分开导出更好读），但要知道后果：
**「用户能 `use tm_engine::store::X` 的所有 X 都成为你的 API 承诺」**，改它们就是 breaking change。

### 实测：哪些是「真没人用」的

我逐项检查 `tests / examples / exp / tools`（即所有外部消费者）：

| 模块 | 外部 0 处使用的 pub 项 |
|---|---|
| `store` / `view` / `agg` / `runtime` | **0 个**（全都被用到过） |
| `budget` | 3 个：`normalized_half_life` / `effective_sample_size` / `assess`（但 `runtime` 内部在用 ⟹ 合理，是给应用层的诊断工具） |
| **`criteria`** | **7 个**：`judge_s1`~`judge_s6` + `s3_floor_for`（外部**真的 0 处**） |

`criteria` 的 7 个是**真过度暴露**：写了判据函数，但没人调（`crates/exp` 的验证装置用自己的实现）。

**要处理吗？** 两个选择：

| 选择 | 工作量 | 好处 |
|---|---|---|
| (a) 标 `#[deprecated]` 或删掉 | 10 分钟 | 少 7 个契约 |
| (b) 保留，但文档写明「内部验证用，不保证稳定性」 | 10 分钟 | 保留将来复用的可能 |

**建议 (b)**：判据函数是有价值的（它们把 S1~S6 的口径写死），只是暂时没消费者。

## 5. 判断：耦合度是否「恰到好处」

**是，偏低但合理。** 理由：

| 维度 | 评价 |
|---|---|
| 模块划分 | ✅ 按**职责**分（存/压/算/编排），不是按「文件方便」分 |
| 依赖方向 | ✅ 严格单向（叶子 → 编排 → 出口），无环 |
| 抽象层次 | ✅ `store/view/agg` 是**与信任语义无关**的通用原语（账户表、草图、衰减函数），可以独立复用 |
| 配置可加性 | ✅ 加字段 0 破坏（`..Default::default()` 覆盖全部构造点） |
| 状态可加性 | ✅ 只破 1 个文件，编译期捕获 |
| 核心数学 | ✅ 有单元测试钉住 |
| 测试可移植性 | ⚠️ `ViewParams` 全是字面量，但对外部使用者零破坏 |
| 跨版本兼容 | ❌ **无锁**（§3.2，唯一的真缺口） |

**唯一需要担心的是 §3.2**，而它不是「耦合」问题，是「缺一条测试」。

---

## 7. 一句话回答

> **不会「改一个小东西牵一发动全身」。**
>
> 最轻的改动（加配置项）0 破坏；最重的改动（加运行状态）破 1 个文件且编译期报错。
>
> **唯一需要补的是快照的跨版本测试** —— 它的问题不是「耦合太紧」，而是「耦合无锁」。
